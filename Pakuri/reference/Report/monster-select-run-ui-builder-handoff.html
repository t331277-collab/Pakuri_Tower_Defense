Pakuri 몬스터 선택 Run 구현 순서 고정 Handoff

이 문서는 Code Builder가 실제 구현에 들어갈 때 따라야 할 고정 순서를 정리한 handoff 문서다. 목적은 현재 이브 단독 전투 프로토타입 위에 몬스터 선택 UI, Run 시작, 전투 후 보상/스킬 선택을 붙일 때, 중간에 되돌이 리팩터링을 최소화하는 것이다.

현재 코드 근거: Assets/Scripts/Combat/EveVerticalSliceController.cs 현재 코드 근거: Assets/Scripts/Combat/DamageCalculator.cs 설계 근거: reference/monster-select-run-ui-expansion-plan.html 범위 고정: 4몬스터 우선 / 린 더미 작성 시각: 2026-04-25 23:16:23 +09:00

고정 범위

  • 확정 1차 플레이 가능 몬스터는 아리엘, 이브, 세인, 베가 4종이다.
  • 확정 린은 더미 카드로 남기고, 선택 불가 상태로 표시한다.
  • 확정 모든 몬스터는 패시브 슬롯 F~J 총 5개를 가진다고 보되, 런 중 실제 습득은 최대 3개까지만 허용한다.
  • 확정 포로 보상은 이번 범위에서 표시만 하는 정보로 처리하고, 영입 시스템은 구현하지 않는다.

왜 이 순서가 필요한가

  • 현재 코드 EveVerticalSliceController는 BeginPrototypeDay, ResolveEncounterForDay, PrepareVictoryRewards, ApplyReward, HandlePointerInput, DrawHud, DrawVictoryPanel처럼 Run 흐름, 전투, 보상, UI를 한 클래스에 함께 들고 있다.
  • 현재 코드 DamageCalculator.Resolve(...)는 단일 defense 값만 받는다. 문서 기준의 속성별 저항 구조와 다르다.
  • 현재 자산 .uxml, .uss 파일이 아직 없어 UI도 제로부터 시작해야 한다.

그래서 UI를 먼저 “예쁘게” 만들거나, 4몬스터 스킬을 바로 각개 구현하면 이후에 상태/데이터/전투 코어를 다시 뜯어야 할 가능성이 높다.

Builder 기본 원칙

  • 원칙 아직 런타임 효과가 없는 스킬/보상은 선택지에 노출하지 않는다.
  • 원칙 린은 플레이 가능한 엔트리로 승격하지 않는다.
  • 원칙 새 UI가 동작하기 전까지 기존 OnGUI를 완전히 제거하지 않는다. 전환 확인 후에만 치운다.
  • 원칙 각 단계는 완료 기준을 만족해야 다음 단계로 넘어간다.

고정 구현 순서

단계 목표 필수 산출물 완료 기준
1 Run 상태 분리 RunSession, RunFlowController 또는 동등 구조 일차/스테이지/보상 선택/선택 몬스터 상태가 더 이상 EveVerticalSliceController 한 곳에만 묶여 있지 않다.
2 카탈로그/데이터 뼈대 4몬스터 + 린 더미의 몬스터 메타데이터, 스킬 메타데이터 UI와 보상 풀이 코드 상수 대신 카탈로그를 참조할 수 있다.
3 UI Toolkit 껍데기 RunFrontPanel, RunHudPanel, RewardPanel 4몬스터 선택 버튼이 보이고, 린은 비활성 더미로 표시되며, 패널 전환이 동작한다.
4 공통 전투 코어 속성별 계산, 상태 저장소, 공통 유닛 런타임, 스킬 실행 인터페이스 이브 외 다른 몬스터도 같은 전투 루프에 연결할 수 있는 구조가 된다.
5 이브 이관 현재 이브 전투를 공통 코어 위 실행기로 이전 이브 플레이 결과가 기존 프로토타입과 크게 다르지 않게 유지된다.
6 기본 A 스킬 4종 아리엘/이브/세인/베가의 A 스킬 실행기 몬스터 선택 후 4종 모두 실제 전투 시작이 가능하다.
7 A/F 축 성장 루프 A 관련 특성, A 마스터, 대응 F 패시브, 보상 풀 생성기 전투 종료 후 현재 구현된 항목만 보상 후보로 나오고, 선택 결과가 다음 전투에 반영된다.
8 B/G 축 추가 4몬스터의 B 액티브, G 패시브, 관련 특성/마스터 B를 실제로 배우고 사용할 수 있을 때만 후보 노출이 열린다.
9 C/H, D/I, E/J 순차 추가 슬롯별 액티브/패시브 구현 각 슬롯은 전 몬스터 공통으로 한 묶음씩 완료 후 다음 슬롯으로 넘어간다.
10 보상/표시 마무리 전투 종류별 골드/어둠의 흔적/포로/유물 표시 정리 일반 전투, 중간보스, 보스 보상 화면이 문서 규칙대로 표시된다. 포로는 표시만 하고 영입은 없다.

단계별 세부 지시

  1. 1단계에서는 기존 파일을 크게 갈아엎기보다, 상태를 옮길 새 구조를 먼저 만들고 기존 이브 코드가 그 구조를 쓰게 바꾼다.
  2. 2단계에서는 최소한 몬스터 이름, 역할, 시작 액티브 A, 패시브 슬롯 구조, 더미 여부가 카탈로그에 들어가야 한다.
  3. 3단계에서는 디자인 완성도보다 상태 전환이 중요하다. 버튼/텍스트만 정확히 동작해도 통과다.
  4. 4단계에서는 속성별 방어력, 치명타 저항, 행동속도, 감전/추위/빙결/방어막/표식 등 공통 저장 구조를 먼저 만든다.
  5. 5단계는 이브를 기준 샘플로 삼는다. 이브가 공통 코어 위에서 다시 동작해야 이후 3몬스터 구현 리스크가 줄어든다.

왜 슬롯 단위로 확장하는가

  • 근거 monster-basic-rule.md는 A↔F, B↔G, C↔H, D↔I, E↔J 대응 구조를 정의한다.
  • 이점 몬스터 하나를 끝까지 파는 방식보다, 슬롯 묶음으로 가는 쪽이 보상 풀과 해금 규칙을 동시에 맞추기 쉽다.
  • 이점 예를 들어 B/G 축이 열리면, 그 순간부터 신규 액티브 B와 대응 패시브 G를 같은 보상 로직에 자연스럽게 넣을 수 있다.

초기 플레이 가능 기준

Builder는 아래 시점을 첫 번째 플레이 가능 마일스톤으로 삼아야 한다.

  • 몬스터 선택 UI에서 아리엘/이브/세인/베가 4개 중 하나를 고를 수 있다.
  • 선택 후 전투 HUD로 넘어가고, 각 몬스터의 A 스킬이 실제로 발동한다.
  • 전투 종료 후 보상 패널이 뜨고, 현재 구현된 A/F 관련 선택지 중 3개 이하를 보여 준다.
  • 선택한 보상이 다음 전투에 반영된다.

여기까지가 되면 Run 프레임은 성립한다. 그 다음부터 B/G, C/H, D/I, E/J를 순차 확장하면 된다.

금지 순서

  • 금지 UI 스킨 작업을 전투 코어 분리보다 먼저 길게 잡지 않는다.
  • 금지 린을 1차 플레이 가능 카드로 올리지 않는다.
  • 금지 B~E, G~J를 구현하지 않은 상태에서 보상 풀에 노출하지 않는다.
  • 금지 속성별 계산 구조 없이 문서 수치를 각 몬스터 클래스에 개별 하드코딩하지 않는다.

Code Builder explicit handoff

  • 이 handoff는 구현 순서를 고정한다. Builder는 1단계부터 순서대로 진행하고, 각 단계 완료 기준을 만족해야 다음 단계로 넘어간다.
  • 첫 구현 마일스톤은 4몬스터 선택 가능 + 각자의 A 스킬 전투 + A/F 보상 루프다.
  • 린은 현재 더미다. 린 관련 플레이 가능 로직을 추가하지 않는다.
  • 후속 B/G, C/H, D/I, E/J는 슬롯 묶음 단위로 구현한다.
  • 실제 구현 단계로 전환되면, Builder는 이 문서와 reference/monster-select-run-ui-expansion-plan.html을 함께 근거로 삼아야 한다.
