Skill Architecture Review

현재 Skill Runtime 구조 문제점과 개선안

이 문서는 현재 저장소에 구현된 스킬 런타임 코드를 직접 확인한 뒤, 왜 구조가 점점 거대한 공통 인터프리터로 비대해질 위험이 있는지와, 어떤 식으로 더 깔끔하게 정리할 수 있는지를 정리한 설계 보고서다.

핵심 결론
중앙 집중 비대화
스킬별 하드코딩은 줄였지만 공통 엔진 내부 예외 분기가 계속 커지는 방향이다.
현재 위험 축
4개
거대 snapshot, 거대 effect executor, 거대 trigger runtime, 확장형 mapper
권장 방향
조합형 IR
큰 스킬 타입 중심이 아니라 작은 동작 노드와 handler registry 중심으로 이동
먼저 요약: 지금 구조는 "CSV 기반이라서 안전한 구조"가 아니라, "CSV가 점점 더 많은 예외를 거대한 공통 코드에 밀어 넣는 구조"로 보인다. 데이터 기반 자체는 유지할 수 있지만, 현재처럼 넓은 필드 스키마와 중앙 switch 분기가 계속 늘어나는 형태는 장기적으로 유지비가 커진다.

현재 구조에서 실제로 보이는 문제

문제 현재 코드에서 보이는 증거 왜 위험한가
선택지와 패시브 modifier가 flat property로 누적됨 SkillExecutionSnapshot 가 수십 개 modifier property를 직접 소유하고, ApplyChoiceSpec 안에서 개별 필드별로 누적한다. 새 규칙 하나 추가할 때 property, 매핑, 적용 로직, 검증 로직이 전부 같이 늘어난다.
effect 실행이 중앙 executor 안에 집중됨 SkillMultiEffectExecutor 가 damage, status, status duration extension, 조건 평가, delay, zone spawn, visual spawn 까지 한 클래스에서 처리한다. 새 effect type 이나 예외 rule 이 들어오면 중앙 클래스가 계속 비대해진다.
trigger 행동 분기가 거대 switch 로 묶여 있음 SkillTriggerRuntime 가 event gate, proc gate, cooldown gate, count gate, delayed execution, action switch 를 모두 가진다. 트리거 액션이 늘 때마다 trigger runtime 전체가 바뀐다. action 별 책임 분리가 약하다.
runtime kind 와 authored field 매핑이 mapper 에 집중됨 InGameSkillDefinitionMapper 가 runtime kind 분기와 세부 authored field 변환을 직접 품고 있다. 새 runtime kind 또는 authored exception 이 생길 때 mapper 도 계속 커진다.
스킬 공통 데이터가 "큰 타입 + 예외 필드" 방식으로 누적됨 Projectile, Beam, Zone, SingleAttack, Buff, Shield 타입은 있지만, 실제 예외는 choice, trigger, multi-effect, status, branch, chain, execute 등으로 옆으로 계속 붙고 있다. 결국 타입 분리 이점보다 예외 조합 관리 비용이 더 커진다.
중요한 해석: 이 구조는 아직 "무조건 잘못된 구조"는 아니다. 다만 스킬 수가 조금 늘어나는 문제가 아니라, 예외 조합과 디자이너 요구가 계속 늘어나는 순간부터 중앙 해석기 코드가 시스템 병목이 될 가능성이 높다.

왜 이 구조가 하드코딩과 가까워지는가

겉모습

  • CSV 에 값 넣는다.
  • 스킬별 새 C# 스크립트를 매번 만들지 않는다.
  • 공통 executor 가 처리한다.

실제 내부

  • 새 요구 하나가 들어오면 공통 snapshot 필드가 늘어난다.
  • 새 trigger action 이 들어오면 중앙 switch case 가 늘어난다.
  • 새 multi effect 조건이 들어오면 중앙 effect evaluator 가 늘어난다.
  • 새 authored 의미가 들어오면 mapper 와 validator 도 함께 바뀐다.

즉 현재 구조는 스킬별 스크립트 하드코딩을 줄이는 대신, 공통 엔진 내부에 예외를 계속 적층하는 형태다. 코드가 더 이상 "스킬 A 전용, 스킬 B 전용"으로 흩어지지 않을 뿐, 중앙 엔진이 모든 스킬의 예외를 다 아는 방향으로 가고 있다.

스킬별 하드코딩 감소
중앙 인터프리터 하드코딩 증가
디자이너 자유도는 증가
엔진 유지보수 비용도 같이 증가

현재 구조를 유지했을 때 예상되는 장기 문제

  • 신규 기능 하나 추가할 때 수정해야 하는 파일이 매번 비슷하게 반복된다. snapshot, mapper, validator, executor, trigger runtime, effect runtime 이 같이 수정될 가능성이 높다.
  • 스킬 조합이 늘수록 테스트해야 할 경우의 수가 크게 늘어난다. 이는 스킬 수 증가보다 "예외 조합 증가"에서 더 크게 터진다.
  • CSV 컬럼이 계속 늘어나면 디자이너 입장에서도 "무슨 값을 어디에 써야 하는지" 이해 비용이 커진다.
  • 비슷한 요구가 조금씩 다른 이름과 필드로 중복 표현될 수 있다. 예를 들어 상태 연장, 상태 부여, 상태 조건, 상태에 의한 추가 피해가 각기 다른 축으로 따로 늘어난다.
  • 중앙 giant class 하나가 깨지면 다수 스킬이 동시에 영향을 받는다. 지역 수정이 어렵다.

더 좋은 방향: 큰 스킬 타입이 아니라 작은 동작 조합으로 바꾸기

현재 구조를 완전히 버릴 필요는 없다. 더 나은 방향은 CSV -> 거대한 runtime kind switch 가 아니라, CSV -> 작은 동작 노드 목록 으로 바꾸는 것이다.

현재 방식

  • 이 스킬은 Projectile 타입이다.
  • Projectile 타입 안에 branch, chain, status, delayed impact, on-hit effect, expire effect 예외를 계속 붙인다.

권장 방식

  • 이 스킬은 Cast, SpawnProjectile, ApplyDamage, ApplyStatus, TriggerOnHit, SpawnZone 같은 노드 묶음이다.
  • 새 요구는 "새 스킬 타입"이 아니라 "새 노드" 또는 "기존 노드 조합"이 된다.
핵심 변화: 스킬을 "타입 하나가 모든 것을 책임지는 구조"로 보지 말고, "작은 공통 연산이 순서대로 연결된 실행 계획"으로 보는 쪽이 더 확장성 있고 더 이쁘다.

구체적 개선안

개선안 설명 장점 주의점
1. Modifier property flood 축소 snapshot 안의 수십 개 전용 property 대신 modifier op list 나 delta bundle 구조로 정리 새 choice 규칙 추가 시 property 폭발을 줄일 수 있다. 기존 UI/CSV authoring 도구와의 호환 계층이 필요하다.
2. MultiEffect handler registry 도입 effect kind 별 중앙 switch 대신 effect handler 등록 방식으로 분해 새 effect 추가 시 giant class 수정 범위를 줄일 수 있다. 초기에는 handler wiring 코드가 추가된다.
3. Trigger action registry 도입 trigger action 을 action handler 로 분리하고, gate 와 action execution 을 나눔 trigger runtime 의 책임을 event selection 과 action execution 으로 나눌 수 있다. 기존 trigger enum 과 authoring 규칙 정리가 필요하다.
4. CSV wide schema 를 정규화된 row set 으로 분해 스킬 기본 정보, 행동, 조건, 트리거, modifier, 시각효과를 별도 테이블로 쪼갬 새 기능 추가 시 컬럼 증식보다 row 조합으로 해결하기 쉬워진다. 초기 authoring 난도는 약간 오를 수 있다.
5. Runtime kind 중심 설계를 primitive action 중심 설계로 전환 Projectile/Zone/SingleAttack 는 유지하더라도 최상위 개념이 아니라 reusable action 집합으로 낮춤 예외가 "새 타입"이 아니라 "새 행동 조합"으로 표현된다. 기존 executor 의 역할 재정의가 필요하다.

가장 현실적인 단계별 리팩토링 순서

1단계: giant class 분해부터 시작

  • SkillMultiEffectExecutor 에서 effect type 별 실행을 handler 로 분리
  • SkillTriggerRuntime 에서 action execution 을 action handler 로 분리
  • 현재 동작은 그대로 유지하고 파일 책임만 줄임

2단계: snapshot flat property 감축

  • choice 결과를 전용 property 나열 대신 grouped modifier record 로 수렴
  • status 관련 bonus, projectile branch 관련 bonus, chain 관련 bonus 를 각각 모듈화

3단계: authoring schema 정규화

  • 기존 CSV 를 유지하되 내부 로딩 시 공통 IR 로 변환
  • 새로운 기능은 wide column 추가보다 row 추가로 authoring 하도록 유도

4단계: primitive action pipeline 로 이동

  • 장기적으로는 스킬을 "실행 노드 리스트"로 구성
  • Projectile, Zone, SingleAttack executor 는 상위 orchestration 이 아니라 reusable action 묶음으로 낮춤
리팩토링 원칙: player-facing 동작, serialized 이름, asset reference, 기존 CSV 데이터 호환은 바로 깨지면 안 된다. 따라서 한 번에 새 구조로 갈아엎기보다, 기존 로더 위에 공통 IR 변환 계층을 얹는 점진적 전환이 가장 안전하다.

권장 목표 구조

계층 책임
Authoring Layer CSV 또는 데이터 에셋에서 스킬 정의를 입력한다.
Compile / Mapping Layer 입력 데이터를 작은 공통 IR, action node, condition node, modifier op 로 변환한다.
Execution Plan Layer 스킬 실행 순서, trigger graph, on-hit / on-expire / delayed plan 을 구성한다.
Runtime Layer cooldown, magazine, active duration, reload, cast state 같은 순수 런타임 상태만 관리한다.
Action Handler Layer damage, status, projectile spawn, zone spawn, cooldown refund 같은 최소 primitive 만 실행한다.

이 구조로 가면 "새 요구 = 새 giant skill type" 이 아니라 "새 요구 = 새 handler 하나 또는 기존 handler 조합" 으로 낮아진다.

호환성 제약과 유지해야 할 것

  • 기존 player-facing 스킬 동작은 유지해야 한다. 리팩토링은 behavior-preserving 방향이어야 한다.
  • 기존 asset reference 와 skill effect prefab 연결은 깨지면 안 된다.
  • 기존 CSV authoring 을 즉시 폐기하지 말고, 중간 변환 계층으로 흡수하는 편이 안전하다.
  • 기존 trigger event 와 choice id, skill id, passive id 문자열 호환은 유지해야 한다.
  • 검증 도구는 새 구조에서도 같은 authored 오류를 잡을 수 있어야 한다.

권장 acceptance criteria

  • 새로운 effect type 추가 시 중앙 giant class 의 switch case 증가 없이 handler 등록만으로 끝나야 한다.
  • 새로운 choice modifier 추가 시 snapshot 전용 property 추가가 필수가 아니어야 한다.
  • 새로운 trigger action 추가 시 trigger runtime 의 event gate 코드는 거의 바뀌지 않아야 한다.
  • 기존 skill id, choice id, passive id, effect prefab 배선은 그대로 동작해야 한다.
  • 최소 한 개 projectile 계열, 한 개 single-attack 계열, 한 개 zone 계열, 한 개 buff/shield 계열이 이전과 같은 결과를 내야 한다.
