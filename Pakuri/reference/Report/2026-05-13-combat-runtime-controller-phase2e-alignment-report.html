1. 요약 결론

현재 Phase 2-E까지의 리팩토링은 원 제안의 방향과 일치한다. 특히 상태 소유권을 먼저 문서화하고, 싱글톤으로 전투 runtime state를 빼지 않았으며, Manifested Party를 먼저 분리한 점은 제안의 9번 권장 결론을 실제 작업 순서로 따른 것이다. 그러나 Projectile / Effect / Drone은 아직 "등록 facade + manifested projectile/drone helper 분리" 단계이고, Enemy Simulation은 아직 시작되지 않았다. 따라서 전체 권장 결론은 "Phase 2 범위에서는 충족, 전체 refactor 목표로는 진행 중"으로 판단한다.

4. 9번 권장 결론 충족도

권장 결론 현재 판정 근거 남은 조건
CombatRuntimeController는 장기 유지보수와 AI 협업 비용이 높은 구조다. 부분 완화 현재도 CombatRuntimeController.cs:307-310이 battlefield lists를 보유하고, :326, :336, :357, :369가 selected-unit runtime state를 보유한다. 다만 Phase 2 파일들은 manifested party 문맥을 별도 파일로 나누어 읽기 범위를 줄였다. Projectile, enemy, selected-unit 책임이 아직 controller partial에 남아 있어 전체 God Class 문제는 남아 있다.
작은 작업을 작은 context 안에서 끝낼 수 있게 만든다. Manifested 범위 충족 새 파일은 ManifestedPartyRuntime 75 lines, Skills 141 lines, Drones 118 lines, Visuals 168 lines, View 304 lines, Damage 490 lines로 역할별 읽기 단위가 생겼다. 전체 CombatRuntime*.cs는 현재 20 files / 16,221 lines라서 projectile/enemy/selected-unit 작업은 여전히 큰 context가 필요하다.
파일 분리보다 상태 소유권 분리가 중요하다. 방향 충족 Phase 0 ownership map이 있고, CombatRuntimeManifestedPartyRuntime.cs:21-25가 manifested monster/drone/slot collection을 소유한다. CombatRuntimeBattlefield.cs:42-79는 battlefield 등록 facade를 제공한다. CombatBattlefieldState는 아직 controller의 list 참조를 감싼 facade다. projectile/effect/drone simulation owner 자체는 Phase 3에서 분리해야 한다.
싱글톤은 runtime state 문제의 해법이 아니다. 충족 Phase 1/2의 새 state boundary는 new CombatBattlefieldState(...), new ManifestedPartyRuntime(...)인 controller instance 소유 객체다. 검색 결과 새 Phase 파일에서 runtime state singleton은 발견되지 않았다. 기존 CombatEffectFactory는 internal static class factory이며 battlefield runtime state 저장소가 아니다. 앞으로 Phase 3-7에서도 battle session state를 static/global singleton으로 올리지 않아야 한다.
가장 먼저 손댈 곳은 Manifested Party, Projectile / Effect / Drone, Enemy Simulation 경계다. 순서 충족, 범위 진행 중 Manifested Party는 Phase 2-E까지 완료됐다. Projectile / Effect / Drone은 Phase 1 facade와 Phase 2-C/2-E의 manifested drone/projectile helper 분리로 진입했다. Projectile / Effect / Drone Simulation의 update/lifecycle owner 분리와 Enemy Simulation 분리는 아직 남아 있다.

5. 현재 코드가 보여주는 남은 결합

  • CombatRuntimeController.Update()는 여전히 UpdateSpawning(), UpdateEnemies(), UpdateProjectiles(), UpdateManifestedMonsterPartyCombat(), UpdateSelectedMonsterCombat() 순서를 직접 호출한다. 확인 위치는 CombatRuntimeController.cs:498-503이다.
  • UpdateProjectiles()와 UpdateSelectedMonsterCombat()은 아직 CombatRuntimeProjectiles.cs:14, :516에 있다.
  • UpdateSpawning()과 UpdateEnemies()는 아직 CombatRuntimeEnemies.cs:306, :706에 있다.
  • 선택 몬스터 runtime adapter는 아직 MonsterSkillRuntimeBase가 CombatRuntimeController 전체 참조를 가진다. 확인 위치는 CombatMonsterSkillRuntime.cs의 constructor와 protected CombatRuntimeController Controller 속성이다.
  • CombatUnitRuntime.cs:193은 여전히 Owner.TickManifestedUnitSkill(this, Skills[i], elapsed) callback을 호출한다. Phase 2-B는 이 경로를 보존한 상태에서 dispatcher만 분리했다.
  • 직접 battlefield list add는 CombatRuntimeBattlefield.cs:63, :68, :73, :78 내부에 집중되어 있다. 다른 검색 결과의 HitEnemies.Add, hitEnemies.Add는 projectile hit set 기록이고 battlefield list 등록은 아니다.

6. 남은 작업

  1. Phase 2 마감 판단: CombatRuntimeParty.cs에 남은 Rin shockwave, persistent field, Eve frost field, Vega queued projectile call-site를 더 쪼갤지 결정한다. 현재 보드의 다음 액션처럼 "더 작은 formula/field-effect slice가 실제로 식별될 때만" 추가 Phase 2를 진행하는 편이 안전하다.
  2. Phase 3. Projectile / Effect / Drone Simulation Split: UpdateProjectiles(), skill effect ticking, battlefield drone ticking/cleanup을 simulation boundary로 옮긴다. 목표는 CombatRuntimeController.Update()가 좁은 simulation tick만 호출하게 만드는 것이다.
  3. Phase 4. Enemy Simulation Split: spawn counters, enemy movement/status timers, enemy target priority를 enemy simulation boundary로 옮긴다. EnemyRuntime private nested class를 밖으로 빼거나 adapter로 감싸는 작업은 이 시점부터 검토한다.
  4. Phase 5. Selected Unit Combat Split: selected 1P HP/shield/ammo/reload/automatic skill trigger를 controller field 중심에서 selected-unit combat boundary로 옮긴다. 기존 HUD와 selectedUnitRuntime mirror는 호환성 때문에 한 번에 제거하지 않는다.
  5. Phase 6. Monster Runtime Adapter Interface Narrowing: CombatMonsterSkillRuntime.cs가 full controller 참조 대신 target query, damage, battlefield spawn, temporary effect용 좁은 인터페이스를 보게 한다.
  6. Phase 7. CombatTarget / TemporaryEffect Migration: selected unit, manifested unit, enemy를 ICombatTarget 또는 adapter로 읽을 수 있게 만든 뒤, shield/action speed/status 같은 transferable effect를 공통 temporary effect 경로로 옮긴다.
  7. 검증/운영: 각 code slice마다 runtime/editor build, git diff --check, Unity-MCP refresh/console evidence, 관련 board update를 유지한다. Play Mode gameplay 검증은 현재 프로젝트 규칙상 user-owned이다.

7. 최종 판단

Phase 2-E까지의 작업은 원 제안의 "먼저 상태 소유권을 정하고, Manifested Party를 먼저 분리하고, runtime state를 singleton으로 옮기지 말라"는 방향을 지키고 있다. 특히 Phase 2는 단순 파일 쪼개기만 한 것이 아니라 party collection/service, view, dispatch, drone lifecycle, visual, generic damage/projectile helper라는 책임 단위로 읽기 범위를 줄였다.

하지만 9번 권장 결론 전체가 끝난 것은 아니다. Projectile / Effect / Drone은 facade와 manifested helper 수준까지 진행됐고, full simulation split은 Phase 3로 남아 있다. Enemy Simulation, Selected Unit Combat, adapter narrowing, common target/effect migration도 아직 구현 전이다.

검증 한계: 이 보고서는 정적 파일 점검과 기존 board/reviewer evidence 기반이다. 이 문서 생성 과정에서 runtime C# 파일을 변경하지 않았고, Unity Play Mode는 실행하지 않았다.
