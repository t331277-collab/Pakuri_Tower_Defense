몬스터 객체 지향 리팩토링 및 현현 런타임 현황 보고서

작성일: 2026-05-08 / 역할: Designer / 기준: 실제 코드, 보드 기록, 빌드 및 Unity-MCP 콘솔 증거

이 문서는 현재 작업 내용, 몬스터 객체 지향 리팩토링의 구조 변화, 현현 몬스터 스킬 이관 상태, 아직 남은 몬스터별 작업, 그리고 리팩토링 전 구조의 문제점을 정리한다.

1. 현재 작업 내용 요약

현현 Rin 패시브 이관

구현됨

현현 Rin의 스킬 피해 경로가 Rin 전용 unit helper를 타도록 확장됐다. TryApplyRinUnitProjectileHit(...), ApplyRinUnitSkillDamage(...), GetRinUnitActionSpeedMultiplier(...)가 그 근거다.

현현 HP SlideBar

구현됨

현현 슬롯에 HP bar fill renderer가 없으면 EnsureManifestedHpBar(...)가 MonsterHpBar, Background, Fill, Shield를 보강한다.

적의 현현 몬스터 공격

구현됨

적 타겟 선택이 선택 1P만 보지 않고 살아있는 현현 유닛을 후보로 포함한다. 원거리 투사체도 TargetManifestedUnit을 저장해 현현 유닛에게 피해를 적용한다.

2. 리팩토링 전 구조의 문제점

이전 현현 구조의 핵심 문제는 "선택 몬스터 전용 런타임"과 "현현 몬스터 공통 런타임"이 분리되어 있었다는 점이다. 선택 몬스터는 각 몬스터 전용 partial script 안의 세부 로직을 탔지만, 현현 몬스터는 CombatRuntimeParty의 공통 피해/쿨다운/시각효과 계산을 주로 탔다.

  • 선택 몬스터 전용 로직에는 몬스터별 패시브, 내부 타이머, 추가 피해, 특수 투사체, 특수 상태가 들어 있었다.
  • 현현 공통 로직은 SkillDefinition과 Offering 선택 일부를 반영했지만, 몬스터별 private helper와 완전히 같지는 않았다.
  • 그 결과 Rin C 넉백, Sein A 관통, Eve C 지속 장판, Vega A 3연속 투사체처럼 선택 몬스터에서는 되지만 현현에서는 빠지는 차이가 생겼다.
  • 현현 UI도 슬롯 하위 오브젝트를 재사용하지 못하거나 HP bar가 없을 때 fallback이 부족해 이름/HP/바 표현이 흔들렸다.
  • 전투 대상 구조도 선택 몬스터 중심이어서, 적이 현현 몬스터를 동일한 아군 전투 유닛으로 취급하지 못했다.

3. 현재 구조

3.1 RunSession 상태

RunSession은 선택 몬스터와 현현 파티 상태를 분리해서 보관한다. ManifestedMonsterIds, EnsurePartyMemberState(...), RunMonsterState.LearnedActives, RunMonsterState.ChosenRewardIds가 근거다. 즉 현현 몬스터도 Offering으로 획득한 액티브와 강화 선택을 자기 상태로 가질 수 있다.

3.2 CombatUnitRuntime

CombatUnitRuntime은 현현 몬스터가 붙는 단위 컴포넌트다. 여기에는 MonsterDefinition, RunMonsterState, HP/공격 스탯, UI 참조, 그리고 List<CombatSkillRuntime>가 묶인다.

3.3 CombatSkillRuntime

CombatSkillRuntime은 스킬 하나의 쿨다운, 탄창, 발사 간격, 재장전 상태를 가진다. 현현 몬스터가 여러 스킬을 가져도 각 스킬이 독립된 런타임 상태를 가질 수 있게 만든 구조다.

3.4 CombatRuntimeParty

CombatRuntimeParty는 2PMonster부터 5PMonster까지의 씬 슬롯에 CombatUnitRuntime을 바인딩하고, 각 유닛의 TickManifestedCombat(...)을 통해 스킬 실행을 위임한다. 또한 Eve/Rin처럼 unit executor가 있는 몬스터는 공통 경로보다 먼저 전용 unit 경로로 보낸다.

3.5 전투 서비스와 책임 분리

현재 구조에서 CombatUnitRuntime은 유닛 상태를 소유하고, CombatRuntimeController partial들은 전장 서비스 역할을 한다. 투사체 생성, 피해 계산, 이펙트 생성, 적 상태 변경은 여전히 컨트롤러 partial에 있다. 이 방식은 유닛 상태와 전장 행위를 나누지만, 아직 모든 몬스터가 unit executor로 완전히 넘어간 상태는 아니다.

5. 앞으로 해야 할 작업 순서

  1. Play Mode 검증 기준 확정: 현현 Rin, Eve를 기준으로 선택 1P와 현현 2P-5P의 피해, 쿨다운, 패시브, 이펙트, HP bar, 적 타겟팅을 먼저 확인한다.
  2. Sein unit executor 이관: 현재 선택 Sein은 특수 projectile/field/line 구조가 많다. 현현 common multiplier만으로는 완전 동일성이 어렵기 때문에 Sein을 다음 후보로 보는 것이 합리적이다.
  3. Vega unit executor 이관: Vega는 이름표식, 침묵, 처형, 취약, 쿨다운 충전처럼 상태 연동이 많다. A는 일부 맞췄지만 B-E/F-J를 unit 기반으로 묶어야 한다.
  4. Ariel unit executor 이관: Ariel은 shield ownership과 Holy Exposure가 핵심이다. 단순 피해보다 보호막 소유/소모/반사/성역 상태를 unit별로 분리해야 한다.
  5. 공통 Manifested fallback 축소: 각 몬스터가 unit executor를 갖게 되면 CombatRuntimeParty의 몬스터별 multiplier 표와 generic skill fallback은 보조 경로로 줄여야 한다.
  6. 1P 완전 통합 여부 결정: Eve/Rin처럼 선택 1P도 selectedUnitRuntime을 통해 자동 스킬을 많이 쓰기 시작했다. 모든 몬스터를 이 방식으로 통일할지, 수동 A 입력은 기존 글로벌 입력 경로에 남길지 결정해야 한다.

6. 구조상 남은 리스크

  • 동일한 이름의 두 경로: 같은 스킬이 선택 몬스터 전용 함수와 현현 공통 함수에 나뉘어 있으면, 한쪽 수정이 다른 쪽에 반영되지 않는 문제가 반복될 수 있다.
  • 몬스터별 상태의 위치: Rin timer 일부는 CombatUnitRuntime에 올라갔지만, 다른 몬스터의 선택 전용 private field는 아직 각 partial controller에 남아 있다.
  • 공통 multiplier 표의 한계: ResolveManifestedSkillDamageMultiplier(...) 같은 표는 단순 수치 강화에는 맞지만, delayed projectile, shield ownership, mark consume 같은 행동 차이는 표현하기 어렵다.
  • 검증 범위: Codex는 AGENTS 규칙상 Play Mode를 직접 검증하지 않는다. 빌드/컴파일/콘솔 증거는 통과했지만, 실제 전투 체감 검증은 사용자가 수행해야 한다.

8. 결론

현재 구조는 현현 몬스터를 단순 복제 오브젝트가 아니라 CombatUnitRuntime을 가진 파티 유닛으로 다루는 방향으로 바뀌었다. Eve와 Rin은 이 방향이 실제 코드에 가장 많이 적용된 상태다. 반면 Sein, Ariel, Vega는 선택 몬스터용 구현이 존재하고 현현 common parity도 일부 들어갔지만, 선택 몬스터와 완전히 같은 스킬 로직을 보장하려면 각 몬스터 전용 unit executor를 추가로 만들어야 한다.
