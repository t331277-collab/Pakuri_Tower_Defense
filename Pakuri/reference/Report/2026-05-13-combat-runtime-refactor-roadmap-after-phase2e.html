4. 전체 리팩토링 로드맵

Phase 0. State Ownership Map

상태: 완료.

boards/REFACTORING/COMBAT_STATE_OWNERSHIP_MAP.md가 현재 owner, proposed owner, move phase, compatibility rule을 기록한다.

다시 하지 않는다. 이후 phase에서 새 owner 누락이 발견될 때만 보완한다.

Phase 1. Battlefield Facade Boundary

상태: 완료.

CombatRuntimeBattlefield.cs:22-39가 enemy/projectile/effect/drone 등록 facade를 제공한다.

아직 simulation owner는 아니다. Phase 3에서 이 facade를 lifecycle owner 방향으로 확장한다.

Phase 2. Manifested Party Runtime Split

상태: Phase 2-E까지 완료, 마감 가능.

party runtime, view, skill dispatcher, drone lifecycle, visual, generic damage/projectile helper가 분리됐다.

Phase 2-F는 기본 작업이 아니다. 더 작은 formula/field-effect slice가 코드에서 명확히 확인될 때만 추가한다.

Phase 3. Projectile / Effect / Drone Simulation Split

상태: 다음 기본 작업.

UpdateProjectiles(), skill effect ticking, battlefield drone ticking/cleanup을 simulation boundary로 옮긴다.

목표는 등록 facade를 넘어 projectile/effect/drone lifecycle을 controller partial에서 읽지 않아도 되는 단위로 만드는 것이다.

Phase 4. Enemy Simulation Split

상태: Phase 3 이후.

UpdateSpawning(), UpdateEnemies(), GetEnemyPriorityTarget(...)를 enemy simulation boundary로 옮긴다.

EnemyRuntime private nested class를 밖으로 빼거나 adapter로 감싸는 작업은 이 단계에서 검토한다.

Phase 5. Selected Unit Combat Split

상태: Phase 4 이후.

1P HP, shield, ammo, reload, automatic skill trigger, selected status visuals와의 결합을 selected-unit combat boundary로 좁힌다.

기존 HUD, public read path, selectedUnitRuntime mirror는 한 번에 제거하지 않는다.

Phase 6. Monster Runtime Adapter Interface Narrowing

상태: Phase 5 이후.

CombatMonsterSkillRuntime.cs:29의 full controller 참조를 target query, damage, battlefield spawn, temporary effect 계약으로 나눈다.

스킬 재사용 리팩토링은 이 단계에서 본격화한다.

Phase 7. CombatTarget / TemporaryEffect Migration

상태: Phase 6 이후.

selected unit, manifested unit, enemy를 ICombatTarget 또는 adapter로 읽을 수 있게 만든 뒤 action speed, shield, status 계열을 공통 temporary effect path로 옮긴다.

바로 모든 HP/shield/status field를 CombatTargetModel로 옮기면 source of truth가 둘로 갈라질 위험이 있다.

Phase 8. Common Actor/Base-Class 승격 판단

상태: Phase 7 안정화 이후에만 검토.

현재 EnemyRuntime은 controller private nested class이고, CombatUnitRuntime은 MonoBehaviour다. 바로 상속 계층으로 묶으면 scene/runtime 결합이 커진다.

ICombatTarget, resource/modifier/effect API가 안정된 뒤 중복이 명확한 부분만 CombatActorBase 또는 순수 model base로 승격한다.

5. 스킬 재사용 리팩토링의 적절한 타이밍

제안 권장 타이밍 이유
투사체 스킬끼리 재사용 구조화 Phase 3에서 기반을 만들고, Phase 6에서 본격적으로 executor/interface화한다. 현재 CombatRuntimeProjectiles.cs:14가 projectile update를 갖고 있고, Phase 1 facade는 등록만 감싼 상태다. 먼저 projectile lifecycle boundary가 있어야 projectile skill executor가 안정적으로 공유된다.
광선 / line / 지속 효과 공격끼리 재사용 구조화 Phase 3에서 skill effect ticking/lifetime을 분리한 뒤, Phase 6-7에서 target/effect API와 결합한다. CombatRuntimeManifestedPartyVisuals.cs는 manifested visual helper만 분리한 상태다. 전체 skill effect simulation owner와 temporary effect path는 아직 없다.
소환 / drone / field object 스킬끼리 재사용 구조화 Phase 3에서 drone/effect object lifecycle을 simulation boundary로 옮긴 뒤, Phase 6에서 skill adapter가 controller 전체를 보지 않게 만들 때 정리한다. Phase 2-C는 manifested Eve drone lifecycle만 분리했다. battlefield drone list 자체는 아직 controller list/facade 구조에 묶여 있다.
몬스터별 스킬 파일을 전면 재분류 Phase 6 이전에는 피한다. CombatMonsterSkillRuntime.cs:29가 full controller 참조를 유지하는 동안 전면 재분류를 하면 파일만 바뀌고 dependency는 그대로 남을 위험이 크다.

6. 공통 전투 대상 모델과 Monster / Enemy 상속 타이밍

항목 권장 타이밍 근거 기반 판단
ICombatTarget / read adapter Phase 7 초입 shared-combat-target-and-temporary-effect-design.html은 selected target, CombatUnitRuntime.Target, EnemyRuntime.Target 연결을 제안한다. 그러나 combat-refactor-start-plan.html은 먼저 wrapper/adapter로 읽기 경로부터 공통화하라고 제한한다.
CombatTargetModel Phase 7에서 adapter 검증 후 현재 selected HP/shield/ammo, manifested unit state, enemy status가 서로 다른 저장소에 있다. 즉시 model로 옮기면 기존 field와 model이 동시에 source of truth가 될 수 있다.
TemporaryEffectInstance Phase 7 중후반 shared target 보고서는 action speed, shield 같은 공통성이 높은 효과부터 옮기고, shock/chill/vulnerable처럼 후속 로직이 많은 상태는 뒤로 미루라고 한다.
Monster / Enemy 공통 상위 클래스 상속 Phase 8, 즉 Phase 7 안정화 이후 현재 EnemyRuntime은 private nested class이고 CombatUnitRuntime은 MonoBehaviour다. 따라서 바로 common base class를 만들기보다 ICombatTarget / adapter와 effect layer가 안정된 뒤 중복이 실제로 보이는 부분만 승격한다.

판단: 기존 로드맵에는 큰 단계로는 포함되어 있었다. 다만 항목별 타이밍, 같은 스킬 타입끼리 묶는 리팩토링 범위 보류, 그리고 프리팹 기반 Monster / Enemy 공통화의 위치가 충분히 분리되어 있지 않았으므로 이 섹션을 추가한다.
2026-05-10 제안 항목 기존 로드맵 포함 여부 보강 후 타이밍 근거와 이유

Phase 7-B: selected / manifested / enemy 상태를 공통 read 경로로 검증.

프리팹 기반 Enemy / Monster 생성 제안 기존 로드맵에는 명시 부족. Phase 4 이후 enemy simulation이 분리된 뒤 검토하고, 실제 적용은 Phase 8의 actor view 공통화에서 결정한다. 프리팹은 scene-facing 표현, collider, label, HP/shield bar 조립을 안정화하는 데 유리하다. 하지만 공통 전투 상태의 정답은 prefab 상속보다 ICombatTarget / CombatTargetModel 쪽이어야 한다. 그래서 제안 방향은 "전투 상태는 pure model / interface, 표시와 씬 구성은 prefab component"로 분리하는 것이 더 안전하다.
임시 효과 재사용 포함됨. 하지만 shield와 복합 상태의 순서를 더 명확히 해야 했다. Phase 7-C의 action speed 1개 성공 후 Phase 7-D shield, Phase 7-E 일반 modifier, Phase 7-F 복합 상태 순서로 진행한다. 2026-05-10 보고서의 성공 기준은 선택 아군, 소환 아군, 적군 모두가 공통 채널을 읽고, 적용/갱신/만료/스택 규칙을 공통 effect layer에서 재현하는 것이다. 현재 shield와 status는 선택/소환/적군 코드에 직접 기록되므로, 가장 단순한 modifier로 공통 layer를 검증한 뒤 확장한다.

보강된 권장 방향

  • 사용자가 제안한 "투사체는 투사체끼리, 광선 공격은 광선 공격끼리, 소환 스킬은 소환 스킬끼리" 묶기는 방향이 맞다. 다만 이 범위는 지금 확정하지 않고, Phase 3에서 lifecycle owner를 만든 뒤 Phase 6에서 adapter interface를 좁힐 때 같이 결정한다.
  • Monster / Enemy 공통화는 "부모 클래스 상속"보다 "공통 target interface + pure combat model + scene-facing prefab/view component" 순서가 더 안전하다. 이 방식은 현재 enemy가 private runtime이고, manifested unit만 MonoBehaviour인 코드 차이를 흡수할 수 있다.
  • 프리팹은 버리지 않는다. 다만 전투 상태의 공통 정답으로 쓰지 말고, enemy / monster 표시물, label, HP/shield bar, collider, sprite 구성의 공통 view 조립 도구로 Phase 8에서 검토한다.

9. 금지 / 보류 규칙

  • Phase 3에서 CombatTargetModel을 만들고 모든 HP/shield/status field를 옮기지 않는다. 이는 기존 controller field와 이중 source of truth를 만든다.
  • Phase 3에서 monster skill executor 전체를 투사체/광선/소환으로 전면 재분류하지 않는다. adapter가 아직 full controller를 본다.
  • Phase 4 전에 enemy target model 상속 구조를 확정하지 않는다. enemy spawn/update/targeting ownership이 먼저 분리되어야 한다.
  • Phase 7 전에 common base class를 강제하지 않는다. 현재 EnemyRuntime과 CombatUnitRuntime의 runtime 형태가 다르다.
  • 같은 스킬 타입끼리 묶는 리팩토링 범위를 지금 확정하지 않는다. projectile / effect / drone owner와 adapter interface가 먼저 안정되어야 한다.
  • enemy prefab화를 common combat model의 대체물로 쓰지 않는다. prefab은 scene-facing view / authoring 문제를 풀고, target/effect owner는 pure model / adapter 쪽에서 푼다.
  • runtime combat state를 singleton/static global state로 올리지 않는다. 기존 제안은 mutable battle state singleton을 권장하지 않는다.

10. 최종 결론

Phase 2-E까지의 작업은 Manifested Party 분리 목표를 달성했고, reviewer 결과까지 통과했으므로 현재 기준으로는 Phase 2를 마감해도 된다. 다음 기본 작업은 Phase 3 Projectile / Effect / Drone Simulation Split이다.

사용자가 제안한 스킬 재사용 리팩토링은 방향이 맞지만, 즉시 전면 적용할 단계는 아니다. Phase 3에서 projectile/effect/drone lifecycle 기반을 만들고, Phase 6에서 monster runtime adapter를 좁힌 뒤 투사체, 광선/line/field, 소환/drone 계열 executor로 재사용 구조를 잡는 순서가 안전하다. 이때 어떤 스킬을 어느 타입으로 묶을지는 아직 확정하지 않고, 실제 Phase 6 리팩토링 시작 시 사용자와 함께 다시 범위를 정한다.

공통 전투 대상 모델은 Phase 7에서 ICombatTarget / adapter로 시작한다. Monster / Enemy 공통 상위 클래스 상속은 Phase 7의 target/effect layer가 안정된 후, 실제 중복이 분명한 부분만 Phase 8로 승격하는 것이 현재 코드 근거상 가장 안전하다. 프리팹 기반 공통화는 Phase 4 이후 enemy simulation 경계가 생긴 뒤, Phase 8에서 scene-facing view / authoring component로 검토하는 쪽을 권장한다.
