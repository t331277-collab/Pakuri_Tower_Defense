Pakuri 데이터 구조 검토

이 문서는 현재 저장소의 실제 데이터 코드와 파일 구조를 기준으로, 왜 현재 데이터 파이프라인이 장기 운영에 불리한지 설명하고 회의에서 예상될 수 있는 반론과 그에 대한 재반론, 그리고 개선 작업 방향을 비즈니스 톤으로 정리한 HTML 장표다.

대상: 현재 논의를 처음 보는 팀원 기준일: 2026-05-01 근거 범위: Pakuri/Assets/Scripts/Data, Pakuri/data, Pakuri/reference/2.Monster 핵심 파일: PakuriGameDataSeeder.cs

1. Executive Summary

현재 구조의 핵심 문제는 ScriptableObject 자체보다 데이터 원본이 하나로 고정되어 있지 않다는 점에 있다.

  • 일부 데이터는 Pakuri/data/*.csv에 있다.
  • 일부 데이터는 Pakuri/reference/2.Monster/.../*.md를 파싱한다.
  • 일부 데이터는 PakuriGameDataSeeder.cs 내부에 직접 하드코딩되어 있다.
  • 런타임은 최종적으로 GameDataCatalog.asset 및 MonsterDefinition, EnemyDefinition만 사용한다.

이 구조는 데이터 작성 경로, 검증 시점, 장애 추적 경로를 분산시킨다. 결과적으로 신규 작업자 온보딩, QA, AI 기반 탐색, 데이터 무결성 관리 비용이 커질 가능성이 높다.

2. 현재 관찰된 구조

원본 후보 1
Pakuri/data/*.csv

원본 후보 2

몬스터 A~J 스킬 정보는 markdown 문서를 읽어 파싱한다.

에디터 메뉴로 자산을 생성하고 일부 적/보상 데이터를 코드에 직접 넣는다.
런타임 소비
GameDataCatalog
실제 전투/런 UI는 생성된 ScriptableObject만 읽는다.

3. 현재 구조에서 보이는 핵심 문제

  • 단일 진실원본 부재: CSV, markdown, 하드코딩, asset이 동시에 존재한다.
  • 유지보수 경로 불명확: 어떤 데이터는 어디서 수정해야 하는지 파일만 보고 즉시 알기 어렵다.
  • 검증 책임 불명확: import 단계인지 runtime 단계인지, 어떤 검증이 강제되는지 코드로 보장되지 않는다.
  • 확장 비용 증가: 현재 구조가 런타임 계약 중심에 이미 들어가 있어, 규모가 커질수록 분리 비용이 커진다.

4. 왜 문제라고 판단하는가

관찰 사실 실제 근거 운영 리스크
런타임은 이미 GameDataCatalog 중심으로 묶여 있다. RunFlowController.cs, DebugSceneController.cs, CombatRuntimeController.cs가 모두 GameDataCatalog를 직렬화 참조한다. 현재 구조는 임시 스크립트가 아니라 런타임 계약 중심이다. 이후 구조 변경 비용이 커진다.
PakuriGameDataSeeder.cs는 826줄이다. 파일 전체 line count 확인 결과 826줄. 도메인 추가 시 한 파일 집중이 심해지고, 탐색성과 리뷰 효율이 계속 낮아진다.
몬스터 스킬은 markdown 파싱에 의존한다. BuildMonsterActiveSkills, BuildMonsterPassives, GetSkillDocumentPaths, ParseActiveSkillDocument, ParsePassiveSkillDocument. 코드/문서 포맷 결합이 생기고, 포맷 흔들림이 곧 데이터 오류로 이어질 수 있다.
Stage 1 적 데이터는 seeder 내부 하드코딩 비중이 높다. CreateOrUpdateStageOneEnemies()에서 8개 적 정의를 직접 생성한다. CSV가 있어도 실제 수정 경로가 코드로 회귀한다.
CSV도 이미 상호 참조 불일치가 보인다. levelup_choices.csv와 skill_branches.csv는 SKILL_004 이상을 참조하지만, 현재 skills.csv는 SKILL_001~003만 존재한다. 원본 데이터 간 무결성 검사를 체계적으로 하지 않으면 QA에서 뒤늦게 발견된다.

5. 가장 큰 잘못된 원인

가장 큰 원인은 데이터 작성용 원본과 런타임용 자산 사이의 경계를 만들었지만, 그 사이를 연결하는 규칙과 검증을 강한 계약으로 만들지 못했다는 점이다.

  • 원본 후보가 여러 개다.
  • 변환 규칙이 한 곳에 길게 누적된다.
  • 검증 실패 시 강제 중단보다 경고 또는 기본값 대체로 흘러가는 코드가 있다.
  • 그 결과, 구조 의도는 분리되어 있으나 실제 운영은 추적성이 낮아진다.

6. 그렇게 생각한 이유

  • GetSkillDocumentPaths()는 문서가 없을 때 Debug.LogWarning만 남긴다.
  • ParseFirstFloat()는 숫자를 못 읽으면 0f를 반환한다.
  • ParseAttribute()는 매칭 실패 시 기본값으로 Physical을 반환한다.
  • 즉 현재 구현은 “검증기”보다 “변환기”에 가깝고, 실패를 차단하기보다 흘려보내는 방향이 더 강하다.
예시 문서 누락 -> 경고 로그 -> 계속 진행 숫자 파싱 실패 -> 0f 속성 파싱 실패 -> Physical 이 방식은 초기 개발에는 편할 수 있지만, 데이터 드리븐 운영 단계에서는 품질 추적을 어렵게 만든다.

7. 예상 반박과 재반박

예상 반박 재반박
반박 ScriptableObject는 Unity 런타임과 잘 맞고, 런타임은 최종 자산만 읽으면 되므로 안정적이다. 재반박 원리에는 동의할 수 있다. 문제는 현재 저장소가 “원본 데이터 하나 + 명확한 변환기”가 아니라 csv + markdown + 하드코딩 + asset 혼합 상태라는 점이다. 즉 SO 사용 자체보다 원본 관리 구조가 더 큰 문제다.
반박 단일 seeder는 초기 단계에서는 빠르다. 재반박 빠를 수는 있다. 다만 현재는 이미 RunFlowController, DebugSceneController, CombatRuntimeController가 GameDataCatalog 중심으로 연결되어 있다. 즉 구조적 영향 범위가 작지 않다. 826줄짜리 seeder를 중심으로 규모를 더 키우는 것은 미래 분리 비용을 낮추지 않는다.
반박 무결성 검사는 런타임이 아니라 import 단계에서 하면 된다. 재반박 이 방향은 합리적이다. 다만 현재 코드에는 강제 import validation이 충분히 보이지 않는다. 지금 구현은 검증 실패를 build blocker로 막기보다 warning 또는 기본값으로 계속 진행하는 쪽에 가깝다. 따라서 “에디터 검증으로 충분하다”는 말은 현재 상태 설명이 아니라 미래 목표에 가깝다.
반박 CSV를 게임 시작 시 모두 읽는 것은 비효율적일 수 있다. 재반박 성능 이슈는 설계 시 고려해야 한다. 다만 이 논점의 본질은 “런타임에 CSV를 직접 읽을지”보다 “원본 데이터와 검증 책임을 어디에 둘지”다. 시작 로딩 비용 최적화보다, 데이터 이원화와 추적성 저하로 생기는 QA 비용이 더 클 수 있다.

8. 제안 작업안

아래 방향은 “현재 구조를 전면 부정”하기보다, 데이터 원본을 하나로 고정하고 검증을 명시적 계약으로 끌어올리는 방향이다.

1. 원본 고정 CSV를 저작 원본으로 명확히 지정한다. 첫 컬럼은 기본 키 의미의 ID로 통일한다.
2. 타입 행 도입 2행을 타입 정의 행으로 사용한다. 기본 타입뿐 아니라 프로젝트용 custom enum도 허용한다.
3. 데이터 클래스 분리 예: waves_chapter1.csv에 대응되는 DataWavesChapter1.cs를 두고, partial 클래스로 데이터별 validator를 둔다.
4. 조회 계약 통일 DataManager.Instance.GetData<T>(id)를 기본 조회 계약으로 둔다. 필요 시 partial 확장으로 도메인별 custom query를 추가한다.

9. 세부 운영 방향

  • 수동 등록 선호 가능: 자동 스캔은 미완성 CSV까지 읽을 수 있으므로, 초기에는 DataManager에 명시 등록하는 방식이 더 안전할 수 있다.
  • 데이터셋 병합 허용: waves_chapter1.csv, waves_chapter2.csv, waves_chapter3.csv처럼 동일 스키마 파일은 내부 시트명 또는 동일 schema group 개념으로 묶어 다룰 수 있다.
  • SO 사용 범위 재정의: Unity 네이티브 참조가 필요한 sprite, prefab, icon, effect는 별도 자산 참조를 유지할 수 있다. 다만 관계형/밸런스 데이터의 진실원본은 하나로 두는 편이 안정적이다.

10. 기대 효과

  • 어떤 데이터를 어디서 수정해야 하는지 즉시 설명 가능해진다.
  • 검증 로직이 데이터셋별 partial validator에 모여, 데이터 오류의 원인 추적이 쉬워진다.
  • 신규 작업자와 AI 도구 모두 탐색 비용이 줄어든다.
  • CSV 원본과 런타임 사용 데이터 사이의 불일치 문제를 구조적으로 줄일 수 있다.
  • 장기적으로는 seeder 한 파일의 비대화를 막고, 도메인 단위로 데이터 책임을 나눌 수 있다.

11. 회의용 결론

현재 구조는 “작동 여부”만 보면 사용할 수 있다. 그러나 팀 운영 관점에서는 데이터 수정 경로가 분산되어 있고, 검증 계약이 약하며, 런타임 계약이 이미 그 구조에 깊게 결합되어 있다는 점이 더 큰 문제다.

따라서 이번 논의의 목적은 “SO를 쓸지 말지”가 아니라, 원본 데이터의 단일성, 검증의 강제성, 조회 계약의 일관성을 재정의하는 데 있어야 한다.
