이 문서는 2026-05-01-data-structure-review.html의 실제 지적사항과 그 이후 현재 저장소에 반영된 CSV 중심 리팩토링을 연결해 설명하는 구현 보고서다. 목적은 “무엇이 문제였고”, “무엇을 어떻게 고쳤고”, “무엇이 아직 남았는지”를 실제 코드와 실제 자산 경로 기준으로 한 번에 정리하는 것이다.

현재 데이터 로드와 SO 적용 원리

현재 구조는 기존 Assets/Data/GameData/*.asset를 CSV로 직접 덮어쓰는 방식이 아니다. 게임 시작 시 PakuriCsvRuntimeData가 PakuriCsvRuntimeSourceCatalog에서 source CSV TextAsset을 읽고, PakuriCsvRuntimeAssetCatalog에서 asset_path에 대응하는 Sprite/GameObject 참조를 읽는다.

그 다음 순서는 source 검증 → runtime asset binding 검증 → in-memory GameDataCatalog 생성 → MonsterDefinition/EnemyDefinition 생성 → PakuriDataManager 등록이다. 이때 생성되는 GameDataCatalog와 MonsterDefinition은 ScriptableObject.CreateInstance<...>로 메모리 안에서 새로 만들어진 runtime object다.

즉 현재 SO의 역할은 “CSV 원본을 Unity 런타임이 소비할 수 있는 형태로 담는 컨테이너”에 가깝고, 실제 진실원본은 Pakuri/Assets/CSVdata/source/*.csv다. 반대로 Assets/Data/GameData/GameDataCatalog.asset와 기존 몬스터/적 asset은 현재 기준으로 legacy bootstrap 또는 editor 복구 경로에 더 가깝다.

1. Executive Summary

기준 문서의 핵심 제안은 원본 데이터 단일화, 2행 타입 정의, 조회 계약 통일, 검증 강제였다.

현재 구현은 이 방향을 일부 실현했다. 구체적으로는 Pakuri/Assets/CSVdata/source의 typed CSV를 런타임 원본으로 삼고, 이를 PakuriCsvRuntimeSourceCatalog와 PakuriCsvRuntimeAssetCatalog를 통해 플레이어 런타임에서 읽도록 바꿨다. 또한 CSV 파싱 실패나 asset binding 실패가 나면 Application.Quit()로 중단하도록 강제했다.

이후 후속 작업으로 기존 PakuriCsvRuntimeData.cs monolith는 runtime entry, loader, validation, build, editor, types support partial 파일로 분리됐다. 즉 “CSV-first 런타임”뿐 아니라 “기능 축 기준 코드 분해”까지는 반영됐다. 다만 PakuriGameDataSeeder.cs는 여전히 Assets/Scripts/Data/Editor/Legacy 아래에 남아 있고, 조회 계약도 아직 프로젝트 전역으로 확장된 상태는 아니다.

3. 리팩토링 전 문제 구조

  • Pakuri/reference/Report/2026-05-01-data-structure-review.html는 원본이 csv + markdown + 하드코딩 + asset 혼합 상태라고 지적했다.
  • 현재 legacy seeder는 실제로 Assets/Scripts/Data/Editor/Legacy/PakuriGameDataSeeder.cs에 남아 있으며, 5 몬스터와 Stage 1 적을 코드에 직접 들고 있다.
  • 같은 파일은 Application.dataPath/../reference/2.Monster/{monster}/skill 아래 markdown를 다시 읽어 skill 데이터를 만든다.
  • 이 구조에서는 런타임 소비 모델과 authoring 입력 경로가 분리돼, 데이터 불일치 원인 추적이 어렵다.

4. 현재 리팩토링 후 구조

  • 사용자가 수정하는 source는 Pakuri/Assets/CSVdata/source/*.csv다.
  • 에디터는 이 CSV를 PakuriCsvRuntimeSourceCatalog.asset에 TextAsset 참조로 묶는다.
  • 동시에 CSV 안의 asset_path를 실제 Sprite/GameObject 참조로 바꿔 PakuriCsvRuntimeAssetCatalog.asset에 저장한다.
  • 게임 시작 시 [RuntimeInitializeOnLoadMethod]가 이 두 catalog를 읽고 source 검증, runtime binding 검증, in-memory GameDataCatalog 생성, PakuriDataManager 등록을 수행한다.
  • CSV source가 import되면 postprocessor가 runtime catalog sync를 자동 예약하므로, 일반적인 수치 수정은 source CSV 쪽을 바꾸는 것으로 닫힌다.

5. 실제 구현 과정

1. 기준 보고서 확인 2026-05-01-data-structure-review.html의 8번 제안 작업안에서 CSV 원본 고정, 타입 행, 데이터 클래스 분리, 조회 계약 통일을 기준 방향으로 삼았다.
2. 1차 CSV 마이그레이션 초기에는 Pakuri/data/source를 직접 읽는 PakuriCsvRuntimeData.cs를 만들고 startup validation + quit 경로를 추가했다.
3. Reviewer 지적 반영 Reviewer는 숨은 asset fallback, unified query 부재, non-Resources asset path 문제를 지적했다. 이후 사용자가 CSV를 Assets/CSVdata로 import했다.
4. 2차 구조 보강 source를 TextAsset 기반으로 바꾸고, PakuriCsvRuntimeSourceCatalog, PakuriCsvRuntimeAssetCatalog, PakuriDataManager, postprocessor를 추가했다.
5. 3차 코드 분해, 조회 계약 확장, 재검증 이후 PakuriCsvRuntimeData를 partial 파일들로 분해하고, PakuriDataManager에 collection/fallback query를 추가해 MainMenu, RunFlow, DebugScene, RunCombatUi, RunSceneBootstrap, CombatRuntimeEnemies의 direct catalog 접근을 줄였다. 그 뒤 full asset refresh와 Pakuri/Validate CSV Source Data를 다시 실행해 동일한 5 monsters / 8 stage-one enemies 로그를 재확인했다.

7. 남아 있는 구조 부채와 우선순위

이 섹션은 실제 후속 작업 후보만 남긴다. 의도적으로 하지 않은 항목, 예를 들어 scene controller singleton 확장은 부채 목록에서 제외했다.

  • 1순위: legacy seeder 정리: PakuriGameDataSeeder.cs는 여전히 5몬스터/8적 하드코딩과 markdown 파싱을 유지한다. 런타임 원본은 이미 CSV로 옮겨졌으므로, 다음 authoring 정리의 중심은 이 legacy 경로를 어떻게 폐기하거나 대체할지다.
  • 2순위: dataset 단위 세분화: monolith 분해는 끝났지만, row model과 parser support 타입은 아직 PakuriCsvRuntimeData.Types.cs 하나에 모여 있다.
  • 3순위: 조회 계약의 전면 확장: 현재 PakuriDataManager는 MainMenu/RunFlow/DebugScene/RunCombatUi/RunSceneBootstrap/CombatRuntimeEnemies까지 확장됐지만, 프로젝트 전체의 모든 data consumer가 stable-id 기반 query service로 통일된 상태는 아니다.
  • legacy CSV 보존: Pakuri/data/*.csv는 reference로 남아 있다.
  • Reviewer 재검증 미실행: Builder 수정 후 새로운 Code Reviewer pass는 아직 수행하지 않았다.

9. 실제 검증 근거

  • Unity 메뉴 Pakuri/Validate CSV Source Data를 다시 실행했고, 콘솔에 PakuriCsvRuntimeData loaded runtime catalog from resource source 'Pakuri/CSVRuntime/PakuriCsvRuntimeSourceCatalog' with 5 monsters and 8 stage-one enemies. 로그가 남았다.
  • Pakuri/Assets/Resources/Pakuri/CSVRuntime/PakuriCsvRuntimeSourceCatalog.asset YAML은 7개 CSV TextAsset GUID를 실제로 참조한다.
  • Pakuri/Assets/Resources/Pakuri/CSVRuntime/PakuriCsvRuntimeAssetCatalog.asset YAML은 11개 AssetPath: sprite entry를 실제로 가진다.
  • full Unity asset refresh 후 PakuriCsvRuntimeData.Build.cs, Editor.cs, Loader.cs, Types.cs, Validation.cs의 새 .meta가 생성됐고, 이후 콘솔 조회에서 프로젝트 C# compile error는 보이지 않았다.
  • Get-ChildItem ... | Select-String 'gameDataCatalog\.Monsters|gameDataCatalog\.StageOneEnemies|fallbackCatalog\.Monsters'를 다시 실행했을 때, 남은 direct 배열 접근은 PakuriDataManager.cs 내부 fallback 처리만 확인됐다.

11. 현 시점 결론

현재 리팩토링의 핵심 성과는 런타임 데이터 원본이 더 이상 markdown parser나 legacy SO 생성기에 매달리지 않게 만들었다는 점이다. 이제 게임 시작 시점의 실제 진실원본은 Assets/CSVdata/source에서 import된 typed CSV와, 그 CSV를 플레이어 런타임에서 안전하게 읽기 위한 PakuriCsvRuntimeSourceCatalog, PakuriCsvRuntimeAssetCatalog다.

반면 구조적으로 완전히 끝난 상태는 아니다. 다음 리팩토링 우선순위는 1) PakuriGameDataSeeder.cs의 legacy 정리, 2) row model / validator의 dataset 단위 세분화, 3) 남아 있는 data consumer의 조회 계약 추가 통일 순서가 가장 자연스럽다.

기준 문서의 8번 제안 작업안과 비교하면, - 원본 고정: 부분 달성 - 타입 행 도입: 달성 - 데이터 클래스 분리: 부분 달성 - 조회 계약 통일: 부분 달성 (gameplay entry/UI와 stage-one enemy pool까지 확대) 즉 현재 상태는 "설계 방향 전환, runtime source 고정, 1차 구조 분해, gameplay 진입부 조회 계약 통일까지는 끝났고, legacy authoring 경로 정리와 dataset 세분화가 남아 있는 2단계"로 보는 것이 가장 정확하다.
