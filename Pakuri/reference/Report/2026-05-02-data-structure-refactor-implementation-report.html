1. 현재 데이터 로드와 SO 적용 원리

현재 구조는 Assets/Data/GameData/*.asset를 수정해서 쓰는 방식이 아니다. 게임 시작 전에 PakuriCsvRuntimeData.InitializeBeforeSceneLoad()가 실행되고, PakuriCsvRuntimeSourceCatalog와 PakuriCsvRuntimeAssetCatalog를 Resources.Load(...)로 읽는다.

그 다음 LoadSourceModel(...)로 CSV row model을 만들고, ValidateSourceModelOrThrow(...)와 ValidateRuntimeCatalogOrThrow(...)를 통과하면 ScriptableObject.CreateInstance<GameDataCatalog>(), ScriptableObject.CreateInstance<MonsterDefinition>()로 메모리 안에 runtime SO container를 새로 만든다.

즉 현재 SO의 역할은 “원본”이 아니라 CSV 데이터를 Unity 런타임이 바로 소비할 수 있게 담는 container / adapter에 가깝다.

SO를 완전히 없애지 않은 이유도 여기에 있다. 현재 런타임 소비 타입은 여전히 GameDataCatalog, MonsterDefinition, EnemyDefinition, SkillDefinition, PassiveDefinition 중심이고, PakuriCsvRuntimeData.Build.cs는 CSV row model 값을 이 Unity 객체 그래프에 채운 뒤 PakuriDataManager.Instance.RegisterCatalog(catalog)로 등록한다. 즉 CSV를 각 consumer가 직접 파싱하게 만드는 대신, Unity 런타임이 바로 쓰는 공통 형태로 한 번 변환해 넘기는 구조다.

이 방식이 해결한 기존 문제는 명확하다. runtime 원본은 이제 Assets/CSVdata/source와 Resources catalog로 고정됐고, ResolveCatalogOrFallback(...)는 CSV 초기화 실패 시 null을 반환하므로 scene에 직렬화된 catalog가 숨은 runtime source로 되살아나지 않는다. 또한 CSV 무결성과 runtime asset binding을 먼저 검증한 뒤에만 runtime SO를 만들기 때문에, 예전 warning / fallback 중심 구조가 startup fatal validation 중심 구조로 바뀌었다.

4. 실제 구현 순서

1차 개선: 초기 CSV Runtime Migration Pakuri/data/source를 읽는 최초 CSV runtime loader와 startup validation / quit 경로를 넣었다.
Reviewer Gate asset path의 player-runtime 안전성, 숨은 asset fallback, unified query 부재, monolith 구조 문제가 확인됐다.
2차 개선: Resources-backed 재구성 source를 Assets/CSVdata/source import 자산으로 바꾸고, PakuriCsvRuntimeSourceCatalog.asset, PakuriCsvRuntimeAssetCatalog.asset, PakuriDataManager를 추가했다.
3차 개선: PakuriCsvRuntimeData partial 분리 runtime entry / loader / validation / build / editor / types로 역할을 나눴다.
4차 개선: roster query contract 통일 MainMenu / RunFlow / DebugScene / RunCombatUi / RunSceneBootstrap / CombatRuntimeEnemies의 monster/enemy roster lookup을 PakuriDataManager로 통일했다.
5차 개선: legacy 제거 + dataset 파일 세분화 + collection query 확장 PakuriGameDataSeeder.cs와 bootstrap 메뉴를 제거하고, row model / parser support를 dataset 파일로 분리했으며, GetActiveSkills(...), GetPassiveSkills(...), GetRewardChoices(...), ResolveActiveSkill(...), ResolvePassiveSkill(...)를 추가해 RunCombatUi / DebugScene / CombatRuntimeEveSkills가 monster 하위 배열 직접 접근 대신 manager query를 쓰도록 바꿨다.

6. 현재 남아 있는 구조 부채와 SO 단점

  • SO 계층 자체는 아직 Unity 결합을 남긴다. MonsterDefinition.cs는 Sprite, Color, 보상 배열, A-J active/passive 배열 같은 Unity 런타임 필드를 직접 들고 있고, GameDataCatalog.cs도 여전히 Monsters와 StageOneEnemies 배열을 중심으로 잡혀 있다.
  • CSV schema와 runtime SO 필드를 같이 유지해야 한다. PakuriCsvRuntimeData.SourceModel.cs는 dataset row model 사전을 따로 들고 있고, PakuriCsvRuntimeData.Build.cs는 그 값을 다시 MonsterDefinition / EnemyDefinition / GameDataCatalog로 복사한다. 그래서 데이터 필드가 늘어나면 CSV row와 SO 양쪽을 함께 수정해야 한다.
  • runtime-safe asset binding을 얻는 대신 SO 기반 중간 계층이 남아 있다. PakuriCsvRuntimeSourceCatalog.cs와 PakuriCsvRuntimeAssetCatalog.cs는 imported CSV TextAsset과 sprite/prefab 참조를 ScriptableObject로 유지한다. 이 계층은 player-runtime 안전성을 주지만, CSV → catalog asset → in-memory runtime SO라는 변환 단계를 계속 관리해야 한다.
  • Run state가 아직 DisplayName 기반이다. RunSession.cs와 일부 run/combat 로직은 여전히 학습 상태와 보상 선택을 display name 문자열에 묶고 있다. 이는 stable-id migration 과제다.
  • 적 데이터 스키마가 여전히 Stage 1 중심이다. GameDataCatalog.cs, EnemyDefinition.cs, CombatRuntimeEnemies.cs는 아직 stage-one enemy와 fallback enemy 생성 규칙을 전제로 한다.
  • dormant legacy asset은 남아 있다. Assets/Data/GameData/*.asset와 Pakuri/data/*.csv는 더 이상 runtime 원본은 아니지만 저장소에는 reference/legacy 자산으로 남아 있다.

7. 실제 검증 근거

  • refresh_unity 이후 Unity 콘솔에서 이번 변경으로 생긴 C# compile error가 남지 않았다.
  • Unity 메뉴 Pakuri/Validate CSV Source Data 실행 후 콘솔에 PakuriCsvRuntimeData loaded runtime catalog from resource source 'Pakuri/CSVRuntime/PakuriCsvRuntimeSourceCatalog' with 5 monsters and 8 stage-one enemies. 로그가 다시 찍혔다.
  • Assets/Scripts 범위 Select-String에서 PakuriGameDataSeeder, Seed Default Game Data, Bootstrap CSV Source Data From Current Catalog, LegacyCatalogAssetPath hit가 나오지 않았다.
  • Get-ChildItem Assets/Scripts/Data -Filter 'PakuriCsvRuntimeData*.cs' 결과로 runtime data 분리 파일 11개를 확인했다.
  • git status --short 기준으로 PakuriGameDataSeeder.cs 삭제와 dataset 파일 추가, query-contract consumer 수정이 실제 작업트리에 반영됐다.

8. 결론

현재 구조는 더 이상 PakuriGameDataSeeder나 markdown parser에 매달려 runtime 데이터를 만들지 않는다. 실질 원본은 Assets/CSVdata/source의 typed CSV이고, 그 CSV를 startup 시 검증한 뒤 runtime SO container로 변환해 쓴다.

이번 5차 개선으로 기준 문서가 “다음 우선순위”로 남겨 두었던 legacy seeder 정리, dataset 단위 파일 세분화, collection query 계약 확장은 실제 코드 기준으로 반영됐다. 대신 다음 구조 부채는 이제 다른 층위로 이동했다.

현재 완료된 축 - CSV source-of-truth 고정 - startup fatal validation - runtime-safe asset binding catalog - legacy seeder 제거 - dataset row/parser 파일 분리 - roster + collection query contract 확장 현재 남은 축 - DisplayName 기반 run state를 stable-id로 전환 - Stage 1 전용 enemy schema 일반화 - dormant legacy asset의 archive / 보존 전략 정리
