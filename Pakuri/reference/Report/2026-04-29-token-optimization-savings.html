결론: 50개 스킬 문서를 모델이 전부 읽는 방식 대신, 문서는 에디터 시더가 파싱하고 모델은 규칙/샘플/검증 요약만 읽는 방식으로 바꾸면 문서 입력 기준 약 90% 전후, 전체 구현 턴 기준으로는 약 35~45% 전후의 컨텍스트 절감이 가능하다.

1. 산정 기준

이 문서는 실제 API billing token 로그가 아니라 저장소 파일 크기와 이번 작업에서 필요한 읽기 범위를 기준으로 한 추정이다. 토큰 환산은 한글/영문/기호가 섞인 프로젝트 문서 특성을 단순화해 대략 4 chars = 1 token으로 계산했다.

외부 Code Reviewer 출력에는 tokens used 123,936이 포함되어 있었지만, 그 값은 Reviewer 프로세스의 내부 검토/출력까지 합친 별도 실행값이다. 아래 절감률 계산에는 직접 사용하지 않았다.

2. 비교 모델

방식 작업 방식 모델 컨텍스트에 들어가는 주요 입력 추정 입력량 추정 토큰
최적화 이전 모델이 A~J 50개 스킬 문서를 전부 읽고, 각 문서 내용을 바탕으로 SO 구조와 시더를 직접 작성한다. 로드맵 23,903 + 2.Monster 전체 103,836 + 핵심 코드 84,369 + 몬스터 SO 확인 일부 약 212,108 chars 이상 약 53,000 tokens 이상
최적화 이후 모델은 규칙 문서와 대표 샘플만 읽고, 50개 스킬 문서는 PakuriGameDataSeeder가 Unity Editor에서 직접 파싱한다. 모델은 결과 count와 일부 asset 검증만 확인한다. 로드맵 핵심 발췌 + 규칙/샘플 10,756 + 핵심 코드 84,369 + asset count 검증 출력 약 115,000~135,000 chars 약 29,000~34,000 tokens
약 90% 문서 입력만 볼 때 절감률. 전체 2.Monster 문서 103,836 chars 대신 규칙/샘플 10,756 chars만 모델이 직접 읽는 기준.
약 95% 스킬 문서 50개만 볼 때 절감률. 64,150 chars 대신 대표 액티브/패시브 샘플 3,125 chars만 읽는 기준.
약 35~45% 코드/로드맵/검증 출력까지 포함한 전체 구현 턴 기준 절감 추정.

3. 이번 작업에 적용된 최적화

최적화 적용 방식 효과
문서 전체 복사 방지 50개 스킬 문서를 모델이 전부 해석하지 않고, 시더가 파일을 직접 읽어 표를 파싱하도록 구현했다. 스킬 문서 내용 대부분이 모델 컨텍스트로 들어가지 않는다.
대표 샘플만 읽기 a-arc-bolt.md, g-weakness-analysis.md 같은 대표 액티브/패시브 구조만 읽어 파서 요구사항을 정했다. 문서 형식 이해에는 충분하면서 전체 50개 문서 입력을 피한다.
검증은 count 중심 생성 후 각 몬스터 asset에서 SkillId, PassiveId, EnhancementChoices, MasterSkillChoices 개수를 검사했다. 119,073 chars 규모의 몬스터 SO 전체를 읽지 않고도 구조 반영 여부를 확인할 수 있다.
빌드/콘솔은 결과 중심 빌드 전체 로그는 오류/경고 요약 중심으로 보고, 반복되는 Unity/MCPForUnity 경고는 기존 경고로 분류했다. 검증 근거는 유지하면서 대량 로그 재소비를 줄인다.

4. 한계와 주의점

항목 주의점
정확한 billing token 아님 저장소에 실제 API billing token 로그가 없다. 따라서 이 문서는 파일 문자 수 기반 추정이며, 모델/토크나이저/출력 길이에 따라 실제 값은 달라진다.
BLACKBOARD.md 시작 규칙 AGENTS.md 규칙상 작업 시작 때 BLACKBOARD.md를 확인해야 하므로, 완전한 절감에는 BLACKBOARD를 task block 단위로 빠르게 찾는 운용이 필요하다. 현재 파일은 130,284 chars로 커졌다.
시더 파서 정확도 문서 파싱을 코드로 넘기면 토큰은 줄지만, 문서 표 형식이 바뀔 경우 시더 파서를 함께 수정해야 한다.
Reviewer 실행 외부 Code Reviewer는 자체적으로 파일을 다시 읽고 긴 출력을 낼 수 있다. 이번 Reviewer 출력에는 tokens used 123,936이 보였으며, 이는 구현 턴 최적화와 별개로 관리해야 할 비용이다.
