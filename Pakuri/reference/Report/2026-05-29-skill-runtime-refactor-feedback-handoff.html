코드 근거

관찰 근거 판단
스킬 실행은 중앙 tick 구조다. InGameCombatManager.cs:93가 SkillExecutionSystem.Tick(...)을 호출하고, SkillExecutionSystem.cs:35와 :120이 roster와 active skill을 순회한다. 캐릭터가 스킬 상태를 갖고 있어도, 캐릭터 단위 실행 주체는 아직 분리되어 있지 않다.
스킬 상태 자체는 유닛 소유다. BaseUnitRuntimeModel.cs:68이 SkillRuntime을 저장하고, SkillRuntimeFactory.cs:67이 new SkillRuntimeInstance(owner, skillData)를 만든다. 현재 구조를 버릴 필요는 없고, 이 상태 저장 위에 unit-scoped controller를 얹는 것이 자연스럽다.
MonsterUnitActor는 gameplay owner가 아니다. MonsterUnitActor.cs:19는 model 참조를 갖지만, :36, :44, :52, :60은 애니메이션과 표시 갱신 중심이다. 정확한 표현은 "model 참조를 가진 presentation actor"다.
execute, boss, kill 규칙은 executor 내부에 직접 들어가 있다. SingleAttackData.cs:17~:21, SingleAttackSkillExecutor.cs:123, :1314~:1328, :1356~:1382 이 필드들은 조건, 피해 보정, 킬 후 액션 handler로 분리해야 한다.

문제가 되는 현재 필드 패턴

monster_skills.csv에는 다음 필드가 실제로 존재한다.

  • execute_health_ratio_threshold
  • require_execute_threshold_to_cast
  • execute_damage_multiplier
  • kill_cooldown_refund_ratio
  • boss_damage_multiplier

monster_skill_choices.csv에도 execute_health_ratio_bonus, execute_crit_chance_bonus, boss_damage_multiplier, kill_cooldown_refund_ratio_bonus, kill_resets_cooldown 같은 대응 필드가 있다.

이 방향을 계속 유지하면 새 스킬 행동마다 CSV 컬럼, definition 필드, mapper, snapshot property, executor 조건문이 같이 늘어난다.

권장 표현

현재 표현 권장 runtime 개념
require_execute_threshold_to_cast CastCondition: target health ratio <= threshold
execute_health_ratio_threshold TargetHealthRatioCondition
execute_damage_multiplier ConditionalDamageModifier
boss_damage_multiplier TargetPredicateDamageModifier with target.IsBoss
kill_cooldown_refund_ratio OnKillAction: ReduceCooldown
kill_resets_cooldown OnKillAction: ResetCooldown

버프와 투사체의 경계

지속적으로 유닛 상태를 바꾸는 것은 buff/status handler가 맡는 것이 맞다. 예시는 행동속도, 공격력, 주문력, 보호막 수치, 받는 피해, 저항, 이동속도, 치명 보정이다.

반대로 보스 추가 피해, 처형 배율, 처형 조건 cast reject, 킬 쿨타임 환급은 지속 버프가 아니라 히트 계산 또는 이벤트 반응이다. 이들은 damage modifier나 post-kill action으로 분리하는 편이 맞다.

투사체 상속이나 특수 projectile behavior는 이동, 충돌, 수명, 분기, delayed impact처럼 투사체 자체가 다르게 행동할 때만 사용해야 한다. 일반 피해 규칙을 projectile subclass에 넣으면 projectile이 전투 규칙을 너무 많이 알게 된다.

목표 구조

구성 책임
MonsterUnitActor 표시, 애니메이션, 데미지 팝업, debug label
MonsterUnitRuntimeModel identity, stats, resources, statuses, skill runtime state
UnitSkillController 해당 캐릭터의 skill tick, cast decision, manual/auto routing, execution request 생성
SkillExecutionPlan CSV에서 컴파일된 condition/action/modifier node 목록
Action and modifier handlers damage, status, projectile spawn, zone spawn, cooldown/reload change, visual spawn
InGameCombatManager and services scene roster, damage/status application, shared combat service coordination

현실적인 구현 순서

  1. 현재 CSV와 동작을 유지한다.
  2. SingleAttackSkillExecutor의 execute, boss, kill recovery 로직을 cast condition, damage modifier, post-hit/post-kill action handler로 추출한다.
  3. UnitSkillController를 추가해 캐릭터 단위 스킬 판단 주체를 만든다.
  4. SkillExecutionSnapshot의 flat property를 grouped modifier op로 줄인다.
  5. 기존 CSV를 SkillExecutionPlan으로 컴파일하는 계층을 추가한다.
  6. runtime plan이 안정된 뒤에만 CSV 물리 분리나 row set 정규화를 검토한다.

원 작업자에게 줄 결론

  1. 두 보고서의 "중앙 인터프리터 비대화" 지적은 현재 코드와 맞다.
  2. 문제는 CSV 자체가 아니라, 새 행동이 wide CSV field와 flat snapshot property로 계속 들어가는 방식이다.
  3. 캐릭터별 스킬 상태는 이미 있으므로, 다음 개선은 unit-scoped skill owner를 추가하는 쪽이 좋다.
  4. execute, boss, kill cooldown 예시는 각각 cast condition, damage modifier, on-kill action으로 분리해야 한다.
  5. buff/status는 지속 상태 변화에 쓰고, projectile subclass는 투사체 행동 변화에만 쓰는 것이 좋다.
  6. 첫 구현은 반드시 behavior-preserving이어야 하며 현재 CSV 호환을 깨면 안 된다.
