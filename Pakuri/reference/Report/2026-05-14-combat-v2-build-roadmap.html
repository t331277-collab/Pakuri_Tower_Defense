InGame Roadmap

InGame 구현 순서 로드맵

이 문서는 현재 작성된 Assets/Scripts2/InGame 스크립트와 기존 SkillDefinition, MonsterDefinition, RunSceneBootstrap 구조를 기준으로 다음 작업 순서를 고정한다. 결론은 전체 스킬 데이터 50개를 먼저 채우는 방식이 아니라, 샘플 Blueprint 데이터로 연결을 검증한 뒤 골격을 안정화하고 전체 데이터를 확장하는 순서다.

1. 현재 근거

영역 확인된 파일 판단 근거
InGame 껍데기 Pakuri/Assets/Scripts2/InGame/Core/InGameCombatManager.cs InGameCombatManager는 현재 빈 MonoBehaviour다. 아직 전투 시작, 스폰, 업데이트 루프가 없다.
유닛 모델 Pakuri/Assets/Scripts2/InGame/Units/BaseUnitRuntimeModel.cs, MonsterUnitRuntimeModel.cs, EnemyUnitRuntimeModel.cs BaseUnitRuntimeModel은 유닛 공통 identity/stat/defense/resource/auto flag만 가진다. 몬스터 learned state는 MonsterUnitRuntimeModel, 적 분류 정보는 EnemyUnitRuntimeModel에 둔다.
Blueprint 스킬 데이터 Pakuri/Assets/Scripts2/InGame/Skills/Data/SkillData.cs, SkillBlueprintSpecs.cs 스킬 ID, 캐릭터, 슬롯, 타이밍, 타겟팅, 선택지, 타입별 스펙을 담는 데이터 구조가 있다. 실행기는 없다.
기존 스킬 데이터 Pakuri/Assets/Scripts/Data/Definition/SkillDefinition.cs 기존 구조는 SkillId, RuntimeKind, 피해량, 쿨다운, 탄창, 상태이상 ID, 선택지 배열을 이미 가진다.
기존 몬스터 데이터 Pakuri/Assets/Scripts/Data/Definition/MonsterDefinition.cs 몬스터는 현재 ActiveSkills, PassiveSkills로 기존 SkillDefinition 계열을 참조한다.
기존 Run 진입 Pakuri/Assets/Scripts/Run/Flow/RunSceneBootstrap.cs 현재 RunScene은 CombatRuntimeController.BeginConfiguredDay(monster, session, fallbackCatalog)로 기존 전투에 진입한다.
핵심 판단: 테스트에는 데이터가 필요하지만, 전체 데이터를 먼저 채우면 연결 방식이 바뀔 때 수정 비용이 커진다. 따라서 Phase1-C에서 샘플 Blueprint 데이터 1~2개만 만들고, 참조 경로와 런타임 골격을 검증한 뒤 전체 데이터를 확장한다.
CSV/Data 로드 결정: InGame 전용 CSV 로더를 새로 만들지 않는다. 현재 PakuriCsvRuntimeData가 CSV를 읽어 GameDataCatalog, MonsterDefinition, SkillDefinition으로 구성하고, PakuriDataManager가 ID/슬롯 조회를 제공한다. Phase1-C는 이 기존 흐름을 원천으로 삼고, InGame에는 기존 SkillDefinition을 새 SkillData 계열로 해석하는 얇은 매퍼 또는 브리지만 둔다.
2026-05-14 CSVData 전환 반영: Pakuri/reference/Report/2026-05-14-csvdata-transition-roadmap.html의 새 원본 전환 계획은 이 InGame 로드맵을 대체하지 않고 중간에 끼워 넣는다. 현재 확인된 상태에서 Pakuri/Assets/CSVData/EnemyStat.csv, MonsterStat.csv, SkillData.csv는 존재하지만 모두 0 byte이고, Assets/Scripts2/InGame은 아직 PakuriCsvRuntimeData, PakuriDataManager, MonsterDefinition, EnemyDefinition, SkillDefinition을 참조한다. 따라서 다음 구현은 Phase2-B 프리팹 바인딩을 깊게 진행하기 전에 CSVData 스키마와 최소 샘플 행을 먼저 고정해야 한다.
Prefab 작성 결정: Code Builder는 유닛/적/스킬 프리팹을 코드로 직접 생성하지 않는다. 사용자가 Unity Editor에서 Pakuri/Assets/Prefab/Monster, Pakuri/Assets/Prefab/Enemy, Pakuri/Assets/Prefab/Skill 아래에 프리팹을 만들고, Code Builder는 해당 프리팹에 붙일 MonsterUnitActor, EnemyUnitActor 및 이후 필요한 바인딩 컴포넌트/API만 제공한다.
2026-05-14 MonsterHpBar Scale 결정: Ariel_Unit.prefab, Eve_Unit.prefab, Sein_Unit.prefab, Vega_Unit.prefab, Rin_Unit.prefab의 MonsterHpBar 시각 크기는 사용자가 Unity Editor에서 직접 조정한 프리팹 Transform 값을 기준으로 한다. 현재 확인된 YAML 기준으로 MonsterHpBar 루트는 대략 {x: 3.3, y: 1.7, z: 1.35}, Background와 Fill은 {x: 20, y: 2.5, z: 1} 스케일을 가진다. Code Builder는 이후 Actor/Model 바인딩이나 HP 갱신 로직을 수정하더라도 이 표시용 Scale을 코드에서 재설정하거나 덮어쓰지 않는다.

2. 전체 순서

Phase1 데이터 그릇과 샘플 데이터 연결 검증
Phase2 유닛 생성, 액터 바인딩, 테스트 씬 진입
Phase3 타겟, 피해, 상태, 보호막 공통 서비스
Phase4 스킬 런타임, 실행기, 최소 스킬 동작
Phase5 학습 선택지, 자동 공격/자동 스킬, 몬스터별 확장
Phase6 기존 Run/Data 흐름과 호환 브리지
Phase7 전체 스킬 데이터 확장과 예외 스킬 처리
Phase8 UI/씬 통합, 회귀 검증, 기존 전투 대체 판단

2-1. CSVData 파이프라인 삽입 타이밍

InGame 타이밍 먼저 또는 병행할 CSVData 작업 이유 / 완료 기준
Phase2-B 시작 전 CSVData Phase0~2: Legacy 격리 기준, MonsterStat.csv / EnemyStat.csv / SkillData.csv 컬럼 확정, Eve + stage1-swordsman + 샘플 스킬 1~2개 입력 프리팹 Actor가 어떤 ID와 필드를 바인딩할지 먼저 고정한다. 이 단계는 런타임 전환이 아니라 데이터 계약 고정이다.
Phase2-B~Phase2-C 직전 또는 병행 CSVData Phase3~4: 새 InGame CSV loader / row model / catalog 구현, UnitFactory의 새 CSV 기반 유닛 모델 생성 경로 추가 테스트 씬에서 프리팹을 붙인 뒤 다시 데이터 원천을 바꾸는 일을 피한다. 완료 기준은 MonsterDefinition, EnemyDefinition, PakuriDataManager 없이 샘플 유닛 모델을 만들 수 있는 것이다.
Phase4-A~Phase4-C 이전 CSVData Phase5: SkillData.csv를 ProjectileSkillData, ZoneSkillData, BuffSkillData, ShieldSkillData, PassiveSkillData로 매핑 스킬 실행기를 만들기 전에 스킬 수치의 최종 원천을 새 CSVData로 돌린다. 최소 실행 샘플인 eve-a, ariel-b가 새 CSVData 기반 SkillData로 조회되어야 한다.
Phase4-C 최소 실행 검증 후 전체 스킬/몬스터/적 데이터 확장 실행기와 검증 규칙이 확정된 뒤 5명 x 10개 스킬로 확장한다. 먼저 전체 50개를 입력하면 구조 변경 때 데이터 수정 비용이 커진다.
Phase8-A Run 통합 직전 CSVData Phase8: Legacy 비활성화 검증 Scripts2/InGame에서 Pakuri.Data 참조 제거, Assembly-CSharp.csproj의 Legacy compile 항목 제거 또는 격리, 씬/Resources/초기화 참조 확인을 끝내야 CSVData를 실제 원본이라고 말할 수 있다.

3. Phase별 작업

Phase 상태 작업 완료 기준
Phase1-A 완료 Assets/Scripts2/InGame 하위 최소 컴파일 가능 스크립트 껍데기 생성 Core, Units, Skills/Data 파일이 존재하고 런타임 어셈블리 빌드가 통과한다.
Phase1-B 완료 Blueprint 스킬 데이터 구조 작성 SkillBlueprintSpecs.cs와 타입별 SkillData 하위 클래스가 컴파일된다.
Phase1-C 완료 기존 CSV/Data 흐름을 참조하는 InGameSkillCatalog와 InGameSkillDefinitionMapper 추가 기존 SkillDefinition의 ariel-a, ariel-b를 각각 ProjectileSkillData, ShieldSkillData로 조회 확인했다.
Phase1-D 완료 Blueprint 데이터 검증 규칙 작성 InGameSkillDataValidator와 에디터 메뉴가 중복 SkillId, 빈 ID, 캐릭터/슬롯 불일치, 필수 타이밍 값 누락을 감지한다.
Phase2-A 완료 기존 Definition에서 유닛 공통 스탯만 추출해 BaseUnitRuntimeModel 계열 생성 UnitFactory가 Eve 선택 몬스터를 MonsterUnitRuntimeModel, stage1-swordsman 테스트 적을 EnemyUnitRuntimeModel로 생성한다. 스킬/투사체 튜닝은 이후 스킬 구현 단계의 SkillData 매퍼로 분리한다.
Phase2-B 부분 완료 사용자 작성 프리팹에 MonsterUnitActor, EnemyUnitActor 모델 바인딩 최소 구현 몬스터 5종은 사용자가 만든 프리팹과 직접 조정한 MonsterHpBar Scale을 기준으로 Actor/Model 바인딩을 진행한다. 프리팹은 코드로 생성하지 않고, HP 바 크기는 프리팹 Transform 소유로 둔다. 남은 범위는 Enemy 프리팹/Actor 바인딩과 이후 실제 전투 HP 갱신 연결이다.
Phase2-C 대기 InGame 테스트 씬 또는 테스트 부트스트랩 작성 기존 RunSceneBootstrap과 분리된 경로에서 선택 몬스터와 적을 스폰할 수 있다.
Phase3-A 대기 타겟 레지스트리와 전투 대상 모델 작성 스킬 실행기가 유닛/적을 직접 찾지 않고 레지스트리에서 타겟 후보를 받는다.
Phase3-B 대기 피해, 상태이상, 보호막 서비스 분리 피해 계산과 상태 적용이 액터/스킬 개별 클래스에 흩어지지 않는다.
Phase4-A 대기 SkillRuntimeInstance 작성 쿨다운, 탄창, 재장전, 지속시간 상태가 SkillData와 분리되어 런타임에 유지된다.
Phase4-B 대기 스킬 실행기 인터페이스와 레지스트리 작성 Projectile, Beam, Zone, Buff, Shield, Passive 실행기가 같은 호출 계약을 가진다.
Phase4-C 대기 최소 실행 스킬 2종 구현 eve-a 투사체와 ariel-b 보호막이 샘플 Blueprint 데이터로 동작한다.
Phase5-A 대기 유닛 상태의 learned choices 조회 연결 1P와 현현 유닛이 같은 MonsterUnitActor 경로에서 같은 선택지 조회 규칙을 쓴다.
Phase5-B 대기 자동 공격/자동 스킬 토글 연결 UnitRuntimeModel.AutoAttackEnabled, AutoSkillEnabled가 실제 실행 조건에 반영된다.
Phase6-A 보류 기존 SkillDefinition 호환 브리지 작성 기존 데이터로도 InGame 테스트가 가능하고, 새 Blueprint 데이터와 충돌하지 않는다.
Phase7-A 보류 전체 스킬 데이터 확장 5명 x 10개 스킬을 샘플 검증된 규칙으로 확장한다. Rin-D, Vega-E 같은 예외는 별도 Custom executor로 분리한다.
Phase8-A 보류 Run UI Flow 통합과 기존 전투 대체 판단 새 전투가 독립 테스트에서 안정화된 뒤 기존 RunSceneBootstrap 진입 경로와 연결한다.

4. 다음 Code Builder 작업 추천

1순위: CSVData Phase0~2

Phase2-B 프리팹 Actor 바인딩 전에 Assets/CSVData의 세 CSV 헤더와 최소 샘플 행을 확정한다. 현재 세 CSV 파일은 존재하지만 0 byte이므로, 먼저 ID와 컬럼 계약을 고정해야 한다.

2순위: Phase2-B 잔여

사용자 작성 몬스터 프리팹의 Scale과 HP 바 자식 구조는 프리팹 소유로 유지한다. Code Builder는 MonsterUnitActor의 모델 ID/HP 표시 갱신과 이후 EnemyUnitActor 바인딩을 ID 기반으로만 연결하고, 사용자가 조정한 MonsterHpBar Transform을 코드에서 초기화하지 않는다.

3순위: CSVData Phase3~4

새 InGame CSV loader와 row model을 만들고, UnitFactory가 새 CSV catalog로 샘플 유닛 모델을 만들 수 있게 한다. 이 경로가 통과해야 이후 테스트 씬과 스킬 실행이 새 데이터 원천을 기준으로 움직인다.

Phase4 이전 필수: CSVData Phase5

SkillData.csv에서 SkillData 하위 클래스를 직접 만들 수 있게 한 뒤 스킬 실행기로 들어간다. 전체 50개 스킬 입력은 Phase4-C 최소 실행 스킬 검증 뒤로 계속 보류한다.

5. 데이터 연결 원칙

  • Phase1-C, Phase1-D, Phase2-A는 기존 CSV/Data 브리지로 완료된 연결 검증이다. 이후 작업은 2026-05-14-csvdata-transition-roadmap.html의 CSVData 전환 단계를 InGame Phase 사이에 삽입한다.
  • Phase2-B 전에 새 Assets/CSVData CSV 헤더와 최소 샘플 행을 확정한다. 현재 세 CSV 파일은 0 byte이므로 런타임 로더보다 데이터 계약 확정이 먼저다.
  • Phase2-B~Phase2-C 직전 또는 병행으로 새 InGame CSV loader/catalog를 만들고, Phase4-A~4-C 이전에는 SkillData.csv 기반 SkillData 매핑을 완료한다.
  • 전체 스킬 데이터는 Phase4-C의 최소 실행 스킬 검증 이후 확장한다.
  • 기존 SkillDefinition은 버리지 않고 Phase6-A에서 호환 브리지 대상으로 둔다.
  • SkillEffectPrefab과 ProjectilePrefab은 프레젠테이션/시각 자료로만 사용하고, 스킬 판정 로직을 프리팹에 숨기지 않는다.
  • Code Builder는 프리팹을 자동 생성하지 않는다. 사용자가 Unity Editor에서 프리팹을 만든 뒤, Code Builder가 제공한 Actor/바인딩 컴포넌트를 붙이는 흐름을 기본 계약으로 둔다.
  • MonsterHpBar의 위치, Scale, 표시 크기, 자식 SpriteRenderer 배치는 사용자 프리팹 작성 영역이다. 런타임 코드는 HP 비율과 텍스트 갱신만 담당하고, 사용자가 조정한 Scale 값을 덮어쓰지 않는다.
  • 선택지 효과는 유닛 상태의 learned choices를 실행 시점에 조회한다. 데이터 에셋이 런타임 선택 상태를 직접 보유하지 않는다.
