InGame Roadmap

InGame 구현 순서 로드맵

이 문서는 2026-05-16 기준 현재 구현된 Assets/Scripts2/InGame, Assets/CSVdata, Assets/CSVData, 그리고 NewRunScene.unity 상태를 반영해 기존 Combat V2 로드맵을 갱신한다. 결론은 최소 InGame 전투 루프, 샘플 스킬 실행, Stage 1 CSV 기반 진행, Reward UI / Manifest 흐름까지 구현됐고, 남은 큰 축은 전체 스킬/상태효과 확장, CSVData 원천 완전 전환, 기존 RunScene 대체 판단이다.

4. 적 스폰 / 적 관리 책임 이관 방향

현재 구현 기준: NewRunStageManager는 이미 StageDay.csv와 StageEncounter.csv를 읽고, SelectBossRows()로 보스 row를 고른 뒤 SpawnEncounterRows(...)에서 NewRunSceneEntryManager.SpawnEnemyById(...)를 호출한다. 또한 WaitForEnemyClear()에서 InGameCombatManager.ActiveEnemyCount를 보고 reward 전환 시점을 결정한다.
책임 현재 위치 로드맵 방향
전투 구성 선택 NewRunStageManager 유지. Stage/Day/Encounter CSV와 보스 선정은 StageManager 책임으로 둔다.
적 스폰 스케줄 NewRunStageManager.SpawnEncounterRows(...)가 NewRunSceneEntryManager.SpawnEnemyById(...)를 호출 StageManager 책임으로 유지하고 강화한다. 이후 wave, reinforcements, elite option, event combat도 StageManager 또는 Stage 하위 enemy lifecycle service로 확장한다.
적 등록 / 활성 수 조회 InGameCombatManager.RegisterEnemy(...), ActiveEnemyCount, 내부 UnitRosterService 단기적으로는 CombatManager API를 사용한다. 중장기적으로 StageManager가 적 lifecycle owner가 되고, CombatManager는 combat query / mutation API 또는 readonly roster facade만 제공하는 방향으로 좁힌다.
적 사망 / 제거 InGameCombatManager.RemoveUnitIfDead(...)가 roster unregister와 Actor destroy를 처리 사망 판정은 resource mutation 결과를 유지하되, encounter 진행/보상 후보/clear 집계는 StageManager가 받는 이벤트나 명시적 callback으로 이관한다.
적 행동 tick InGameCombatManager.Update()가 EnemyCombatSimulationSystem.Tick(...) 호출 StageManager가 적 wave/lifecycle을 소유하게 되면 enemy simulation tick의 호출 위치도 StageManager 하위 전투 단계 또는 별도 EnemyRuntimeSystem으로 분리한다. CombatManager가 모든 전투 세부 루프를 직접 호출하는 구조는 더 줄인다.

이 방향은 InGameCombatManager를 "전투의 모든 것을 아는 관리자"로 키우지 않기 위한 구조 조정이다. InGameCombatManager는 피해/보호막/회복, 스킬 실행, 충돌 대상 조회처럼 전투 규칙 API를 제공하고, StageManager는 어떤 적을 언제 만들고 언제 전투가 끝났는지 판단하는 Stage 진행 책임을 가진다.

5. 데이터와 런타임 원칙

  • Assets/CSVdata는 현재 NewRunStageManager와 scene TextAsset 참조에서 쓰이는 활성 Stage Flow 데이터 경로다.
  • Assets/CSVData에도 같은 이름의 CSV 파일들이 존재하지만, 현재 InGame 코드가 이 폴더만을 단일 원천으로 삼는다고 말할 근거는 없다.
  • 현재 InGame 유닛/스킬 생성은 여전히 기존 Pakuri.Data 정의와 catalog/data manager를 통해 동작한다. 따라서 Legacy 제거는 완료가 아니다.
  • 프리팹은 시각/트리거/Actor 바인딩을 담당하고, 피해/회복/보호막/사망/보상 판정은 runtime service가 담당한다.
  • 스킬 choice modifier는 실행 시점 snapshot에 반영하고 원본 SkillData를 런타임 선택 상태로 변형하지 않는 방향을 유지한다.
  • 현재 Stage 1 normal boss HP multiplier는 StageEncounter.csv의 boss_health_multiplier_min/max와 NewRunStageManager.SelectBossRows() / ApplyEnemyHealthMultiplier(...) 경로로 적용된다.

6. 다음 작업 추천

0순위: 적 lifecycle owner 정리

InGameCombatManager 안의 적 활성 수, 사망 제거, enemy simulation tick 책임을 StageManager 또는 Stage 하위 enemy lifecycle service로 옮기는 설계를 먼저 잡는다. CombatManager는 전투 규칙 API와 roster facade로 축소한다.

1순위: 전체 스킬 확장 전 상태효과/임시효과 계층

Shock, slow, freeze, vulnerability, timed shield, buff duration 같은 효과를 공통 temporary effect 구조로 묶어야 Beam/Zone/Buff/Passive 스킬 확장이 안정적이다.

2순위: Beam / Zone / Buff executor

현재 Projectile/Shield는 동작 경로가 있으므로, 다음은 Beam trigger relay, Zone tick, Buff duration executor를 공통 runtime contract로 확장하는 순서가 맞다.

3순위: CSVData 원천 전환 판단

CSVdata와 CSVData가 공존하므로, 어떤 폴더를 활성 원천으로 삼을지 결정하고 InGame 코드의 Pakuri.Data 의존 제거 범위를 별도 Phase로 잡아야 한다.

4순위: Play Mode 수락 기준 정리

Codex는 Play Mode를 실행하지 않는다. 사용자는 NewRunScene에서 Day 1~11 진행, boss HP, RewardPanel, Offering, Manifest, 2P~5P 현현 스폰, projectile/shield 효과를 실제 플레이로 검증해야 한다.
