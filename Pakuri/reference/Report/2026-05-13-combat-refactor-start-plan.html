전투 런타임 전면 리팩토링 시작 설계안

이 문서는 기존 두 보고서와 현재 코드 상태를 근거로, 전투 구조를 크게 뜯어고칠 때 무엇부터 시작해야 하는지 정리한 리팩토링 설계 문서다. 결론부터 말하면 첫 작업은 새 타깃 모델을 전면 도입하는 것이 아니라, 현재 공유 상태의 소유권과 접근 경계를 고정하는 것이다.

2. 현재 문제 인식

2-1. partial 분리는 됐지만 상태 소유권은 아직 분리되지 않았다

현재 CombatRuntimeController partial 총량은 실제 검사 기준 14개 partial 파일, 14,022 lines, 668,782 chars다. 파일이 나뉘었지만 핵심 mutable state는 여전히 한 class 안에 있다.

근거현재 의미리팩토링상 문제
CombatRuntimeController.cs:307-310 enemies, projectiles, skillEffects, drones 리스트가 controller private field다. 스킬, projectile, enemy, party partial이 같은 전장 리스트를 직접 읽고 쓴다.
CombatRuntimeController.cs:326-378 선택 1P 유닛의 HP, shield, stat, skill id, sprite, projectile 설정이 controller field다. 선택 유닛 상태 owner가 명확하지 않아 selectedUnitRuntime과 controller field 동기화가 계속 필요하다.
CombatRuntimeController.cs:481-505 하나의 Update()가 spawn, enemies, projectiles, skill effects, manifested party, selected unit, HUD, battle resolution을 순서대로 호출한다. 실행 순서가 controller 내부 지식으로만 유지되어 시스템 단위 검증이 어렵다.

2-2. 전투 대상이 세 종류의 서로 다른 상태 저장소로 존재한다

기존 shared target/effect 보고서의 핵심 지적은 현재도 유효하다. 선택 아군은 controller field, 소환 아군은 CombatUnitRuntime, 적군은 nested EnemyRuntime에 상태가 흩어져 있다.

대상현재 저장 위치증상
선택 1P 유닛 CombatRuntimeController.cs:326-378 plus selectedUnitRuntime CombatRuntimeParty.cs:65-80이 controller field를 다시 runtime으로 mirror한다.
Manifested 2P-5P 유닛 CombatUnitRuntime.cs:21-50 Rin, Sein, Ariel, Vega 상태 field가 같은 MonoBehaviour에 계속 추가된다.
Enemy CombatRuntimeController.cs:28-94 nested EnemyRuntime shield, damage multiplier, buff timer, status timer, monster별 상태가 enemy 내부 field로 직접 누적된다.

2-3. 임시효과가 공통 객체가 아니라 직접 field 수정이다

현재 action speed, shield, chill, shock, vulnerable, enemy buff 같은 전투 중 임시 효과는 공통 active-effect list가 아니라 대상별 field와 timer로 흩어져 있다.

  • CombatRuntimeProjectiles.cs:516-529: 선택 유닛 shot/reload 감소가 GetSelectedMonsterActionSpeedMultiplier()에 직접 의존한다.
  • CombatRuntimeEnemies.cs:724-765: enemy의 shock, damage reduction, attack buff, move buff, chill/freeze/slow timer를 직접 감소시킨다.
  • CombatRuntimeEnemies.cs:1165-1204: Guardian/Charge enemy skill이 enemy shield와 buff timer field를 직접 수정한다.
  • CombatRuntimeEveSkills.cs:1465-1495: Eve status helper가 enemy의 shock/chill/vulnerable field를 직접 수정한다.
  • CombatRuntimeEveSkills.cs:1682-1731: Eve F shield가 selected controller field와 manifested runtime field를 각각 따로 갱신한다.

3. 리팩토링 목표

Goal 1

상태 소유권 고정

각 전투 상태를 누가 소유하는지 먼저 고정한다. controller는 직접 상태를 소유하는 곳이 아니라 scene wiring과 update 순서를 조율하는 얇은 orchestrator로 남긴다.

Goal 2

전장 리스트 접근 통제

enemies, projectiles, skillEffects, drones를 직접 수정하지 않고 service/facade API를 통해서만 조작하게 만든다.

Goal 3

공통 타깃 모델 도입 준비

처음부터 모든 상태를 CombatTargetModel로 옮기지 않는다. wrapper와 adapter를 둔 뒤 읽기 경로부터 공통화한다.

Goal 4

TemporaryEffect 계층화

shield/action speed/status처럼 중복 구현이 많은 임시효과부터 active-effect 모델로 옮긴다.

4. 무엇부터 시작해야 하는가

첫 작업: CombatRuntimeController의 상태 소유권 지도를 문서화하고, BattlefieldRuntime 또는 CombatBattlefield 계층을 만들어 전장 리스트 접근 API를 먼저 고정한다.

이유는 단순하다. 지금 바로 CombatTargetModel을 만들면 기존 skill partial들이 여전히 enemies, projectiles, skillEffects, controller selected fields를 직접 만진다. 그러면 새 모델과 기존 field가 병존하고, 동기화 지점만 늘어난다.

권장 시작 순서

  1. State Ownership Map 작성: controller field, CombatUnitRuntime field, EnemyRuntime field를 owner별로 분류한다.
  2. Battlefield facade 추출: enemies/projectiles/effects/drones list를 감싸는 읽기/쓰기 API를 만든다. 첫 단계에서는 내부 리스트를 그대로 쓰되 직접 접근을 줄인다.
  3. Projectile/Effect/Drone simulation 분리: 전장 object lifecycle을 controller에서 떼어내고 skill executor는 facade에 spawn 요청만 하게 한다.
  4. Manifested Party runtime 분리: 가장 큰 manager partial인 CombatRuntimeParty.cs를 party state, party combat, party UI adapter로 나눈다.
  5. CombatTargetModel adapter 도입: selected, manifested, enemy 순서로 공통 target read model을 붙인다. 처음에는 mirror/read-only로 시작한다.
  6. TemporaryEffect registry 도입: action speed, shield, shock/chill/vulnerable 순서로 직접 field 수정 경로를 effect application API로 옮긴다.

5. 단계별 구조 설계

Phase 0. 소유권 지도와 금지 규칙

목표: 코드를 거의 바꾸지 않고 어떤 상태를 어느 시스템이 소유할지 먼저 고정한다.

  • 출력물: Pakuri/reference/Report/combat-state-ownership-map.html 또는 markdown.
  • 분류: battlefield objects, selected unit state, manifested unit state, enemy state, skill runtime state, reward/result state, HUD state.
  • 금지 규칙: 새 code에서는 skill executor가 battlefield list를 직접 Add/Remove하지 않는다.
  • 검증: 문서와 코드 검색 결과가 일치해야 한다.

Phase 1. Battlefield facade

목표: 기존 리스트를 유지하되 접근 경로를 하나로 묶는다.

proposed sealed class CombatBattlefield
{
    IReadOnlyList<EnemyRuntime> Enemies { get; }
    ProjectileHandle SpawnProjectile(ProjectileSpawnRequest request);
    CombatEffectInstance SpawnEffect(EffectSpawnRequest request);
    DroneHandle SpawnDrone(DroneSpawnRequest request);
    EnemyRuntime FindNearestEnemy(Vector3 origin, float range, Predicate<EnemyRuntime> filter);
}

이 단계에서는 EnemyRuntime을 public model로 승격하지 않아도 된다. 먼저 controller partial 내부에서 facade를 만들고, 직접 리스트 조작을 facade method로 바꾸는 식으로 시작한다.

주의: 첫 PR에서 모든 projectile/effect 생성 지점을 바꾸지 말고, Eve나 Manifested Party처럼 호출 빈도가 높은 한 구간만 선택한다.

Phase 2. Projectile / Effect / Drone simulation service

목표: UpdateProjectiles(), UpdateMonsterSkillRuntimeEffects(), drone update를 별도 simulation service로 이동한다.

  • controller는 projectileSystem.Tick(delta)처럼 호출만 한다.
  • skill files는 projectiles.Add(...) 대신 spawn request를 보낸다.
  • damage application은 아직 controller method를 호출해도 된다. 이 단계의 목표는 list ownership 분리다.

Phase 3. Manifested Party runtime 분리

목표: CombatRuntimeParty.cs의 party state, party combat tick, party UI 표시를 분리한다.

새 책임옮길 내용남길 내용
ManifestedPartyRuntime 2P-5P 슬롯, party member runtime list, skill runtime sync, tick loop. scene object lookup은 controller/scene binder에 남겨도 된다.
ManifestedPartyViewAdapter HP/shield bar, label, fallback UI update. 전투 계산과 damage application은 넣지 않는다.
ManifestedSkillExecutor Eve/Rin/Sein/Vega/Ariel unit dispatch 선택과 generic fallback. 몬스터별 상세 damage 공식은 기존 skill files에 남겨 점진 분리한다.

Phase 4. CombatTargetModel read adapter

목표: 선택 아군, 소환 아군, 적군을 같은 read interface로 다룬다.

proposed interface ICombatTarget
{
    string Id { get; }
    CombatTargetSide Side { get; }
    Transform Transform { get; }
    CombatResourceState Resources { get; }
    CombatModifierState Modifiers { get; }
    TemporaryEffectCollection Effects { get; }
}

처음부터 모든 field를 옮기면 위험하다. 우선 SelectedUnitTargetAdapter, ManifestedUnitTargetAdapter, EnemyTargetAdapter를 만들어 읽기 경로를 통합한다. 쓰기 경로는 shield/status처럼 작은 효과부터 이동한다.

Phase 5. TemporaryEffect layer

목표: 임시효과를 대상별 field가 아니라 effect instance로 관리한다.

먼저 옮길 효과선정 이유수용 기준
Action speed modifier 선택/소환/적에서 각각 다른 multiplier 경로가 있다. 선택 유닛 shot/reload와 manifested unit cooldown이 같은 modifier API를 읽는다.
Shield Ariel/Eve/Enemy guardian에서 반복 구현되고 first-frame decay 같은 규칙이 민감하다. selected, manifested, enemy shield가 같은 resource API와 timer 정책을 쓴다.
Shock/Chill/Vulnerable Eve와 enemy update에서 직접 field/timer를 만진다. stack cap, duration refresh, expiration reset이 effect layer에서 재현된다.

6. 하지 말아야 할 시작점

  • 금지: CombatRuntimeController를 한 번에 여러 MonoBehaviour로 쪼개기. Unity serialized reference와 scene wiring 위험이 크다.
  • 금지: CombatTargetModel을 만들자마자 모든 HP/shield/status field를 옮기기. 기존 controller field와 이중 source of truth가 된다.
  • 금지: monster skill files를 먼저 전면 OOP화하기. 현재 skill files가 battlefield list와 target state를 직접 만지므로, service 경계 없이 옮기면 wrapper만 늘어난다.
  • 금지: 전투 중 mutable state를 singleton으로 빼기. 기존 보고서도 runtime battle state는 singleton 대상이 아니라고 판단했다.

8. 최종 판단

지금 바로 시작할 가장 좋은 리팩토링은 Battlefield/state ownership 경계 만들기다. 이는 두 기존 보고서의 결론을 합친 시작점이다. controller token 문제는 파일 크기만의 문제가 아니라 shared mutable state 문제이고, shared target/effect 문제는 대상 모델 부재만의 문제가 아니라 상태 접근 경계 부재 문제다.

따라서 첫 구현은 작아야 한다. CombatBattlefield facade로 리스트 접근을 줄이고, 그 다음 projectile/effect/drone simulation과 Manifested Party runtime을 분리한다. 그 후에야 CombatTargetModel과 TemporaryEffectInstance를 안정적으로 도입할 수 있다.

9. 제안서 목표 충족 여부 재검증

2026-05-13 재검증 결과, 이 문서의 순서만으로 첫 구현 티켓 하나가 모든 목표를 끝내지는 않는다. 다만 전체 phase를 끝까지 적용하면 두 2026-05-10 제안서의 핵심 목표인 스킬 재사용, 공통 대상 모델, 임시효과 재사용, God Class 해소로 갈 수 있다. 단, 공통 상위 클래스 상속은 첫 설계의 필수 조건으로 두지 않는다. 현재 코드에서는 EnemyRuntime이 private nested class이고 CombatUnitRuntime은 MonoBehaviour라서, 바로 상속 계층으로 묶으면 scene/runtime 결합이 커진다. 먼저 ICombatTarget / adapter를 만들고, 그 뒤 중복이 안정적으로 드러나는 부분만 CombatActorBase 같은 base class로 승격하는 순서가 안전하다.

목표 현재 HTML 순서로 해결 가능한가 필요한 보강 조건 근거
God Class 문제 해결 가능. 단기적으로는 완화, 전체 phase 완료 시 실질 해결. CombatRuntimeController가 list/state owner가 아니라 orchestrator만 맡도록 facade, simulation service, party runtime을 실제로 분리해야 한다. CombatRuntimeController.cs:307-310, :326-378, :481-505가 현재 집중 지점이다.
스킬 재사용 가능. 하지만 첫 단계가 아니라 service 경계와 target/effect layer 이후 가능하다. 몬스터별 skill executor가 projectiles.Add, skillEffects.Add, enemy field 직접 수정을 하지 않고 spawn/effect request를 보내야 한다. CombatRuntimeEveSkills.cs와 다른 monster skill partial들이 battlefield list와 enemy 상태를 직접 다룬다.
공통 전투 대상 모델 가능. Phase 4의 ICombatTarget / CombatTargetModel adapter가 해당 목표다. selected, manifested, enemy 순서로 read model을 붙이고, shield/status 같은 작은 write path부터 이관해야 한다. 기존 shared target 보고서가 CombatTargetModel selectedTarget, CombatUnitRuntime.Target, EnemyRuntime.Target 연결을 제안한다.
재사용 가능한 임시효과 가능. Phase 5가 이 목표다. 처음에는 action speed, shield처럼 공통성과 검증 지점이 명확한 효과부터 옮기고, shock/chill/vulnerable은 후속으로 옮긴다. CombatRuntimeEnemies.cs:724-765, CombatRuntimeEveSkills.cs:1465-1495, :1682-1731이 직접 field 수정 근거다.
Monster / Enemy 객체화 부분 가능. 이 HTML은 객체화를 직접 첫 단계로 삼지 않고, 객체화 가능한 경계를 먼저 만든다. EnemyRuntime을 controller nested class에서 빼고, CombatUnitRuntime과 공통으로 읽히는 ICombatTarget를 먼저 적용해야 한다. CombatRuntimeController.cs:28-94의 EnemyRuntime은 private nested class이고, CombatUnitRuntime.cs:8은 별도 MonoBehaviour다.
공통 상위 클래스 상속 현재 HTML만으로는 미완. 명시적 base-class migration 단계가 추가되어야 한다. 1차는 interface/adapter로 통합하고, 공통 resource/modifier/effect가 안정화된 뒤 CombatActorBase 또는 순수 모델 base class를 도입한다. 기존 shared target 보고서는 proposed CombatTargetModel 순수 런타임 객체를 제안하며, 상속 자체를 첫 조건으로 두지는 않는다.

보강된 최종 마이그레이션 기준

  1. CombatBattlefield facade가 전장 리스트 직접 접근을 대체한다.
  2. Projectile / Effect / Drone, Manifested Party, Enemy Simulation이 controller 밖의 책임 단위로 분리된다.
  3. SelectedUnitTargetAdapter, ManifestedUnitTargetAdapter, EnemyTargetAdapter가 같은 ICombatTarget 계약을 제공한다.
  4. TemporaryEffectInstance와 modifier/resource API가 action speed, shield, status 계열을 처리한다.
  5. 위 단계가 안정화된 후, 중복된 target/resource/effect 구현을 CombatActorBase 또는 순수 CombatTargetModel base로 올릴지 결정한다.

재검증 결론: 이 HTML의 리팩토링 순서는 두 제안서의 방향과 충돌하지 않는다. 다만 사용자가 말한 “공통 상위 클래스로 상속받아 Monster, Enemy 객체화”까지 보장하려면, 기존 문서의 phase 뒤에 base-class 승격 단계를 명시적으로 추가해야 한다. 따라서 구현을 시작한다면 먼저 facade/adapter/effect layer를 만들고, 그 다음 상속 구조를 선택하는 것이 현재 코드 근거상 더 안전하다.
