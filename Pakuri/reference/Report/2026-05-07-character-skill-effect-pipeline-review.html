캐릭터 생성 / 스킬 / 이펙트 구조 검토

작성일: 2026-05-07 | 역할: Designer | 기준: 실제 파일 검색, 코드 열람, Unity-MCP 실행 결과

작동 중인 축 CSV 런타임 데이터는 PakuriCsvRuntimeData에서 로드, 검증, 런타임 ScriptableObject 생성 후 PakuriDataManager에 등록된다.
구조상 위험 전투, 스킬, 투사체, 이펙트가 모두 CombatRuntimeController partial 클래스의 private 상태를 공유한다. 파일은 나뉘었지만 책임은 아직 한 클래스에 집중되어 있다.
우선 개선 대상 전용 SkillManager, EffectFactory, CharacterFactory가 없고, 런 세션은 학습 스킬을 안정적인 ID가 아니라 표시 이름 문자열로 저장한다.

확인한 현재 파이프라인

CSV / AssetCatalog Assets/CSVdata/source와 Assets/Resources/Pakuri/CSVRuntime 리소스를 사용한다.
Runtime Build PakuriCsvRuntimeData.Build.cs가 몬스터, 적, 액티브, 패시브, 보상 정의를 런타임 SO로 만든다.
Data Manager PakuriDataManager.RegisterCatalog가 몬스터, 적, 스킬, 보상 조회용 딕셔너리를 재구성한다.
Run Creation MainMenuFlowController, RunStartContext, RunSession, RunSceneBootstrap가 선택 몬스터와 세션을 넘긴다.
Combat Runtime CombatRuntimeController partial들이 선택 몬스터, 투사체, 적, 스킬, 이펙트까지 직접 실행한다.

근거 요약

영역 확인한 파일 / 출력 판단
데이터 로딩 Pakuri/Assets/Scripts/Data/PakuriCsvRuntimeData.cs에서 RuntimeInitializeOnLoadMethod(BeforeSceneLoad), LoadAndValidateRuntimeCatalog, PakuriDataManager.Instance.RegisterCatalog(catalog) 확인. 런타임 시작 전 데이터 등록 의도는 명확하다. 실패 시 FailAndQuit로 치명 오류 처리도 있다.
런타임 데이터 생성 PakuriCsvRuntimeData.Build.cs에서 MonsterDefinition과 EnemyDefinition을 ScriptableObject.CreateInstance로 만들고 UnitSprite, ProjectileSprite, 스킬, 패시브를 채운다. CSV 기반 값을 런타임 SO로 변환하는 어댑터 구조는 존재한다.
데이터 매니저 PakuriDataManager.cs에 monsters, stageOneEnemies, activeSkills, passiveSkills, 몬스터별 스킬/보상 딕셔너리 확인. 데이터 조회 매니저는 있다. 단, 전투 실행 매니저나 팩토리는 아니다.
캐릭터 선택 / 생성 MainMenuFlowController.StartRun은 RunStartContext.Ensure().PrepareNewRun(selectedMonster)를 호출하고, RunSceneBootstrap은 pending context 또는 fallback monster로 BeginCombat을 호출한다. 선택 몬스터 전달 흐름은 있다. 하지만 별도 캐릭터 런타임 생성 팩토리는 검색되지 않았다.
전투 상태 집중 CombatRuntimeController.cs에 EnemyRuntime, ProjectileRuntime, SkillEffectRuntime, DroneRuntime 내부 클래스와 enemies, projectiles, skillEffects 리스트 확인. 전투 도메인 상태가 한 컨트롤러에 몰려 있다.
스킬 구현 방식 CombatRuntimeArielSkills.cs, CombatRuntimeEveSkills.cs, CombatRuntimeRinSkills.cs, CombatRuntimeSeinSkills.cs, CombatRuntimeVegaSkills.cs가 모두 public partial class CombatRuntimeController. 파일 분리는 되어 있지만 클래스 분리가 아니라서 사이드 이펙트 경계가 약하다.
이펙트 생성 CombatRuntimeEveSkills.cs의 CreateLineEffect, CreateCircleEffect가 new GameObject, SpriteRenderer, GetSharedSprite, GetCircleSprite로 즉석 생성한다. 공용 이펙트 생성 함수는 있지만 데이터 기반 이펙트 정의, 프리팹 우선 사용, 풀링 매니저는 없다.
세션 스킬 저장 RunSession.cs에서 LearnedActives, LearnedPassives가 List<string>이고 HasLearnedActive(skill.DisplayName) 사용처가 RunCombatUiController.cs에 있다. 표시 이름 변경, 번역, 중복 이름에 취약하다. SkillId, PassiveId 기반으로 바꾸는 것이 맞다.
검증 결과 Unity-MCP 실행 결과: catalogNull=False, managerSame=True, monsters=5, enemies=8, firstMonster=ariel, firstActive=5, firstPassive=5. 현재 에디터 안에서 런타임 카탈로그와 데이터 매니저 등록은 정상 확인됐다.
자동 테스트 Get-ChildItem Pakuri\Assets -Recurse -Include *Tests*.cs,*Test*.cs 결과 출력 없음. 현재 검색 범위에서는 EditMode/PlayMode 테스트 파일을 찾지 못했다.

현재 구조 설명

1. 데이터 계층

PakuriCsvRuntimeData는 CSV 소스 카탈로그와 에셋 카탈로그를 리소스에서 읽고, 소스 모델 검증 후 런타임 GameDataCatalog를 만든다. PakuriCsvRuntimeData.Build.cs는 MonsterDefinition, EnemyDefinition, SkillDefinition, PassiveDefinition을 메모리 SO로 조립한다. 이후 PakuriDataManager.RegisterCatalog가 조회용 딕셔너리를 채운다.

2. 캐릭터 선택과 런 시작

메인 메뉴는 PakuriDataManager.Instance.GetMonsters(gameDataCatalog)로 캐릭터 목록을 만들고, 선택 시 RunStartContext.PrepareNewRun으로 몬스터와 RunSession을 보관한다. 런 씬에서는 RunSceneBootstrap가 pending context가 있으면 그것으로, 없으면 fallback monster로 전투를 시작한다.

3. 전투 / 스킬 / 이펙트

전투 실행은 사실상 CombatRuntimeController 하나가 담당한다. 몬스터별 스킬 파일은 partial 파일로 나뉘어 있지만 모두 같은 클래스이므로 enemies, projectiles, skillEffects, 선택 몬스터 상태를 직접 공유한다. 이펙트는 공용 CreateLineEffect, CreateCircleEffect를 사용하지만, 별도 이펙트 서비스나 풀링 계층 없이 즉석 GameObject를 생성하고 수명이 끝나면 Destroy한다.

구조상 문제

1. partial 분리는 책임 분리가 아니다.

CombatRuntimeController는 여러 파일로 분할됐지만 하나의 private 상태를 공유한다. 새 몬스터 스킬을 추가할 때 다른 몬스터의 상태, 투사체 충돌, 이펙트 수명, 보상/세션 상태까지 건드릴 수 있는 구조다. 실제 줄 수 기준으로 CombatRuntimeSeinSkills.cs 1125줄, CombatRuntimeEveSkills.cs 1057줄, CombatRuntimeVegaSkills.cs 883줄, CombatRuntimeController.cs 841줄이었다.

2. 스킬 실행이 데이터 기반이 아니라 코드 분기 기반이다.

SkillDefinition에는 SkillId, Slot, RuntimeKind, SkillEffectPrefab 같은 데이터가 들어오지만, 실제 실행은 몬스터별 partial 메서드와 하드코딩된 분기에 강하게 묶여 있다. 신규 캐릭터 추가 시 CSV만 추가해서 끝나는 파이프라인은 아니다.

3. 이펙트 파이프라인이 임시 생성 중심이다.

현재 공용 이펙트 생성 함수는 SpriteRenderer 직사각형/원형을 빠르게 만들 수 있어 프로토타입에는 유용하다. 하지만 SkillEffectPrefab 데이터가 있음에도 이펙트 생성 계층이 없어, 아트 교체와 스킬별 프리팹 적용 경로가 약하다. 이전 Vega projectile sprite 문제처럼 CSV, 에셋 카탈로그, 런타임 SO 사이의 동기화가 어긋나면 화면에 예전 리소스가 나올 수 있는 구조다.

4. UI/런 컨트롤러도 비대하다.

줄 수 확인 결과 RunCombatUiController.cs는 1372줄, DebugSceneController.cs는 1181줄이었다. 이 파일들은 UI 생성, 바인딩, 보상 처리, 세션 조회, 테스트/디버그 편의 기능을 같이 가진다. UI가 커질수록 전투 로직 수정과 UI 수정이 서로 영향을 줄 가능성이 높다.

5. 학습 스킬 상태가 표시 이름에 의존한다.

RunSession은 기본 액티브를 monster.ActiveSkillName으로 저장하고, UI는 skill.DisplayName으로 학습 여부를 확인한다. 이 구조는 이름 변경, 한국어/영어 표기 변경, 같은 이름의 스킬 추가에 취약하다.

잘 되어 있는 부분

데이터 로드와 검증 루트는 명확하다.

PakuriCsvRuntimeData는 BeforeSceneLoad 초기화, 소스 검증, 런타임 카탈로그 검증, 데이터 매니저 등록까지 한 경로로 묶여 있다. Unity-MCP 실행에서도 카탈로그가 null이 아니고, 데이터 매니저의 현재 카탈로그와 같은 참조로 등록된 것이 확인됐다.

프로토타입 확장 속도는 확보되어 있다.

partial 파일 분리와 공용 이펙트 함수 덕분에 새 스킬을 빠르게 붙이기는 쉽다. 현재 단계에서 기능 실험에는 장점이 있지만, 캐릭터 수와 이펙트 종류가 늘어나면 유지보수 비용이 급격히 올라갈 수 있다.

개선 방향

1순위런 세션을 ID 기반으로 바꾸기

RunSession.LearnedActives와 LearnedPassives는 SkillId, PassiveId를 저장해야 한다. UI는 ID로 학습 여부를 확인하고, 표시 텍스트는 SkillDefinition.DisplayName에서 렌더링만 담당하게 분리한다.

2순위CombatEffectFactory 또는 CombatEffectService 도입

CreateLineEffect, CreateCircleEffect를 먼저 새 클래스로 옮기고, SkillEffectPrefab이 있으면 프리팹을 사용하고 없으면 현재 임시 SpriteRenderer 이펙트로 fallback하는 구조가 좋다. 이후 수명 관리와 풀링을 같은 계층에서 처리하면 Destroy 남발을 줄일 수 있다.

3순위몬스터 스킬 런타임 모듈 분리

CombatRuntimeController가 모든 몬스터 스킬을 직접 소유하지 않도록, IMonsterSkillRuntime 또는 MonsterSkillRuntimeBase 형태로 Ariel/Eve/Rin/Sein/Vega 모듈을 분리한다. 컨트롤러는 CombatContext를 넘기고, 모듈은 자신의 스킬 상태만 관리하는 쪽이 안전하다.

4순위캐릭터 런타임 팩토리 도입

선택된 MonsterDefinition을 전투에서 쓰는 체력, 공격력, 스프라이트, 탄창, 쿨다운 상태로 변환하는 MonsterRuntimeFactory를 만든다. 그러면 RunStartContext와 RunSceneBootstrap는 선택 전달만 담당하고, 전투 컨트롤러의 초기화 책임을 줄일 수 있다.

5순위검증 자동화 추가

현재 검색한 범위에서는 테스트 파일이 없었다. 최소한 CSV/AssetCatalog 동기화, PakuriDataManager 조회, 스킬 ID 중복, 스킬 슬롯 규칙, 이펙트 프리팹 참조 유효성을 EditMode 테스트나 Editor validation 메뉴로 추가하는 것이 좋다.

권장 진행 순서

지금 구조를 한 번에 갈아엎는 것은 위험하다. 기능이 이미 여러 몬스터에 퍼져 있으므로, 먼저 RunSession의 ID 기반 학습 상태와 CombatEffectFactory 분리처럼 영향 범위가 작고 확인하기 쉬운 변경부터 진행하는 편이 좋다. 그 다음 새 몬스터나 대형 스킬 추가 시점에 스킬 런타임 모듈 분리를 적용하면, 기존 기능을 유지하면서 구조를 점진적으로 바꿀 수 있다.

검토 한계

  • Designer 역할 검토이므로 런타임 코드 수정은 하지 않았다.
  • AGENTS.md 기준에 따라 Play Mode 실행 검증은 하지 않았다.
  • Unity 콘솔의 warning/error 조회 결과에는 missing script 경고 2개와 MCP 연결 로그가 있었다. 해당 missing script는 이번 구조 검토 범위에서 특정 오브젝트까지 추적하지 않았다.
