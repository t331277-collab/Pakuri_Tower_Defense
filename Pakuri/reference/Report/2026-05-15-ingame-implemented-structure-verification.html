작성일: 2026-05-15. 이 문서는 현재 저장소에서 검사한 실제 파일과 명령 출력만 근거로, 데이터 로드 및 할당 방식, 몬스터/적 구조, 스킬 구현 상태와 다음 구현 방향을 검증한다.

Blueprint 데이터, 기존 데이터 매퍼, learned active runtime 상태는 있다. Executor, hitbox relay, 실제 투사체/빔/장판/데미지/보호막 실행은 아직 없다.

1. 2026-05-10 구조 제안 대비 검증

1-1. God Class 위험 검증

2026-05-10 제안의 문제 기준 현재 InGame 구현 근거 판정
CombatRuntimeController가 enemies, projectiles, skillEffects, drones 같은 mutable runtime state와 update loop를 한곳에서 공유하던 문제 InGameCombatManager는 UnitRosterService, EnemyCombatSimulationSystem, UnitResourceMutationService를 필드로 두고, Update()에서는 enemy simulation tick만 위임한다. 현재 범위에서는 God Class 아님 전투 roster, 적 simulation, resource mutation이 별도 클래스로 나뉘어 있다.
Enemy Simulation은 selected-unit 로직에서 떼어내야 한다는 제안 EnemyCombatSimulationSystem이 enemy state dictionary, 이동, target 선택, attack attempt loop를 가진다. 실제 damage 호출은 아직 연결하지 않았다. 방향 일치 적 simulation 책임은 manager 본문에 직접 누적되지 않았다.
Shield/damage/resource 변경이 여러 skill partial에 흩어지는 문제 UnitResourceMutationService.ApplyDamage, GrantShield, SetShield가 shield 우선 흡수와 HP 갱신 결과를 만든다. InGameCombatManager는 결과가 바뀐 경우 Actor refresh만 호출한다. 현재 구현은 분리됨 단, duration shield나 reactive hook은 아직 없다.
Controller 대신 다른 전역 singleton으로 mutable battle state를 옮기는 것은 해법이 아니라는 경고 현재 새 InGame runtime state는 InGameCombatManager 인스턴스 내부 service와 unit model에 있다. NewRunSceneEntryManager.ResolveCatalog()는 데이터 조회용으로 PakuriDataManager.Instance를 사용하지만, battle state 저장소로 쓰지는 않는다. 전역 상태 이전 문제는 보이지 않음 데이터 catalog singleton 의존은 별도 CSVData 전환 리스크다.
새 기능이 한 entry/controller에 계속 붙으면 다시 큰 클래스가 될 수 있음 NewRunSceneEntryManager는 현재 Start, selected monster spawn, 3종 enemy spawn sequence, catalog/definition resolve, prefab resolve, combat manager registration까지 담당한다. 성장 위험 있음 지금은 NewRunScene bootstrap으로 허용 가능하지만, wave policy, run reward, skill load, pooling까지 추가하면 split 대상이다.

1-2. Shared Combat Target / Temporary Effect 제안 문제 검증

2026-05-10 제안 항목 현재 InGame 구현 근거 현재 구조에 같은 문제가 있는지
선택 아군, 소환 아군, 적이 공통 target/resource 모델을 통해 처리되어야 함 BaseUnitRuntimeModel이 identity, stats, defenses, resources, SkillRuntime을 공통으로 가진다. MonsterUnitRuntimeModel과 EnemyUnitRuntimeModel은 이를 상속한다. 기본 문제는 완화됨 현재 새 InGame 구조는 Monster/Enemy가 같은 base model/resource 경로를 쓴다.
CombatTargetModel.ActiveEffects와 TemporaryEffectInstance가 필요함 UnitStateBucket은 learned active/passive skill id와 chosen choice id만 가진다. Scripts2/InGame 검색에서 ActiveEffects, TemporaryEffect, StatModifier, ModifierState 파일/타입은 확인되지 않았다. 아직 미구현 이전 구조의 중복 타이머 문제를 새 구조로 옮긴 증거는 없지만, 공통 temporary effect 계층도 아직 없다.
Shield는 공통 subsystem으로 분리해야 함 UnitResourceMutationService가 현재 shield grant/set과 damage 시 shield 우선 흡수를 처리한다. MonsterUnitActor, EnemyUnitActor는 HP와 shield를 같은 bar의 segment로 표시한다. 부분 해결 수치형 shield pipeline은 공통화됐지만, duration, stack, source, refresh rule, reactive hook은 아직 skill executor 이후 과제다.
ActionSpeed, MoveSpeed, DamageTaken, DamageDealt 같은 modifier aggregator가 필요함 Scripts2/InGame 검색에서 ActionSpeedMultiplier, MoveSpeedMultiplier, DamageTakenMultiplier, DamageDealtMultiplier 공통 modifier 경로는 확인되지 않았다. 아직 미구현 Phase4-B/C에서 실제 효과를 붙이기 전에 modifier/effect owner를 정해야 한다.
Skill executor가 target/effect/resource 경로를 재사용해야 함 현재 Phase4-A 파일은 SkillRuntimeInstance, UnitSkillRuntimeSet, SkillRuntimeFactory까지다. SkillExecutorRegistry, SkillExecutionSnapshot, SkillHitboxRelay는 아직 존재하지 않는다. 구현 전 위험 지점 executor를 manager에 직접 누적하면 2026-05-10의 shared-state controller 문제가 재발할 수 있다.
결론적으로, 현재 새 InGame 구현 범위에서는 2026-05-10 보고서가 지적한 거대한 shared-state controller 문제는 재현되지 않았다. 다만 공통 temporary effect, modifier aggregator, skill executor/relay가 아직 없기 때문에, 다음 구현에서 이 책임을 InGameCombatManager나 NewRunSceneEntryManager에 직접 누적하지 않는 것이 핵심이다.

3. 검증 범위와 판정

영역 현재 판정 근거 요약
NewRunScene 데이터 진입 동작 경로 있음 NewRunSceneEntryManager가 선택 몬스터 ID, fallback catalog, prefab 필드, 적 ID를 사용해 런타임 모델과 Actor를 만든다.
새 CSVData 원천화 전환 전 MonsterStat.csv, EnemyStat.csv, SkillData.csv에는 샘플 행이 있지만, Scripts2/InGame 검색 결과 아직 기존 Pakuri.Data 타입과 로더 참조가 남아 있다.
몬스터/적 모델 구조 구현됨 BaseUnitRuntimeModel, MonsterUnitRuntimeModel, EnemyUnitRuntimeModel, UnitFactory가 분리되어 있다.
Actor 표시 구조 구현됨 MonsterUnitActor와 EnemyUnitActor가 모델을 보유하고 HP/Shield segment를 같은 bar 안에서 갱신한다.
적 행동 공격 시도까지 EnemyCombatSimulationSystem은 target search, 이동, attack attempt count/log만 처리한다. 실제 피해나 적 스킬은 연결되지 않았다.
HP/Shield 변경 파이프라인 구현 InGameCombatManager.ApplyDamage, GrantShield, SetShield가 UnitResourceMutationService를 거쳐 Actor refresh를 호출한다.
스킬 실행 미구현 Phase4-A runtime state는 있으나 SkillExecutorRegistry, SkillExecutionSnapshot, SkillHitboxRelay, Projectile/Beam/Zone executor는 아직 파일로 존재하지 않는다.

4. 데이터 로드 및 할당 방식 검증

4-1. 현재 NewRunScene 런타임 데이터 흐름

  1. NewRunSceneEntryManager.Start()가 ResolveCombatManager(), SpawnSelectedPlayerUnit(), SpawnInitialEnemySequence()를 호출한다.
  2. 선택 몬스터 ID는 NewRunStartContext.SelectedMonsterId 또는 Eve fallback에서 결정된다.
  3. ResolveCatalog()는 PakuriDataManager.Instance.CurrentCatalog, serialized fallbackCatalog, PakuriCsvRuntimeData.ResolveCatalogOrFallback(null) 순서로 catalog를 얻는다.
  4. ResolveMonsterDefinition(...)과 ResolveEnemyDefinition(...)은 PakuriDataManager 등록 데이터 또는 GameDataCatalog lookup을 사용한다.
  5. UnitFactory가 MonsterDefinition, EnemyDefinition, RunSession.RunMonsterState를 런타임 모델로 복사한다.
확인 항목 실제 근거 판정
Scene serialized assignment NewRunScene.unity에 fallbackCatalog, 5개 몬스터 prefab, 3개 적 prefab, initialEnemyId/rangedEnemyId/bufferEnemyId, Y 범위, spawn interval이 저장되어 있다. 확인됨
현재 샘플 CSVData MonsterStat.csv에는 Eve/Ariel, EnemyStat.csv에는 Warrior/Rogue/Priest, SkillData.csv에는 eve-a/ariel-b 샘플 행이 있다. 파일 존재
CSVData authoritative 여부 Scripts2/InGame 검색 결과 PakuriCsvRuntimeData, PakuriDataManager, GameDataCatalog, MonsterDefinition, EnemyDefinition, SkillDefinition 참조가 남아 있다. 아직 아님
Legacy CSV source path Test-Path Pakuri\Assets\CSVdata\source 결과는 False였다. 자동 sync 위험
결론: 현재 InGame은 NewRunScene 테스트를 위해 기존 데이터 catalog/fallback 흐름을 계속 사용한다. 새 Assets/CSVData 파일은 구조 전환용 샘플 데이터로 존재하지만, 아직 런타임 source of truth는 아니다. 나중에 CSVData loader/catalog가 들어오면 NewRunSceneEntryManager, UnitFactory, InGameSkillCatalog의 기존 데이터 의존을 줄이는 순서로 전환해야 한다.

5. 몬스터와 적 구조 검증

5-1. 모델 계층

파일 역할 현재 구현 상태
BaseUnitRuntimeModel.cs 공통 identity, stats, defense, resources, skill runtime, auto flags 보유 구현됨
MonsterUnitRuntimeModel.cs 몬스터 전용 UnitStateBucket 보유 구현됨
EnemyUnitRuntimeModel.cs 적 encounter role, attack type, attribute, attack attempt range/cooldown 보유 구현됨
UnitStateBucket.cs learned active/passive skill IDs와 chosen choice IDs 보유 구현됨

5-2. Actor와 HP/Shield 표시

MonsterUnitActor와 EnemyUnitActor는 각각 모델을 저장하고, MonsterNameLabel, MonsterHpLabel, MonsterHpBar/Background, Fill, Shield를 찾아 표시한다. HP와 Shield는 maxHealth와 currentHealth + currentShield 중 큰 값을 분모로 삼아 하나의 background 안에서 segment로 나뉜다.

예시 현재 계산 방식
HP 100 / Shield 0 / BG X 20 분모 100, HP segment X 20, Shield inactive
HP 100 / Shield 100 / BG X 20 분모 200, HP segment X 10, Shield segment X 10, 둘이 BG 전체를 채움
HP 50 / Shield 50 / MaxHP 100 / BG X 20 분모 100, HP segment X 10, Shield segment X 10

5-3. 로스터와 적 combat attempt

InGameCombatManager는 UnitRosterService를 소유하고, 등록된 player/enemy 리스트를 기준으로 EnemyCombatSimulationSystem.Tick(...)을 호출한다. 적 simulation은 살아 있는 player target을 찾고, 거리가 attack attempt range보다 멀면 이동하며, 범위 안이면 cooldown 후 attack attempt count를 올린다.

현재 적 attack attempt는 실제 ApplyDamage(...)를 호출하지 않는다. 이 결정은 몬스터/적 스킬 구현 전까지 HP 감소와 death 검증을 보류하기 위한 구조와 일치한다.

6. 스킬 구현 상태 검증

스킬 계층 현재 파일/상태 구현 범위
Blueprint data SkillData.cs, SkillBlueprintSpecs.cs, 각 하위 *SkillData.cs 데이터 구조 구현 Timing, targeting, damage, status, projectile, area, buff, shield, passive spec이 있다.
기존 데이터 bridge InGameSkillCatalog.cs, InGameSkillDefinitionMapper.cs 임시 bridge 구현 기존 SkillDefinition을 transient SkillData로 만든다.
검증 도구 InGameSkillDataValidator.cs, editor menu 구조 검증 구현 카탈로그/스킬 매핑 검증용. 실행 검증은 아니다.
Runtime state SkillRuntimeInstance.cs, UnitSkillRuntimeSet.cs, SkillRuntimeFactory.cs Phase4-A 완료 learned active skill만 runtime instance로 만들고 cooldown/cast/duration/tick/magazine/reload를 관리한다.
Executor / registry 예정: SkillExecutionSnapshot, SkillChoiceResolver, IInGameSkillExecutor, SkillExecutorRegistry Phase4-B 예정 아직 파일 없음. 실제 효과 없이 호출 계약과 선택지 snapshot만 먼저 만든다.
Hitbox relay 예정: SkillHitboxRelay, Projectile/Beam/Zone runtime Phase4-B/C 예정 프리팹 trigger는 신호만 전달하고 판정 로직은 runtime/executor가 소유한다.
실제 효과 예정: Projectile/Shield 최소 executor Phase4-C 예정 eve-a 데미지와 ariel-b 보호막을 최소 샘플로 연결한다.

7. 앞으로의 스킬 구현 방향

  1. Phase4-B: executor 인터페이스, registry, execution context, choice resolver, execution snapshot을 추가한다. 이 단계에서는 ApplyDamage, GrantShield, prefab instantiate를 호출하지 않는다.
  2. Phase4-B hitbox 계약: SkillHitboxRelay를 설계해 Projectile/Beam/Zone 프리팹 collider가 접촉 신호만 전달하게 한다. 게임 판정은 runtime system이 처리한다.
  3. Phase4-C projectile: ProjectileSkillData.Projectile.ProjectilePrefab을 우선 사용하고, 없으면 SkillEffectPrefab fallback을 검토한다. 빠른 투사체는 trigger 신호만 믿지 않고 이전 위치와 현재 위치 사이를 cast로 보정한다.
  4. Phase4-C beam: Beam은 길쭉한 trigger collider를 가진 프리팹 방향으로 간다. 런타임이 길이, 회전, 지속시간을 맞추고 trigger 신호를 executor/runtime으로 넘긴다.
  5. Phase4-C zone: Zone은 원형/영역 trigger collider 프리팹을 사용하고 Enter/Stay/Exit 신호를 relay한다. 대상 목록, tick interval, 지속시간, 중복 적용 제한은 zone runtime이 관리한다.
  6. Phase5 이후: Run 중 배운 active/passive와 choice state를 runtime rebuild 또는 다음 전투 진입 때 반영한다. SkillData 원본은 런타임 선택 상태로 수정하지 않는다.

8. 리스크와 확인 필요 항목

리스크 근거 권장 조치
새 CSVData와 현재 런타임 데이터 경로가 다름 CSVData 샘플 파일은 존재하지만 Scripts2/InGame은 기존 Pakuri.Data 경로를 사용한다. CSVData loader/catalog를 별도 phase로 구현하고, 기존 fallback 경로와 비교 검증한 뒤 전환한다.
Legacy CSV source path 누락 Pakuri\Assets\CSVdata\source가 존재하지 않는다. 현재 fallback catalog로 NewRunScene 테스트가 가능한지 유지하되, auto-sync 오류가 반복되면 legacy sync 경로 또는 CSVData 전환 정책을 정리한다.
스킬 실제 효과 미구현 executor, relay, projectile/beam/zone runtime 파일이 아직 없다. Phase4-B에서 계약을 먼저 만들고, Phase4-C에서 최소 샘플만 연결해 구조를 검증한다.
죽음/보상/제거 미구현 UnitResourceMutationService는 IsDead를 반환하지만 제거/보상 흐름은 없다. 실제 데미지 연결 후 death 처리, roster unregister, Actor 제거, reward 조건을 별도 phase로 추가한다.
대량 적 성능 현재 적 simulation은 roster list를 순회하고 nearest player를 선형 검색한다. 100+ enemies Play Mode 검증 후 필요하면 spatial partition 또는 target cache를 검토한다.

10. 최종 결론

현재 구조는 NewRunScene 기준으로 선택 몬스터와 3종 적 prefab을 runtime model/Actor/roster에 연결하고, 적 이동 및 attack attempt, HP/Shield mutation/display pipeline, learned active skill runtime state까지 구현되어 있다. 그러나 새 CSVData source of truth, 스킬 executor/relay, 실제 projectile/beam/zone/shield/damage 실행, death/reward 처리는 아직 다음 단계다.

2026-05-10 두 제안 기준으로 보면, 현재 InGame 구현은 InGameCombatManager가 모든 전투 상태와 실행 로직을 직접 보유하는 God Class 형태는 아니다. 하지만 NewRunSceneEntryManager는 bootstrap 책임이 이미 넓고, 공통 temporary effect / modifier / skill executor 계층은 아직 없으므로 Phase4-B 이후에는 이 경계를 별도 service로 유지해야 한다.

다음 구현은 Phase4-B에서 실행 계약과 relay 구조를 먼저 만들고, Phase4-C에서 eve-a와 ariel-b만 최소 샘플로 연결하는 순서가 가장 안전하다.
