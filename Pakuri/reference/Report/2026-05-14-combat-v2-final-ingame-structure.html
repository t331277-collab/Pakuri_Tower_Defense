InGame Target Structure

InGame 완성 후 인게임 구조와 클래스 책임

이 문서는 2026-05-14-combat-v2-build-roadmap.html의 Phase1-D부터 Phase8-A까지 끝까지 구현된다는 전제에서, 인게임이 어떤 흐름으로 실행되고 어떤 클래스가 무엇을 담당해야 하는지 정리한 구조 보고서다. 현재 저장소에 존재하는 클래스와 아직 제안 단계인 클래스를 분리해서 표시한다.

1. 완성 목표: 공통 유닛 상속과 Blueprint 스킬 구조

공통 유닛 상속/대상 구조

InGame이 완성되면 플레이어 유닛, 적 유닛, 넥서스처럼 전투 대상이 되는 객체는 공통 부모 또는 공통 대상 계약을 공유한다. 버프, 행동속도, 쉴드, 상태이상, 피해 증감은 각 유닛 클래스가 따로 들고 있는 개별 필드가 아니라 공통 전투 대상 모델의 modifier/effect 레이어에 동일하게 적용된다.

이 방향은 2026-05-10-shared-combat-target-and-temporary-effect-design.html에서 제기한 문제, 즉 selected unit, manifested unit, enemy가 서로 다른 상태 필드와 타이머를 가져 임시 효과를 재사용하기 어려웠던 문제를 해결하기 위한 구조다.

재사용 가능한 스킬 Blueprint 구조

스킬은 C:\TowerDefence_Pakuri\towerdefense_pakuri_docs\docs\dev\skill-class-design.md의 설계에 맞춰 SkillData 추상 ScriptableObject와 projectile, beam, zone, buff, shield, passive, status 계열 데이터로 분리한다. 실행 코드는 데이터 Blueprint를 읽는 executor/registry 쪽으로 모아, 이전 스킬 하드코딩 문제를 해결한다.

최종 구조는 Blueprint를 참고해 스킬 데이터를 재사용 가능하고 확장 가능한 형식으로 완성하는 것을 목표로 한다. 공통 데이터로 표현되지 않는 예외 스킬은 Blueprint 계약을 유지한 상태에서 전용 executor 또는 custom hook으로만 분리한다.

문제 완성 구조 기대 효과
유닛 종류별 버프/상태/행동속도 적용 경로가 달라지는 문제 공통 전투 대상 부모/계약과 공통 temporary effect 적용 레이어 선택 유닛, 소환 유닛, 적, 넥서스에 같은 방식으로 버프와 행동속도 보정이 적용된다.
스킬별 로직이 코드에 직접 박혀 재사용과 확장이 어려운 문제 SkillData 계열 Blueprint 데이터와 executor/registry 분리 새 projectile, beam, zone, buff, shield, passive 스킬을 데이터 중심으로 추가하고, 예외만 별도 실행기로 확장한다.
임시 효과와 스킬 효과가 서로 다른 구조로 누적되는 문제 StatusEffectData, modifier, action speed multiplier, shield pool을 공통 전투 대상 모델에 연결 일시 버프, 디버프, 실드, 피해 보정이 동일한 갱신/만료 규칙을 따른다.

2. 최종 인게임 실행 흐름

RunStartContext / RunSession MainMenu에서 선택된 MonsterDefinition과 런 진행 상태를 보관한다.
→
NewRunScene / GameManager NewRunScene의 GameManager가 InGame 진입점을 가진다.
→
InGameCombatManager 전투 세션 생성, 서비스 구성, Tick 순서, 결과 반환을 총괄한다.
PakuriDataManager / GameDataCatalog CSV 기반 MonsterDefinition, EnemyDefinition, SkillDefinition을 제공한다.
→
UnitFactory / InGameSkillCatalog 기존 정의를 InGame 런타임 모델과 SkillData로 변환한다.
→
Actors / Services / Executors 유닛 표시, 대상 탐색, 피해/상태, 스킬 실행, 투사체/효과 시뮬레이션을 분리해서 처리한다.

전투 1프레임의 목표 Tick 순서

  1. InGameCombatManager가 전투 상태가 진행 중인지 확인한다.
  2. UnitRosterService와 대상 레지스트리가 살아 있는 아군/적/넥서스 대상을 갱신한다.
  3. 자동 공격과 자동 스킬 시스템이 UnitRuntimeModel.AutoAttackEnabled, AutoSkillEnabled, learned skill 상태를 확인한다.
  4. SkillRuntimeInstance들이 쿨다운, 재장전, 지속시간, 내부 쿨다운을 Tick한다.
  5. SkillExecutorRegistry가 SkillData 타입에 맞는 실행기(projectile, beam, zone, buff, shield, passive)를 호출한다.
  6. 실행기는 직접 유닛 리스트를 뒤지지 않고 TargetQueryService, DamageService, StatusEffectService, ProjectileSimulation, SkillEffectSimulation에 요청한다.
  7. MonsterUnitActor, EnemyUnitActor, 투사체/이펙트 프리팹 뷰가 모델 상태를 표시한다.
  8. 넥서스 파괴, 적 전멸, 제한시간 등 종료 조건이 충족되면 InGameResultManager를 만들고 Run/UI 계층으로 넘긴다.

3. 계층별 책임

계층 주요 클래스 담당 소유하면 안 되는 것
Run / 진입 RunStartContext, RunSession, 제안 InGameSceneBootstrap 선택 몬스터, 파티 멤버, learned skills, reward choices, 런 일차/스테이지 상태를 InGame 입력으로 전달한다. 전투 피해 계산, 타겟 탐색, 스킬 실행, 투사체 Tick을 소유하지 않는다.
전투 오케스트레이션 InGameCombatManager, InGameContextManager, InGameResultManager 전투 시작/종료, 서비스 생성, 프레임별 Tick 순서, 결과 생성만 담당한다. 개별 스킬 공식, 개별 상태이상 공식, 프리팹 내부 표시 로직을 직접 갖지 않는다.
데이터 PakuriCsvRuntimeData, GameDataCatalog, PakuriDataManager, InGameSkillCatalog 기존 CSV/Data 흐름을 유지하고, InGame에서 필요한 몬스터/적/스킬 데이터를 조회한다. 전투 중 체력, 쿨다운, 위치, 상태이상 인스턴스 같은 런타임 상태를 소유하지 않는다.
유닛 모델 UnitRuntimeModel, UnitIdentity, UnitStatsRuntime, UnitResourceRuntime, UnitStateBucket 아군/적/소환체의 런타임 ID, 스탯, HP/쉴드, learned state, 자동 전투 플래그를 소유한다. Unity 렌더링 컴포넌트나 프리팹 생성 정책을 직접 소유하지 않는다.
유닛 뷰/액터 MonsterUnitActor, EnemyUnitActor, 제안 CombatActorView 모델을 Unity 오브젝트, SpriteRenderer, 애니메이션, 위치, HP 표시로 반영한다. 피해 공식, 스킬 쿨다운, learned choice 판정을 직접 소유하지 않는다.
스킬 데이터 SkillData, ProjectileSkillData, BeamSkillData, ZoneSkillData, BuffSkillData, ShieldSkillData, PassiveSkillData 스킬의 정적 설정, 타이밍, 타겟팅, 데미지 계수, 프리팹 참조, 선택지 데이터를 가진다. 쿨다운 잔여시간, 현재 탄창, 이번 전투 중 히트 수 같은 실행 인스턴스 상태를 소유하지 않는다.
스킬 런타임 제안 SkillRuntimeInstance, 제안 SkillRuntimeSet 스킬별 쿨다운, 재장전, 지속시간, 내부 쿨다운, 현재 탄창, 예약 발사 같은 전투 중 상태를 소유한다. 데이터 원본이나 프리팹 표시 방식을 소유하지 않는다.
스킬 실행 제안 SkillExecutorRegistry, 제안 ProjectileSkillExecutor, ShieldSkillExecutor, ZoneSkillExecutor 등 SkillData 타입별로 실행 방식을 선택하고, 대상/피해/상태/투사체 서비스에 요청을 보낸다. 전체 전투 상태 리스트를 직접 순회하거나 RunSession을 직접 수정하지 않는다.
전투 서비스 제안 TargetQueryService, DamageService, StatusEffectService, ShieldService 공통 대상 탐색, 피해 계산/적용, 상태이상/쉴드 적용, 임시 효과 갱신을 담당한다. 스킬별 고유 선택지 데이터나 UI 패널 상태를 소유하지 않는다.
시뮬레이션 제안 ProjectileSimulation, SkillEffectSimulation, SpawnSimulation 투사체 이동/충돌/수명, 장판/빔/소환 이펙트 수명, 적 스폰 주기를 처리한다. 스킬 데이터 변환이나 Run 보상 상태를 소유하지 않는다.
프리팹/에셋 Assets/Prefab/Monster, Assets/Prefab/Enemy, Assets/Prefab/Skill, Assets/SO 유닛/적/스킬 시각 프리팹과 향후 ScriptableObject 데이터를 보관한다. 프리팹 자체가 전투 판정의 최종 소유자가 되지 않는다.

4. 클래스 참조 방향

허용되는 큰 방향

  • InGameCombatManager는 서비스와 모델을 만든다.
  • 서비스는 UnitRuntimeModel, SkillRuntimeInstance, SkillData를 읽고 변경한다.
  • 액터는 모델을 참조해서 화면에 표시한다.
  • 스킬 실행기는 TargetQueryService와 DamageService 같은 좁은 서비스만 참조한다.
  • Run 계층은 전투 입력과 결과만 주고받는다.

피해야 할 방향

  • SkillData가 직접 씬 오브젝트를 찾거나 전투 상태를 바꾸면 안 된다.
  • MonsterUnitActor가 직접 RunSession을 수정하면 안 된다.
  • 개별 스킬 실행기가 모든 유닛 리스트를 직접 소유하면 안 된다.
  • RunCombatUiController가 최소 전투 루프 이전에 InGame 내부 서비스에 직접 붙으면 안 된다.

참조 관계 표

클래스/모듈 참조 대상 참조 목적 현재 구현 상태

InGameContextManager MonsterDefinition, RunSession, GameDataCatalog, 스폰 포인트 전투 시작 입력과 씬 앵커를 하나의 컨텍스트로 전달한다. 현재 존재필드 없음

5. 인게임 구성 요소별 동작

5.1 아군 몬스터 1P / 2P-5P

완성 구조에서 1P 선택 몬스터와 2P-5P Manifested 몬스터는 같은 MonsterUnitActor와 같은 UnitRuntimeModel 구조를 사용한다. 차이는 UnitIdentity.SlotIndex와 RunSession.RunMonsterState에 연결되는 learned state다.

  • 1PSpawnPoint는 선택 몬스터의 스폰 위치다.
  • 2PSpawnPoint부터 5PSpawnPoint는 manifested party의 스폰 위치다.
  • 각 유닛은 UnitStateBucket.LearnedActiveSkillIds, LearnedPassiveSkillIds, ChosenChoiceIds를 가진다.
  • 자동 공격/자동 스킬은 AutoAttackEnabled, AutoSkillEnabled가 켜져 있을 때만 실행된다.

5.2 적과 넥서스

적은 EnemyDefinition에서 EnemyUnitActor와 UnitRuntimeModel로 생성된다. Nexus는 보드상 넥서스 구조물로 기록되어 있으므로, 완성 단계에서는 유닛과 같은 대상 인터페이스를 가진 별도 목표 모델로 다루는 것이 맞다.

  • 적 스폰 정책은 제안 SpawnSimulation이 담당한다.
  • 적의 이동/공격 대상은 TargetQueryService가 제공한다.
  • 넥서스 HP/피해 판정은 제안 NexusTargetModel 또는 ICombatTarget 구현체가 담당한다.

5.3 스킬

스킬은 데이터, 런타임 상태, 실행기, 시각 표현으로 나뉜다. 현재 SkillData 계열은 데이터 구조만 가지고 있고, 실행기는 아직 없다. 완성 구조에서는 같은 스킬 데이터가 1P와 2P-5P 모두에서 재사용된다.

스킬 계층 담당 클래스 설명
정적 데이터 SkillData 및 하위 클래스 쿨다운 기준값, 범위, 반경, 데미지 계수, 상태 ID, 프리팹 참조, 선택지를 보관한다.
런타임 상태 제안 SkillRuntimeInstance 남은 쿨다운, 탄창, 재장전, 지속 시간, 내부 쿨다운을 보관한다.
실행 선택 제안 SkillExecutorRegistry 스킬 데이터 타입에 따라 projectile, beam, zone, buff, shield, passive executor를 호출한다.
판정 요청 제안 executor들 대상 탐색, 피해 적용, 상태 적용, 투사체 생성, 장판 생성 요청을 서비스로 보낸다.
표현 SkillEffectPrefab, 제안 visual/effect actor 프리팹은 시각 표현을 담당하고, 스킬 판정 로직의 소유자가 되지 않는다.

6. 완성 단계별 구조 변화

Phase 완성 후 추가/안정화되는 구조 인게임에서 보이는 변화
Phase1-D 제안 InGameSkillDataValidator가 중복 ID, 빈 ID, 슬롯/캐릭터 불일치, 필수 대상값 누락을 잡는다. 잘못된 스킬 데이터가 실행기로 들어가기 전에 차단된다.
Phase2-A/B/C UnitFactory, MonsterUnitActor, EnemyUnitActor, 씬 부트스트랩이 실제 모델/액터 바인딩을 수행한다. NewRunScene에서 1P 몬스터와 테스트 적이 스폰된다.
Phase3 TargetQueryService, DamageService, StatusEffectService, ShieldService가 만들어진다. 스킬 실행기가 직접 대상 목록을 뒤지지 않고 공통 판정 서비스를 사용한다.
Phase4 SkillRuntimeInstance, SkillExecutorRegistry, 최소 executor가 동작한다. eve-a 투사체와 ariel-b 쉴드 같은 최소 샘플 스킬이 InGame 구조에서 실행된다.
Phase5 learned choice 조회와 자동 공격/자동 스킬 조건이 유닛 상태와 연결된다. 1P와 manifested 몬스터가 같은 규칙으로 배운 스킬을 자동 사용한다.
Phase6 기존 Run/Data 흐름과 InGame 컨텍스트가 안정적으로 연결된다. MainMenu 선택, RunSession, Manifested party 상태가 InGame 전투 입력으로 들어온다.
Phase7 전체 5명 x 10개 스킬 데이터가 검증된 규칙으로 확장되고, Rin-D/Vega-E 같은 예외는 custom executor로 분리된다. 대부분의 스킬은 데이터/공통 executor로 실행되고, 예외만 별도 코드로 처리된다.
Phase8 Run UI Flow와 NewRunScene의 최종 교체 경로가 연결된다. 기존 전투 대신 InGame이 실제 인게임 전투 루프로 쓰인다.

7. 최소 최종 파일 구조 제안

폴더 클래스 상태 책임
Core InGameCombatManager, InGameContextManager, InGameResultManager, 제안 InGameSceneBootstrap 일부 현재 존재 전투 시작/종료, 씬 입력, 결과 전달
Units UnitRuntimeModel, UnitFactory, UnitRosterService, MonsterUnitActor, EnemyUnitActor 현재 존재, 일부 빈 셸 유닛 모델 생성과 액터 바인딩
Skills/Data SkillData 계열, InGameSkillCatalog, InGameSkillDefinitionMapper 현재 존재 스킬 데이터와 기존 데이터 호환 브리지
Skills/Runtime 제안 SkillRuntimeInstance, SkillRuntimeSet 현재 없음 쿨다운/탄창/지속시간 상태
Skills/Executors 제안 SkillExecutorRegistry, 타입별 executor, custom executor 현재 없음 스킬 타입별 실행
Services 제안 TargetQueryService, DamageService, StatusEffectService, ShieldService 현재 없음 전투 공통 판정
Simulation 제안 ProjectileSimulation, SkillEffectSimulation, SpawnSimulation 현재 없음 전장 오브젝트 생명주기
Validation 또는 Editor 제안 InGameSkillDataValidator 현재 없음 데이터 품질 검증

8. 검증 기준

  • 기존 CSV/Data 로딩을 중복 구현하지 않고 PakuriCsvRuntimeData, GameDataCatalog, PakuriDataManager 흐름을 재사용한다.
  • InGameCombatManager가 전투 오케스트레이션만 담당하고 개별 스킬 공식이 들어가지 않는다.
  • 1P와 2P-5P는 같은 MonsterUnitActor / UnitRuntimeModel 경로를 쓴다.
  • 스킬 데이터, 스킬 런타임 상태, 스킬 실행기, 시각 프리팹 책임이 분리된다.
  • 피해/쉴드/상태이상은 공통 서비스에서 처리되어 몬스터/적/넥서스 대상에 같은 규칙으로 적용된다.
  • Run UI 통합은 최소 전투 루프가 안정화된 뒤 Phase8에서 연결한다.
  • Unity Play Mode gameplay 검증은 사용자 소유이고, Code Builder는 빌드/컴파일/Unity-MCP 콘솔 근거를 남긴다.
