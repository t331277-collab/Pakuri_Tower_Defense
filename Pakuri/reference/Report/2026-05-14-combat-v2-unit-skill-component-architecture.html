Designer Report / Proposed Architecture

Combat V2 유닛 생성 관리와 스킬 구현 구조

이 문서는 새 Combat V2를 구현할 때 유닛 생성, 런타임 상태, 스킬 데이터, 스킬 실행기, 시각 프리팹을 어떻게 나눌지 정리한 설계 산출물이다. 여기서 제안하는 파일과 클래스는 아직 구현물이 아니라 proposed 구조다.

유닛 생성

UnitRuntimeModel이 전투 상태를 소유하고, MonsterUnitActor / EnemyUnitActor는 표시와 씬 연결만 맡는다.

스킬 구현

skill-class-design.md의 SkillData 계층을 스킬 데이터 스키마 기준으로 삼되, 기존 SkillDefinition 호환 어댑터를 먼저 둔다.

관리 원칙

수치와 조건은 데이터, 현재 쿨다운/탄창은 런타임, 실제 판정은 executor, 이펙트 외형은 prefab/presenter가 소유한다.

3. 유닛 생성 관리 다이어그램

Run 입력

MonsterDefinition, RunSession, GameDataCatalog를 기존 흐름에서 받는다.

CombatV2Controller

전투 하루치 컨텍스트를 만들고 유닛/스폰/스킬 시스템 초기화를 지시한다.

UnitFactory

선택 1P, 현현 2P-5P, 적 정의를 UnitRuntimeModel로 변환한다.

Actor Binding

MonsterUnitActor 또는 EnemyUnitActor 프리팹을 생성하고 모델에 연결한다.

Roster / Registry

UnitRosterService와 CombatTargetRegistry가 대상 조회와 생존 상태를 관리한다.

유닛 책임 경계

컴포넌트 소유한다 소유하지 않는다
UnitRuntimeModel HP, 실드, 스탯, 방어, auto attack 토글, learned state 참조, 상태효과 컨트롤러, 스킬 런타임 목록 SpriteRenderer, Animator, Collider, Unity Transform 직접 조작
MonsterUnitActor 1P와 현현 몬스터 공통 프리팹 표시, 위치, 애니메이션 브리지, 피격/상태 표시 연결 스킬 수치, 강화 판정, HP 계산, 고유 캐릭터 로직
EnemyUnitActor 적 프리팹 표시, 이동 표현, 피격 표시, 사망 연출 연결 AI 판단, 피해 공식, 스폰 정책
UnitFactory 데이터 정의와 RunSession 상태를 읽어 모델/Actor를 생성하고 바인딩 전투 tick 실행, 스킬 판정, UI 보상 처리
UnitRosterService 아군/적 목록, 1P/현현 슬롯, 생존 유닛 조회 프리팹 Instantiate 세부 처리, 피해 계산

4. 스킬 구현 컴포넌트 다이어그램

Data Source

SkillDefinition / PassiveDefinition 또는 최종 SkillData SO.

SkillSpecAdapter

기존 데이터와 skill-class-design.md 스키마를 V2 실행용 spec으로 정규화한다.

SkillRuntimeInstance

쿨다운, 탄창, 재장전, 내부 쿨다운, 런타임 스택처럼 전투 중 변하는 값만 가진다.

SkillExecutor

타입별 공통 실행기가 타겟 조회, 피해 요청, 상태 요청, 프리젠테이션 요청을 발행한다.

CombatEventBus

OnCast, OnHit, OnKill, OnDamage, OnStatusStack 같은 이벤트를 기록한다.

PassiveTriggerSystem

PassiveSkillData.triggerType과 linkedSkillId를 해석한다.

Damage / Status / Shield

DamageResolver, StatusEffectController, ShieldController가 실제 적용을 담당한다.

Presentation

SkillEffectPrefab과 presenter는 외형만 담당하고 전투 공식은 소유하지 않는다.

스킬 데이터 계층 채택 방식

skill-class-design.md 기준 V2 실행 컴포넌트 관리 방식
ProjectileSkillData ProjectileSkillExecutor + ProjectileSimulation 탄창, 재장전, 투사체 수, 속도, 관통, on-hit 상태를 데이터로 관리한다.
BeamSkillData BeamSkillExecutor + tick query 지속시간, tick 간격, 폭, 상태 적용 확률을 데이터로 관리한다.
ZoneSkillData ZoneSkillExecutor + ZoneSimulation 장판 반경, 전체 필드 여부, tick 피해, 아군 부가효과를 데이터로 관리한다.
BuffSkillData BuffSkillExecutor + ModifierAggregator 행동속도, 공격력, 태그, 동반 피해 같은 효과를 modifier/effect request로 바꾼다.
ShieldSkillData ShieldSkillExecutor + ShieldController Replace, TakeHighest, Stack 갱신 규칙을 shield 시스템에서 처리한다.
PassiveSkillData PassiveTriggerSystem + CombatEventBus 상시 효과는 전투 시작 1회 적용, 이벤트 기반 효과는 이벤트 버스에서 조건을 확인한다.
Rin-D / Vega-E 예외 CustomSkillExecutor 공통 데이터로 표현하기 어려운 처형 조건만 별도 코드로 격리한다.

5. 스킬 3중 구현 방지 규칙

SkillData, SkillExecutor, SkillEffectPrefab 세 가지가 존재해도 이것은 3중 구현이 아니다. 다만 같은 수치와 조건을 세 곳에 중복하면 3중 구현이 된다.

데이터가 소유

피해 계수, 쿨다운, 반경, 지속시간, tick 간격, 상태 태그, shield 갱신 규칙, linked skill ID.

런타임이 소유

현재 HP, 현재 실드, 남은 쿨다운, 남은 탄창, 내부 쿨다운, 현재 상태 스택, learned choice 조회 결과.

프리젠테이션이 소유

prefab, sprite, animation trigger, line/circle/zone 표시, projectile 외형, popup 위치.

금지할 구현 패턴

  • SkillEffectPrefab에 피해량, tick 간격, 상태 확률을 넣지 않는다.
  • MonsterUnitActor나 EnemyUnitActor가 스킬 공식이나 강화 판정을 직접 소유하지 않는다.
  • 일반 스킬을 EveBExecutor, SeinDExecutor처럼 스킬 ID별 클래스로 먼저 만들지 않는다.
  • 강화 선택을 executor 내부의 문자열 분기만으로 계속 추가하지 않는다. 기본값은 SkillChoiceEffectSpec로 해석한다.

허용할 예외

  • 문서가 이미 예외로 둔 Rin-D, Vega-E 처형 로직은 CustomSkillExecutor로 격리할 수 있다.
  • 공통 executor와 effect spec으로 표현하면 오히려 더 복잡해지는 보스/특수 스킬은 별도 executor를 허용한다.
  • 단, 예외 executor도 damage/status/shield/presentation 직접 적용은 하지 않고 request API를 사용한다.

6. 실행 순서

  1. CombatV2Controller.BeginConfiguredDay(...)가 기존 Run 입력을 받는다.
  2. SkillSpecAdapter가 기존 SkillDefinition / PassiveDefinition을 V2 실행 spec으로 변환한다.
  3. UnitFactory가 1P와 현현 몬스터의 UnitRuntimeModel을 생성하고 같은 MonsterUnitActor 계열에 바인딩한다.
  4. SpawnManagerV2가 적 스폰 규칙에 따라 EnemyUnitActor와 적 모델을 생성한다.
  5. 전투 tick은 상태효과 tick, passive event 처리, auto attack/auto skill 판단, skill executor 실행, projectile/zone/summon simulation, damage/status/shield resolve, death/reward 판정 순서로 실행한다.
  6. 전투 결과는 UI에 직접 쓰지 않고 CombatResultModel로 반환한다.

7. 구현 단계 제안

단계 내용 완료 기준
1. 계약 / 모델 CombatV2Controller, CombatV2Context, UnitRuntimeModel, CombatResultModel 골격 기존 Run 입력을 받을 수 있고 UI 연결 없이 최소 전투 컨텍스트를 생성한다.
2. 유닛 생성 UnitFactory, MonsterUnitActor, EnemyUnitActor, UnitRosterService 1P 1명과 적 1종을 새 씬에서 생성하고 모델/Actor 바인딩을 확인한다.
3. 스킬 기반 SkillSpecAdapter, SkillRuntimeInstance, ProjectileSkillExecutor 기존 SkillDefinition 데이터를 읽어 기본 자동 공격을 실행한다.
4. 상태 / 쉴드 StatusEffectData, StatusEffectController, ShieldController, ModifierAggregator 상태와 쉴드가 1P/현현/적 중 두 종류 이상에 같은 API로 적용된다.
5. 스킬 다양화 Beam, Zone, Buff, Shield executor 추가 공통 executor 추가만으로 여러 스킬이 실행되고 prefab은 표시만 담당한다.
6. 패시브 PassiveSkillData, CombatEventBus, PassiveTriggerSystem Always, OnTargetStatus, DuringBuff, AfterSkill, OnEvent가 각각 최소 1개 케이스로 검증된다.
7. 예외 스킬 Rin-D, Vega-E, Rin-F 이중 패시브, name_mark 소모 같은 고급 케이스 예외 로직이 공통 damage/status/shield/presentation API를 우회하지 않는다.
8. UI 연결 기존 UI 어댑터 또는 RunCombatUiControllerV2 새 전투가 독립 검증된 뒤 Run UI Flow에 연결된다.

8. 수용 기준

  • 새 Combat V2는 기존 MonsterDefinition, EnemyDefinition, SkillDefinition, PassiveDefinition, RunSession을 읽을 수 있어야 한다.
  • 1P와 현현 몬스터는 같은 MonsterUnitActor 계열과 같은 스킬 실행 경로를 사용해야 한다.
  • 스킬 수치 변경은 기본적으로 데이터 변경으로 가능해야 하며, 일반 스킬마다 새 C# executor를 만들지 않아야 한다.
  • SkillEffectPrefab은 표시 리소스이며 전투 공식의 소유자가 아니어야 한다.
  • 패시브는 PassiveSkillData와 이벤트 기반 시스템으로 처리하고, linkedSkillId는 기존 액티브 스킬 데이터를 재사용해야 한다.
  • Rin-D / Vega-E 같은 예외 스킬은 명시적 예외 executor로 격리하고 공통 request API를 통해 피해와 상태를 적용해야 한다.
  • UI 연결은 새 전투 loop가 독립적으로 유닛 생성, 자동 공격, 피해, 승패 판정을 수행한 뒤 진행해야 한다.
