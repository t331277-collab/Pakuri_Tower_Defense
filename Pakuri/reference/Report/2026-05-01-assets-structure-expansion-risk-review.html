Pakuri Assets 구조 확장 리스크 리뷰

이 보고서는 실제 스크립트와 ScriptableObject 자산에서 확인한 저장소 근거만 사용해 현재 Pakuri/Assets 구조의 확장 병목을 정리한다. 존재하지 않는 시스템, 숨은 헬퍼, 문서화되지 않은 컨텐츠 파이프라인은 가정하지 않았다.

1. 검토 범위

검토 범위는 Pakuri/Assets/Scripts, Pakuri/Assets/Data/GameData, Pakuri/data, Pakuri/reference/2.Monster와 이를 연결하는 PakuriGameDataSeeder.cs 하위 실제 파일이다. 여기에는 GameDataCatalog.asset, 몬스터 자산 5개, 적 자산 8개도 포함된다.

주요 코드 근거

  • Data/GameDataCatalog.cs는 Monsters와 StageOneEnemies만 가진다.
  • Combat/CombatRuntimeEnemies.cs는 Stage 1 적 풀과 fallback 적 생성을 직접 가진다.
  • Run/RunSession.cs는 배운 스킬 상태를 문자열로 저장한다.
  • Combat/CombatRuntimeProjectiles.cs는 선택 몬스터 타입에 따라 분기한다.
  • Data/Editor/PakuriGameDataSeeder.cs는 Stage 1 적 일부를 코드로 만들고, 몬스터 스킬은 reference/2.Monster markdown에서 읽는다.

주요 자산 근거

  • 실제 존재하는 몬스터 자산은 Ariel, Eve, Rin, Sein, Vega 총 5개다.
  • 실제 존재하는 Stage 1 적 자산은 총 8개다.
  • rin.asset과 sein.asset은 UnitSprite, ProjectileSprite가 비어 있다.
  • 많은 스킬 슬롯의 SkillIcon, SkillEffectPrefab 참조가 null 상태다.
  • Pakuri/data/skills.csv는 현재 SKILL_001~003만 가지지만, levelup_choices.csv와 skill_branches.csv는 SKILL_004~006을 참조한다.

2. 전체 판단

현재 구조는 "SO를 더 추가하면 컨텐츠가 자동으로 확장되는 구조"에 가깝지 않다. 새 컨텐츠를 넣을 때 ScriptableObject 자산뿐 아니라 전투 런타임 분기, Run 상태 로직, 보상 또는 UI 흐름까지 함께 수정할 가능성이 높다.

또한 문제의 축이 SO 스키마만은 아니다. 실제 데이터 원본이 csv + markdown + seeder 하드코딩 + 최종 asset으로 나뉘어 있어 어떤 파일을 진실원본으로 보고 수정해야 하는지가 한 번에 드러나지 않는다.

실제 코드 기준으로 가장 큰 병목은 원본 데이터 경로의 분산, Stage 1 전용 적 구조, 몬스터별 하드코드 전투 분기, 그리고 DisplayName 기반 Run 상태 저장이다.

3. 데이터 파이프라인 관점의 추가 리스크

원본 경로가 여러 갈래다

  • Pakuri/data/*.csv에는 스킬/선택지/웨이브 CSV가 실제 존재한다.
  • Pakuri/reference/2.Monster/.../*.md는 몬스터 A~J 스킬 문서 원본으로 쓰인다.
  • PakuriGameDataSeeder.cs는 에디터 메뉴에서 자산을 생성하며 Stage 1 적 일부를 코드에 직접 가진다.
  • 런타임은 최종적으로 GameDataCatalog, MonsterDefinition, EnemyDefinition 자산만 읽는다.

즉 현재는 "원본 데이터 하나를 변환해 자산을 만든다"보다, 여러 원본 후보를 사람이 구분해 동기화해야 하는 구조에 가깝다.

검증보다 변환이 더 강하다

  • GetSkillDocumentPaths()는 문서 폴더나 문서가 없을 때 Debug.LogWarning만 남긴다.
  • ParseFirstFloat()는 숫자를 읽지 못하면 0f를 반환한다.
  • ParseAttribute()는 속성 매칭 실패 시 DamageAttribute.Physical로 돌아간다.
  • 현재 CSV도 이미 skills.csv와 levelup_choices.csv/skill_branches.csv 사이에 참조 불일치가 있다.

초기 프로토타입 단계에서는 유연할 수 있지만, 컨텐츠가 늘어날수록 데이터 오류가 늦게 발견될 가능성을 키운다.

왜 확장 비용을 더 키우는가

실제 런타임은 이미 RunFlowController, DebugSceneController, CombatRuntimeController가 GameDataCatalog를 직렬화 참조하는 구조다. 동시에 PakuriGameDataSeeder.cs는 현재 826줄이며, Application.dataPath/../reference/2.Monster 경로에서 문서를 읽고, Stage 1 적 정의 일부는 코드 내부에서 직접 생성한다.

그래서 신규 컨텐츠 추가 비용은 자산 작성만의 문제가 아니라, 원본 위치 판별, 변환 경로 추적, 생성 결과 확인까지 함께 커지는 방향으로 누적된다.

4. 주요 리스크

리스크 근거 확장 영향 우선도
원본 데이터 경로 분산과 Seeder 집중 PakuriGameDataSeeder.cs는 현재 826줄이며, Application.dataPath/../reference/2.Monster에서 스킬 문서를 읽고, CreateOrUpdateStageOneEnemies()에서 Stage 1 적 일부를 코드로 직접 만든다. 런타임은 최종적으로 GameDataCatalog 중심으로 소비된다. 신규 컨텐츠를 추가할 때 CSV, markdown, seeder 코드, 최종 asset 중 어디를 먼저 수정해야 하는지 즉시 드러나지 않으며, 동기화 실수 가능성이 커진다. 높음
약한 import 검증과 무결성 누수 GetSkillDocumentPaths()는 누락 시 warning만 남기고, ParseFirstFloat()는 실패 시 0f, ParseAttribute()는 실패 시 Physical을 반환한다. 현재 CSV도 skills.csv의 SKILL_001~003와 별개로 levelup_choices.csv, skill_branches.csv가 SKILL_004~006을 참조한다. 데이터 누락이나 참조 오탈자가 import 단계에서 강하게 차단되지 않으면, 잘못된 기본값이나 부분 생성 자산이 QA 이후에야 드러날 가능성이 높다. 높음
Stage 1 전용 스테이지 및 적 구조 GameDataCatalog.cs는 StageOneEnemies만 노출한다. EnemyDefinition.cs는 StageOneEnemySkillKind를 사용한다. CombatRuntimeEnemies.cs는 Stage 1 적 풀 해석과 fallback Stage 1 적 생성을 직접 가진다. 새 챕터, 새 적군 계열, 다른 보스 규칙을 추가할 때 자산 추가만으로는 부족하고 스키마와 런타임 변경이 함께 필요해질 가능성이 높다. 높음
몬스터별 하드코드 전투 분기 CombatRuntimeProjectiles.cs는 Eve와 Ariel을 직접 분기한다. CombatRuntimeEveSkills.cs와 CombatRuntimeArielSkills.cs는 몬스터 전용 런타임 로직을 각각 가진다. 새 몬스터나 새 스킬 계열은 SO 작성만으로 동작하기 어렵고, 추가 런타임 분기 파일이 계속 필요해질 가능성이 높다. 높음
DisplayName 문자열 기반 Run 상태 연결 RunSession.cs, RunCombatUiController.cs, DebugSceneController.cs, 전투 스킬 로직 일부가 배운 스킬 상태 판정을 표시 이름 문자열로 처리한다. 스킬 이름 변경, 현지화, 표기 수정이 저장 데이터 또는 해금 판정을 깨뜨릴 수 있다. 확장 관점에서는 안정적인 내부 ID 경로가 더 안전하다. 높음
SO 내부의 중복된 기준 데이터 MonsterDefinition.cs는 BaseStats와 별도 전투 튜닝 필드를 함께 가진다. CombatRuntimeScene.cs는 주로 top-level 전투 튜닝 필드를 소비한다. 동일 몬스터에 여러 기준 스탯 원본이 생겨 밸런스 튜닝 드리프트가 발생하기 쉬워진다. 중간
프로토타입 성격이 강한 보상 및 진행 규칙 RunDayModel.cs는 stage/day 범위를 고정한다. CombatRuntimeRewards.cs는 하드코드 보상 값과 보상 흐름 가정을 직접 가진다. Shop, Elite, 이벤트 노드, 스테이지별 보상 테이블이 늘어날수록 데이터 확장보다 런타임 조건 분기가 먼저 커질 수 있다. 중간
코드와 강하게 결합된 UI 및 authoring 파이프라인 실제 자산 검색 기준 Pakuri/Assets 하위에는 *.prefab, *.uxml, *.uss가 없다. 현재 메뉴, Run, 디버그 UI는 코드에서 조립된다. 컨텐츠가 늘어날수록 UI 변경이 런타임 코드 수정과 함께 움직일 가능성이 높고, 자산 누락 검증도 계속 약할 수 있다. 중간

5. 자산 모델 메모

스킬 메타데이터 소비 불균형

SkillDefinition.cs에는 RuntimeKind, ImplementationState, StatusEffectId, SkillEffectPrefab 같은 필드가 있다. 실제 코드 사용 기준으로 이들 중 일부는 런타임 소비 지점이 거의 없거나 없다.

자산 메타데이터가 풍부해 보여도 런타임 동작이 자동으로 따라오는 구조는 아니라는 뜻이다.

자산 완성도 편차

Ariel 자산은 구현 상태가 표시된 스킬이 상대적으로 많지만, Eve, Rin, Sein, Vega는 훨씬 제한적이다. 현재 자산 개수만으로 모든 몬스터가 동일한 준비 상태라고 볼 수는 없다.

6. 신규 컨텐츠 추가 시 예상 수정 범위

  • 새 데이터셋 또는 새 저작 규칙은 CSV, markdown, seeder, asset 중 무엇이 진실원본인지부터 정리해야 할 가능성이 높다.
  • 새 스테이지는 카탈로그 모델, 적 정의 모델, 적 생성 런타임, 보상 로직을 함께 건드릴 가능성이 높다.
  • 새 몬스터는 SO 작성 외에도 투사체 또는 스킬 런타임 분기, UI 또는 해금 판정을 함께 수정할 가능성이 높다.
  • 새 보상 타입은 RunDayModel, CombatRuntimeRewards, 보상 표시 코드를 함께 수정할 가능성이 높다.
  • 이름 변경이나 현지화는 현재 표시 문자열 기반 연결 때문에 배운 스킬 상태에 직접 영향을 줄 수 있다.

7. 우선순위 제안

우선 1

원본 데이터의 단일 진실원본을 먼저 정하고, import 단계에서 누락과 참조 불일치를 강하게 차단하는 validation 계약을 세울 필요가 있다.

데이터 파이프라인

우선 2

적 데이터와 스테이지 데이터를 Stage 1 전용 명명과 런타임 가정에서 분리할 필요가 있다.

구조

우선 3

배운 스킬 상태 추적을 DisplayName 기반 문자열에서 안정적인 내부 ID 기반으로 바꿔야 한다.

데이터 안정성

우선 4

몬스터별 직접 분기를 줄이고, 보다 데이터 기반인 전투 런타임 진입 경로를 정의하는 편이 확장 비용을 낮춘다.

전투 런타임

8. 결론

현재 Pakuri 자산 구조는 프로토타입 단계에서는 실용적이지만, 새 스테이지, 새 적군 계열, 새 몬스터, 새 보상 타입이 계속 늘어나는 시점에는 데이터 확장보다 런타임 전용 분기 비용과 원본 데이터 추적 비용이 더 빠르게 커질 가능성이 높다.

저장소 근거 기준으로 가장 먼저 정리할 대상은 원본 데이터의 단일화와 import validation 계약 정리, Stage 1 전용 구조 가정 제거, DisplayName 기반 상태 연결 제거, 몬스터 전용 전투 분기 축소다.
