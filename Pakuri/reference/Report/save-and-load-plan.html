Pakuri SaveAndLoad 설계안

이 문서는 현재 작성된 Run 확장 설계안과 메타 성장 문서를 기준으로, Pakuri 프로토타입의 저장 / 불러오기 경계를 어디서 나눠야 하는지 정리한 설계 문서다. 핵심 판단은 저장 구조 설계는 지금, 실제 파일 저장 구현은 Run 상태 분리 이후다.

짧은 결론

SaveAndLoad는 지금 당장 데이터 구조를 설계해야 하지만, 실제 저장 파일 입출력은 RunSession과 메타 진행 상태가 분리된 뒤에 구현하는 것이 맞다.

이유는 현재 코드가 전투, 일차 진행, 보상, UI를 하나의 컨트롤러에 함께 들고 있고, 문서상으로는 이미 런 내부 상태와 런 외부 영구 상태가 분명히 갈라져 있기 때문이다.

추가로 정적 게임 데이터 로딩은 저장 파일과 별개로 다뤄야 한다. 현재 Pakuri/data의 CSV들은 빌드에 자동 포함되는 위치가 아니고, 프로젝트 안에 CSV 로더도 없다. 따라서 v1은 CSV 저작 원본 → 빌드용 런타임 자산 생성 → 게임 시작 시 그 자산 1회 로드 흐름으로 가는 것이 맞다.

현재 확인된 사실

  • 코드 현재 게임 전용 런타임 스크립트는 Assets/Scripts/Combat/DamageCalculator.cs, Assets/Scripts/Combat/EveVerticalSliceController.cs 중심이다.
  • 상태 결합 현재 EveVerticalSliceController는 일차 시작, 전투 판정, 포인터 입력, HUD, 보상 패널까지 함께 관리한다.
  • 런 문서 스테이지는 11일 단위이며, 일반 진행일에는 일반 전투 / 정예 전투 / 상점이 얽히고, 전투 진입 직후 이벤트 20%가 있다.
  • 보상 문서 골드는 런 내부 재화고 런 종료 시 사라지며, 어둠의 흔적은 런 외부 장기 성장 재화다.
  • 메타 문서 공통 스탯 강화와 액티브 강화는 캐릭터별 영구 진행으로 저장되어야 하고, 패시브는 메타에서 다루지 않는다.
  • 데이터 위치 현재 CSV는 Pakuri/data에 있고, Assets/Resources나 Assets/StreamingAssets는 아직 없다.
  • 데이터 규모 CSV 22개 전체 크기는 약 28KB 수준이다. 순수 용량만 보면 부트 로딩 화면이 필요한 수준은 아니다.

지금 바로 구현하면 위험한 이유

  • 경계 불명확 현재 구조에 저장을 바로 붙이면 Run 상태와 전투 UI 임시 상태가 한 파일에 섞일 가능성이 높다.
  • 재롤 위험 정예 전투 30%, 이벤트 20%, 포로 수 1~3명, 유물 3택1, 상점 하루 1회 같은 확률 결과를 저장하지 않으면 로드로 결과를 다시 굴리게 된다.
  • 메타 범위 미완료 메타 문서에는 캐릭터 해금, 난이도 해금, 시작 보너스가 아직 미작성이다. 따라서 영구 저장도 지금은 확정된 범위만 담아야 한다.
  • 데이터 파이프라인 부재 현재 CSV는 빌드 포함 위치 밖에 있고, 스크립트 검색 기준 CSV 로더 흔적도 없다. 즉 지금 상태로는 게임이 이 파일들을 직접 읽지 못한다.

저장 상태는 3층으로 나눈다

1. MetaSaveData 런 밖에서 유지되는 영구 상태다. 어둠 계열 재화, 캐릭터별 공통 스탯 강화, 캐릭터별 액티브 강화가 여기에 들어간다.
2. RunSnapshot 진행 중인 한 런의 체크포인트 상태다. 선택 몬스터, 현재 스테이지 / 일차, 런 내부 골드, 유물, 배운 스킬, 오늘의 고정된 선택 결과가 들어간다.
3. EphemeralRuntime 전투 프레임 중간 위치, 투사체 좌표, 임시 UI 열림 상태 같은 휘발성 상태다. v1에서는 저장 대상에서 제외한다.
4. SaveManifest 어떤 저장 파일이 최신인지, 어떤 슬롯이 진행 중인지, 스키마 버전이 무엇인지 관리하는 얇은 인덱스다. v1에서는 단일 활성 런 슬롯만 두는 것이 안전하다.

방향 메타 저장은 문서가 이미 확정한 것만 담는다. 캐릭터 해금, 난이도 해금, 시작 보너스는 현재 문서가 미작성이라 v1 저장 구조에서 제외하거나 비어 있는 예약 섹션으로만 둔다.

MetaSaveData에 지금 넣지 않는 것

  • 미작성 문서 캐릭터 / 타워 해금
  • 미작성 문서 난이도 해금
  • 미작성 문서 시작 보너스
  • 제외 패시브 메타 성장 데이터

이 항목들은 메타 인덱스 문서에서 후속 결정으로 남아 있으므로, 지금 설계 단계에서 완성된 구조처럼 저장 필드를 강하게 박아두는 것은 근거 부족이다.

핵심 v1 Run 저장은 결과가 이미 굴려진 것을 다시 계산하지 않게 하는 쪽이 중요하다. 확률이 들어간 선택지는 seed만 저장하는 것보다, 현재 시점의 실제 결과를 저장하는 쪽이 프로토타입에서는 안전하다.

RunSnapshot에 바로 넣지 않는 것

  • v1 제외 전투 중 적 좌표
  • v1 제외 투사체 리스트와 이동 중간값
  • v1 제외 재장전 타이머 중간 프레임
  • v1 제외 현재 열린 UI 윈도우 픽셀 위치
  • v1 제외 이브 전용 컨트롤러 내부 임시 런타임 객체 참조

이 상태들은 현재 구조상 EphemeralRuntime에 가깝고, 지금 저장 대상으로 넣으면 전투 리팩터링 때 저장 포맷도 함께 깨질 확률이 높다.

v1 저장 시점

1. 메타 화면 종료 직후 메타 재화 사용, 스탯 강화, 액티브 강화, 초기화가 끝났을 때 MetaSaveData를 저장한다.
2. 몬스터 선택 확정 직후 새 런이 시작되고 선택 몬스터가 결정되면 첫 RunSnapshot을 만든다.
3. 일차 체크포인트 오늘의 선택지, 상점 등장일, 이벤트 결과, 보상 후보가 확정되는 시점마다 RunSnapshot을 갱신한다.
4. 보상 적용 직후 골드, 유물, 스킬 선택, 일차 이동이 반영된 뒤 다음 일차 시작 전에 다시 저장한다.

정적 게임 데이터 로딩 방향

구분 권장 위치 권장 처리
저작 원본 데이터 Pakuri/data/*.csv 디자이너 / 밸런싱 원본으로 유지한다. 런타임이 직접 읽지 않는다.
빌드용 런타임 데이터 Assets/DataGenerated/ 에디터 importer가 CSV를 검증하고 생성한 ScriptableObject 또는 단일 JSON/TextAsset 자산을 둔다.
게임 시작 시 로드 GameDataCatalog 1개 타이틀 진입 직후 또는 bootstrap 단계에서 1회 읽고 메모리에 유지한다.
저장 파일 PersistentData/*.json 정적 밸런스 수치 전체를 저장하지 않고, 선택 결과와 진행 상태만 저장한다.

핵심 게임은 CSV를 직접 파싱하는 대신, 사전에 검증된 런타임 자산을 읽어야 한다. 그렇게 해야 빌드 포함 경로, 참조 무결성, 저장 파일 버전 관리가 모두 단순해진다.

왜 이 방식이 맞는가

  • 근거 현재 CSV는 Assets 밖에 있다.
  • 근거 Resources, StreamingAssets 폴더도 아직 없다.
  • 근거 CSV 총량이 매우 작아 런타임 스트리밍 이점이 작다.
  • 근거 스킬 참조 일부가 비어 있어 import 시 검증 단계가 먼저 필요하다.

데이터 로딩 파이프라인

1. CSV authoring 디자이너가 Pakuri/data의 CSV를 수정한다. 여기에는 런타임 직접 접근을 기대하지 않는다.
2. Editor import 에디터 메뉴나 prebuild 단계에서 importer가 CSV를 읽고, ID 누락 / 참조 누락 / 중복 키를 검증한다.
3. Generated asset importer가 Assets/DataGenerated/ 아래에 GameDataCatalog.asset 또는 동등 자산을 생성한다.
4. Runtime boot load 게임 시작 시 저장 파일보다 먼저 런타임 데이터 자산을 1회 로드하고, 그 다음 MetaSaveData와 RunSnapshot를 읽는다.

게임 시작 시 로드 방식

  1. 부팅 초기에 GameDataCatalog를 동기 로드한다.
  2. 그 다음 MetaSaveData를 읽는다.
  3. 진행 중인 런이 있으면 RunSnapshot를 읽는다.
  4. 타이틀 화면 또는 Continue 진입 시 이미 정적 데이터는 메모리에 올라와 있어야 한다.

현재 데이터 크기 기준으로는 별도 Loading 화면보다 빠른 부트 로드가 더 자연스럽다. 화면이 필요해도 짧은 초기화 오버레이 정도면 충분하다.

지금 추천하지 않는 방식

  • 비권장 런타임이 Pakuri/data의 CSV를 직접 읽는 방식
  • 비권장 저장 파일 안에 정적 밸런스 표 전체를 함께 넣는 방식
  • 비권장 현재 규모에서 CSV를 위해 별도 장시간 Loading 화면을 두는 방식
  • 후속 고려 외부 패치 / 모드 지원 전까지 StreamingAssets 직접 파싱

v1에서 저장 금지 구간

  • 금지 전투 도중
  • 금지 투사체 이동 도중
  • 금지 적 스폰 웨이브가 진행 중인 프레임 사이
  • 금지 보상 선택 버튼을 누르는 중간 프레임

현재 문서 구조는 일차 단위 반복과 선택지 단위 진행을 정의하고 있다. 따라서 v1은 일차 경계 체크포인트형 저장으로 가는 것이 자연스럽다.

로드 흐름

  1. 앱 시작 시 MetaSaveData를 먼저 읽는다.
  2. 진행 중인 RunSnapshot가 있으면 Continue 버튼을 활성화한다.
  3. Continue 시 runPhase를 보고 적절한 패널로 복구한다.
  4. 전투 도중 저장은 없으므로, 로드 후에는 항상 안전한 패널 상태에서 재개한다.
  5. 런 종료 시 RunSnapshot는 삭제하거나 completed 상태로 닫는다.

권장 v1은 단일 활성 런 슬롯으로 시작한다. 다중 슬롯은 UI와 충돌 해결 비용이 커지므로 후속 확장으로 두는 편이 안전하다.

버전 관리 규칙

  • 필수 모든 저장 파일에 schemaVersion을 둔다.
  • 필수 최소한 saveCreatedAt, saveUpdatedAt를 둔다.
  • 권장 저장 시점의 앱 빌드 문자열을 보관한다.
  • 권장 로드 실패 시 기본값으로 조용히 넘기지 말고, 손상 감지 후 새 런 시작 또는 메타만 복구하도록 분기한다.

SaveAndLoad는 나중에 필드가 늘어날 가능성이 높다. 따라서 지금부터 버전 키를 넣지 않으면 이후 마이그레이션 비용이 커진다.

무결성 규칙

  • 필수 현재 일차의 확률 결과는 로드 시 재계산하지 않는다.
  • 필수 이미 제시된 유물 후보, 스킬 후보, 포로 보상은 동일하게 복구한다.
  • 필수 상점 등장일은 스테이지당 1회 고정 저장한다.
  • 필수 메타 재화와 런 내부 골드는 서로 다른 저장 경로에서 관리한다.

Designer 결정

  • 결정 SaveAndLoad는 MetaSaveData와 RunSnapshot을 별도 파일로 나눈다.
  • 결정 정적 게임 데이터는 저장 파일에 넣지 않고, 별도 GameDataCatalog로 부팅 시 1회 로드한다.
  • 결정 Pakuri/data는 저작 원본으로 유지하고, 런타임은 생성 자산만 읽는다.
  • 결정 프로토타입 v1은 일차 경계 체크포인트 저장만 지원한다.
  • 결정 전투 도중 저장은 지원하지 않는다.
  • 결정 메타 저장은 현재 문서로 확정된 재화 / 스탯 / 액티브 강화까지만 담는다.
  • 결정 확률 결과 재롤 방지를 위해, 현재 시점의 실제 후보와 결과를 저장한다.

Code Builder handoff 조건

  • 조건 먼저 RunSession과 RunFlowController가 생겨야 한다.
  • 조건 그 전에 또는 함께 CsvGameDataImporter와 GameDataCatalog 구조를 먼저 고정한다.
  • 조건 CSV importer는 참조 누락 시 생성 자산을 갱신하지 말고 오류를 내야 한다.
  • 조건 그 다음 MetaSaveData, RunSnapshot, SaveLoadService를 만든다.
  • 조건 저장 호출은 EveVerticalSliceController에 직접 박지 말고, 분리된 Run 상태 객체에서 하게 한다.
  • 조건 첫 구현은 메타 저장 + 단일 런 슬롯 + 체크포인트 저장까지만 한다.

한 줄 추천

SaveAndLoad는 지금 설계하지 않으면 늦고, 지금 바로 구현하면 이르다. 따라서 현재 단계에서는 정적 게임 데이터 / 메타 저장 / 런 저장 / 비저장 런타임 경계를 문서로 먼저 고정하고, 실제 구현은 GameDataCatalog 부팅 로드와 RunSession 분리 이후에 체크포인트 저장부터 시작하는 것이 가장 안전하다.
