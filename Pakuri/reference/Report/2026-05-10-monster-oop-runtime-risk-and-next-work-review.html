1. 결론

일부만 지금 권장

현재 플레이 검증과 소규모 밸런스 조정은 진행 가능하다. 다만 meta 전역 강화, 배치 시스템, 새 몬스터 추가를 본격화하기 전에는 수치 적용 계층과 배치 데이터화를 먼저 정리하는 것이 낫다.

2. 기존 리포트 이후 진행된 작업

2026-05-08 보고서 시점에는 Sein, Vega, Ariel의 unit executor가 남은 작업으로 보였지만, 현재 보드와 코드 기준으로는 세 몬스터 모두 manifested unit executor가 추가되어 있다.

Vega unit executor 있음 CombatRuntimeParty.cs:633에서 TryTickVegaUnitSkill 호출. 보드에는 CombatRuntimeVegaSkills.cs:139 dispatcher가 기록되어 있다.

3. 현재 구조가 잘 된 부분

  • CombatUnitRuntime가 MonsterDefinition, RunMonsterState, HP, 공격력, 주문력, 보호막, 몬스터별 지속 상태, List<CombatSkillRuntime>를 보유한다. 즉 2P~5P가 단순 복제 오브젝트가 아니라 전투 상태를 가진 유닛으로 바뀌었다.
  • CombatSkillRuntime가 스킬별 쿨다운, 탄창, 재장전, 발사 간격, Vega 예약 투사체 상태를 가진다. 스킬별 런타임 상태를 유닛 단위로 분리한 점은 향후 밸런스 조정에 유리하다.
  • RunSession.RunMonsterState는 몬스터별 LearnedActives, LearnedPassives, ChosenRewardIds, DamageMultiplier, MagazineBonus, ShotIntervalMultiplier, ReloadDurationMultiplier, MaxHealthBonus, StatusChanceBonus를 가진다. 수치 보상과 Offering 상태를 1P와 파티 멤버에 나눠 적용할 기반은 있다.
  • 이펙트는 SkillDefinition.SkillEffectPrefab와 CombatEffectFactory 경로가 생겼다. 프리팹 기반 이펙트를 붙이는 방향은 맞다.

4. 완전한 객체 지향 구조가 아닌 이유

근거 판단 리스크
CombatUnitRuntime.TickManifestedCombat는 결국 Owner.TickManifestedUnitSkill(this, ...)를 호출한다. 유닛이 실행 주체처럼 보이지만 실제 스킬 실행 책임은 중앙 컨트롤러 partial에 있다. 몬스터가 늘수록 CombatRuntimeController partial들이 계속 비대해진다.
CombatRuntimeParty.cs:611부터 Eve, Rin, Sein, Vega, Ariel 순서로 전용 tick을 직접 호출한다. 다형성 dispatch가 아니라 if-chain dispatcher다. 새 몬스터 추가 때 공통 dispatcher를 계속 수정해야 한다.
selectedUnitRuntime는 있지만 SyncSelectedUnitRuntimeStats에서 1P 전역 필드를 mirror한다. 1P는 아직 완전한 unit-owned 상태가 아니다. 1P와 2P~5P 사이의 보호막, 쿨다운, 패시브 차이가 다시 생길 수 있다.
ResolveManifestedSkillDamageMultiplier는 skill id 문자열로 여러 몬스터 보정을 한곳에서 처리한다. 이전 fallback 보정 로직이 남아 있다. 전용 unit executor와 fallback 보정이 중복 적용되거나 누락될 위험이 있다.
CombatUnitRuntime에 Rin, Sein, Ariel, Vega 상태 필드가 직접 추가되어 있다. 상태는 유닛으로 옮겨졌지만 몬스터별 상태 타입으로 분리되지는 않았다. 몬스터가 많아지면 공통 유닛 클래스가 모든 몬스터 전용 필드로 커진다.

5. 남은 작업을 지금 해야 하는지

작업 지금 필요성 이유
모든 몬스터 unit executor 추가 이미 주요 범위 완료 Eve/Rin/Sein/Vega/Ariel 모두 TickManifestedUnitSkill에서 전용 경로가 호출된다.
1P 선택 유닛 완전 unit-owned 전환 콘텐츠 확장 전 권장 지금 당장 소규모 밸런스에는 필수는 아니지만, 1P와 2P~5P 차이 버그를 줄이려면 필요하다.
몬스터별 skill executor 인터페이스 분리 새 몬스터 대량 추가 전 권장 현재는 중앙 dispatcher가 몬스터별 함수를 직접 안다. 새 몬스터가 늘면 구조 비용이 커진다.
배치/포메이션 데이터화 배치 변경 기능 전 필수 현재 2P~5P 슬롯 이름과 fallback 좌표가 CombatRuntimeParty에 하드코딩되어 있다.
meta 전역 강화 적용 계층 meta 구현 전 필수 현재 검색한 스크립트에는 명시적인 meta/global upgrade 계층이 확인되지 않았다. RunSession 수치 보정은 있지만 영구 전역 강화 시스템은 별도 설계가 필요하다.
이펙트 서비스 확장과 풀링 이펙트 양 증가 전 권장 CombatEffectFactory는 프리팹 생성 경로를 제공하지만 lifetime, pooling, 레이어 정책까지 독립 서비스화된 것은 아니다.

6. 향후 작업별 적용성 판단

6.1 수치 밸런스 조정

현재 구조에서 비교적 잘 된다. SkillDefinition, RunSession.RunMonsterState, CombatSkillRuntime가 있으므로 데미지, 쿨다운, 탄창, 재장전, 상태 확률 같은 수치는 조정 경로가 있다. 단, 일부 몬스터별 trait 계산이 코드 상수와 문자열 id 분기로 남아 있어, 대규모 밸런스 작업에서는 “데이터 수정만으로 끝나는 수치”와 “코드 수정이 필요한 trait”가 섞일 수 있다.

6.2 이펙트 적용

현재 구조에서 가능하다. SkillEffectPrefab 필드와 CombatEffectFactory가 있고, Eve/Rin/Sein/Vega/Ariel 스킬 경로에서 프리팹을 전달하는 코드가 확인된다. 다만 아직 모든 시각 효과의 생성, 지속시간, 정리, 풀링 정책이 하나의 effect service로 통합된 상태는 아니다. 이펙트 수가 많아지면 성능과 정리 누락 리스크가 생긴다.

6.3 meta 전역 강화

현재 구조만으로는 “일부 가능, 완전 적용은 별도 계층 필요”다. RunSession에는 전역처럼 보이는 보정 필드와 몬스터별 보정 필드가 있다. 하지만 실제 스크립트 검색에서 명시적인 meta 영구 강화 클래스나 전역 강화 resolver는 확인되지 않았다. meta를 넣을 때는 RunSession에 직접 계속 누적하기보다, 전투 시작 시 selected/party unit에 적용되는 CombatStatModifier 또는 유사한 resolver 계층을 두는 편이 안전하다.

6.4 몬스터 배치 변경

현재 구조에서 가장 약한 부분이다. 2P~5P 슬롯은 ManifestedMonsterSlotNames와 ResolveManifestedMonsterPosition의 하드코딩에 묶여 있다. 단순히 RunScene의 기존 슬롯 위치를 조금 바꾸는 것은 가능하지만, 전투 중 배치 변경, 포메이션 보너스, 드래그 재배치, 행/열 전술 같은 기능은 데이터 모델과 UI, 저장 구조가 추가되어야 한다.

7. 권장 의사결정

  1. 지금 당장 모든 구조 리팩터링을 계속 밀 필요는 없다. 최근 수정한 Ariel/Eve 보호막, Sein/Vega/Ariel unit executor는 먼저 Play Mode로 체감 검증하는 것이 맞다.
  2. 단, meta 전역 강화나 배치 변경을 곧 할 계획이면 그 전에 구조 작업을 멈추면 안 된다. 그 두 기능은 현재 구조의 약한 부분을 직접 건드린다.
  3. 다음 구조 작업 1순위는 “배치 데이터화” 또는 “전투 시작 stat modifier resolver”다. 둘 중 어떤 기능을 먼저 할지에 따라 순서가 갈린다.
  4. 새 몬스터를 추가하기 전에 monster skill executor 인터페이스를 분리하는 것이 좋다. 지금처럼 CombatRuntimeParty dispatcher에 몬스터 이름별 tick 함수를 계속 추가하면 확장 비용이 누적된다.
