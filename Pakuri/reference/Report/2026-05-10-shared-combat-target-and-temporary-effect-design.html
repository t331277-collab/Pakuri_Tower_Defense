Designer Report · 2026-05-10

공통 전투 대상 모델과 재사용 가능한 임시효과 설계안

현재 전투 코드는 선택 아군, 소환 아군, 적군이 서로 다른 상태 저장소를 사용한다. 그 결과 같은 의미의 임시효과를 양쪽에 공통 적용하기 어렵고, 구현이 누적될수록 아군용과 적군용 작업이 다시 분기된다. 이 문서는 inspected code 기준으로 왜 공통 전투 대상 모델이 필요한지, 왜 임시효과를 재사용 가능하게 만들어야 하는지, 그리고 현재 코드를 무리 없이 옮기는 단계별 방법이 무엇인지 정리한다.

1. 왜 공통 전투 대상 모델이 필요한가

현재 구조의 핵심 문제는 임시효과가 전투 대상에 붙는 것이 아니라, 전투 대상마다 다른 필드 집합에 흩어져 저장된다는 점이다.

선택 아군

선택 아군 상태는 CombatUnitRuntime에 완전히 수렴하지 않았다. 실제 HP, 기본 공격력, 주문력, 방어, 보호막의 일부가 아직도 CombatRuntimeController 필드에 있다.

  • CombatRuntimeController.cs:326-378가 unitCurrentHealth, selectedMonsterDefenses, unitMaxHealthConfigured, powerStatConfigured, baseDamageConfigured를 소유한다.
  • CombatRuntimeParty.cs:72-79는 위 컨트롤러 필드를 다시 selectedUnitRuntime로 미러링한다.
  • CombatRuntimeArielSkills.cs:21-28은 선택 아군 전용 축복/성역/보호막 타이머를 컨트롤러 partial 필드로 별도 유지한다.

소환 아군

소환 아군은 CombatUnitRuntime를 사용하지만, 선택 아군과 같은 의미의 효과를 항상 같은 경로로 처리하지 않는다.

  • CombatUnitRuntime.cs:25-46가 ShieldValue, ArielBlessingTimer, VegaExterminationPermitTimer, RinHowlingTimer 같은 필드를 가진다.
  • CombatUnitRuntime.cs:152-190이 위 타이머를 자체 감소시킨다.
  • CombatRuntimeArielSkills.cs:856-922는 선택 아군과 소환 아군 보호막을 각각 다른 필드 세트에 기록한다.

적군

적은 CombatUnitRuntime가 아니라 EnemyRuntime라는 private nested class로 관리된다. 즉 아군과 같은 런타임 타입 계층 자체가 없다.

  • CombatRuntimeController.cs:28-94가 EnemyRuntime를 정의한다.
  • EnemyRuntime는 DamageTakenMultiplier, AttackBuffMultiplier, MoveSpeedBuffMultiplier, ShockTimer, ChillTimer, FreezeTimer, VulnerableStacks를 직접 가진다.
  • CombatRuntimeEnemies.cs:725-766은 적 전용 타이머 감소와 만료 복구를 수행한다.

결과

같은 의미의 “임시 전투 효과”가 이미 세 갈래 저장소에 분산돼 있다. 이 상태에서는 효과를 추가할 때마다 “선택 아군용”, “소환 아군용”, “적군용”을 따로 생각하게 된다.

  • CombatRuntimeArielSkills.cs:1266-1279는 선택 Ariel 전용 행동속도 계산을 별도 함수로 둔다.
  • CombatRuntimeVegaSkills.cs:1329-1331는 소환 Vega 전용 행동속도 계산을 별도 함수로 둔다.
  • CombatRuntimeEnemies.cs:1197-1200는 적군의 이동/공격 버프를 또 다른 방식으로 기록한다.

2. 왜 임시효과를 재사용 가능하게 만들어야 하는가

영구 성장치와 전투 중 임시효과는 다르다. 이 문서의 대상은 "3초간 공격속도 20% 증가"처럼 수명과 적용 대상을 갖는 전투 중 효과다.

2-1. 지금은 같은 효과를 한 번 만들어 두 번 쓰기 어렵다

현재 선택 아군의 행동속도는 GetSelectedMonsterActionSpeedMultiplier()와 각 몬스터별 selected 함수에서 읽고, 소환 아군은 각 Get...UnitActionSpeedMultiplier(runtime)에서 읽으며, 적은 공통 행동속도 축이 아예 없다.

  • CombatRuntimeProjectiles.cs:516-529는 선택 아군 사격/재장전에 GetSelectedMonsterActionSpeedMultiplier()를 사용한다.
  • CombatRuntimeArielSkills.cs:1580-1584, CombatRuntimeVegaSkills.cs:1329-1331, CombatRuntimeRinSkills.cs:1848-1852는 소환 아군용 별도 action speed 함수를 둔다.
  • CombatRuntimeEnemies.cs:744는 적의 ActiveCooldownRemaining을 그냥 Time.deltaTime로 줄인다. 적용 가능한 공용 행동속도 계수가 아직 없다.

2-2. 지금은 공통 버프 객체가 아니라 직접 필드 수정이다

현재 효과는 대부분 스킬 함수가 대상 필드를 직접 수정하고, 별도 업데이트 루프가 타이머를 감소시키는 구조다. 이 방식은 단기 구현에는 빠르지만, 같은 효과를 양쪽에 공유하기 어렵다.

  • CombatRuntimeArielSkills.cs:824-922가 보호막을 selected/controller 필드와 manifested runtime 필드에 직접 쓴다.
  • CombatRuntimeEnemies.cs:1165-1200가 적 보호막/공격 버프/이동 버프를 적 필드에 직접 쓴다.
  • CombatRuntimeEveSkills.cs:1465-1495가 감전/추위/취약을 EnemyRuntime 필드에 직접 쓴다.

2-3. 재사용 가능 구조의 이점

이점 현재 구조의 문제 공용 임시효과 구조에서 얻는 것
확장성효과 추가 때마다 대상별 분기 구현이 필요하다.효과 정의 1개 + 적용 대상 선택만으로 재사용 가능하다.
일관성선택 아군, 소환 아군, 적군의 만료/중첩 규칙이 코드 위치마다 흩어진다.만료, 중첩, 갱신 규칙을 공용 효과 레이어에서 통일할 수 있다.
디버깅왜 속도가 빨라졌는지 한 눈에 보이지 않는다.대상의 active effects 목록만 보면 원인을 추적할 수 있다.
양산성비슷한 효과가 몬스터별 helper로 계속 복제된다.공용 effect spec만 추가하고 데이터만 바꾸는 방향으로 이동할 수 있다.

3. 어떻게 만들 수 있는가

아래 순서는 “처음부터 전부 갈아엎는” 방식이 아니라, 현재 코드를 유지하면서 공통 모델로 점진 이동하는 순서다. 특히 선택 아군의 controller-owned 상태를 먼저 공통 모델로 끌어내리는 것이 핵심이다.
Step 0

범위를 분리한다

먼저 영구 성장치와 전투 중 임시효과를 분리한다. 현재 세션/보상 누적치인 DamageMultiplier, MaxHealthBonus, StatusChanceBonus는 계속 RunSession 계층에 남긴다.

  • RunSession.cs:344-386는 세션/파티 멤버 누적 보상치를 관리한다.
  • CombatRuntimeScene.cs:227-232는 전투 시작 시 그 누적치를 현재 전투 설정에 반영한다.
Step 1

공통 전투 대상 모델을 순수 런타임 객체로 정의한다

proposed class CombatTargetModel
{
    string Id;
    CombatTargetSide Side;
    CombatTargetRole Role;
    CombatStatBlock BaseStats;
    AttributeDefenseSet BaseDefenses;
    CombatResourceState Resources;
    CombatModifierState Modifiers;
    List<TemporaryEffectInstance> ActiveEffects;
}

이 모델은 MonoBehaviour일 필요가 없다. 현재 적도 MonoBehaviour가 아니므로, pure runtime model이 양쪽을 묶기 쉽다.

Step 2

현재 세 가지 저장소를 공통 모델에 연결한다

  1. 선택 아군용 CombatTargetModel selectedTarget를 추가한다.
  2. unitCurrentHealth, unitMaxHealthConfigured, selectedMonsterDefenses, unitShieldValue 같은 값을 이 모델에 복제한다.
  3. selectedUnitRuntime는 시각/씬 표현체로만 남기고, 전투 상태의 owner는 점차 selectedTarget로 옮긴다.
  4. 소환 아군은 CombatUnitRuntime 내부에 CombatTargetModel Target 참조를 추가한다.
  5. 적은 EnemyRuntime 내부에 CombatTargetModel Target 참조를 추가한다.
Step 3

공통 전투 중 스탯 채널을 정한다

채널 현재 사용 근거 양측 공통화 이유
ActionSpeedMultiplier선택/소환 아군에 이미 존재, 적은 없음"3초간 공격속도 20% 증가"의 대표 채널
MoveSpeedMultiplier적은 MoveSpeedBuffMultiplier, 느려짐/빙결도 존재양측 공통 이동 버프/디버프 채널
DamageDealtMultiplier적은 DamageMultiplier, 아군은 스킬별 보정 다수공통 피해 증가 계층 필요
DamageTakenMultiplier적은 이미 존재피해감소/취약 같은 효과의 공통 채널
ShieldPool양측 모두 보호막 수치 존재별도 시스템 분리 후보
StatusApplicationChance아군 투사체/효과가 사용공통 상태이상 확률 버프용
Step 4

임시효과 객체를 만든다

proposed class TemporaryEffectInstance
{
    string EffectId;
    string SourceId;
    float RemainingDuration;
    StackingPolicy Stacking;
    List<StatModifier> Modifiers;
    List<EffectTag> Tags;
}
proposed class StatModifier
{
    CombatStatChannel Channel;
    ModifierOperation Operation;
    float Value;
}

"3초간 공격속도 20% 증가"는 RemainingDuration = 3f, Channel = ActionSpeedMultiplier, Operation = Multiply, Value = 1.2f로 표현된다.

Step 5

버프 적용 API를 공통화한다

  1. ApplyTemporaryEffect(CombatTargetModel target, TemporaryEffectInstance effect)
  2. 필요한 경우에만 별도 시스템 트리거: 예를 들어 GrantShield(target, amount, duration)

즉 “효과가 단독으로 끝나는 경우”와 “효과가 다른 시스템을 깨우는 경우”를 동시에 지원한다. shield 분리 방향은 여기서 자연스럽게 들어간다.

Step 6

Shield는 공통 시스템으로 따로 뺀다

  • CombatRuntimeProjectiles.cs:427-490는 선택/소환 아군 피해 흡수 로직을 별도로 가진다.
  • CombatRuntimeProjectiles.cs:399-425는 적 보호막 흡수 로직을 또 별도로 가진다.
  • CombatRuntimeArielSkills.cs:924-984는 Ariel 계열 보호막 흡수 후속 로직을 가진다.

첫 단계에서는 CombatTargetModel.Resources.Shield만 공통화하고, 이후 필요 시 shield stack, source, reactive hooks를 확장한다.

Step 7

읽기 지점을 공통 채널로 바꾼다

  1. 선택 아군: CombatRuntimeProjectiles.cs:516-529의 action speed 계산을 selectedTarget.Modifiers.ActionSpeedMultiplier로 교체한다.
  2. 소환 아군: Get...UnitActionSpeedMultiplier(runtime) 계열을 공통 modifier read + 캐릭터 고유 보정으로 분리한다.
  3. 적군: ActiveCooldownRemaining, 이동, 공격 계산에 공통 modifier를 읽게 만든다.
Step 8

첫 마이그레이션 대상은 공통성이 높은 효과부터 고른다

  1. 3초 공격속도 증가
  2. 이동속도 증가/감소
  3. 피해량 증가 / 받는 피해 증가
  4. 보호막

반대로 감전/빙결/신성노출/이름표식처럼 후속 로직이 많은 상태는 1차 공통화 뒤에 옮기는 것이 안전하다.

Step 9

기존 개별 필드를 제거하는 기준을 정한다

  • 선택 아군, 소환 아군, 적군 모두가 공통 채널을 통해 값을 읽는다.
  • 효과 적용, 갱신, 만료, 스택 규칙이 공통 effect layer에서 재현된다.
  • 기존 스킬 helper는 effect 생성기 역할만 남고, 대상 필드를 직접 수정하지 않는다.

4. 이 설계를 현재 코드에 맞게 적용할 때의 권장 순서

  1. 선택 아군의 상태 owner를 점진적으로 CombatRuntimeController 필드에서 selectedTarget으로 옮긴다.
  2. 소환 아군 CombatUnitRuntime에 CombatTargetModel 참조를 붙인다.
  3. EnemyRuntime에 CombatTargetModel 참조를 붙인다.
  4. 공통 modifier aggregator를 만든다.
  5. ActionSpeedMultiplier 임시효과 하나를 양측 공통 효과로 먼저 이관한다.
  6. MoveSpeedMultiplier, DamageTakenMultiplier, DamageDealtMultiplier를 같은 방식으로 이관한다.
  7. Shield subsystem을 분리한다.
  8. 상태이상 계열을 마지막에 옮긴다.
이 순서를 따르면 “현재 전투를 깨지 않고 공통 임시효과 계층을 먼저 세운 뒤, 개별 스킬 로직을 점진 이동”하는 방식으로 갈 수 있다.

5. 최종 판단

현재 inspected code 기준으로, 공통 전투 대상 모델과 재사용 가능한 임시효과 구조는 필요하다. 그리고 그것은 현재 코드 위에서 단계적으로 만들 수 있다.

다만 지금 구조를 보면 바로 “버프 객체를 넣는다”보다 먼저 해야 할 일은 선택 아군 / 소환 아군 / 적군의 전투 중 상태를 한 레이어에서 읽을 수 있게 만드는 것이다. 그 공통 대상 모델이 생긴 뒤에야 "3초간 공격속도 20% 증가" 같은 임시효과를 한 번 구현해 양쪽에 안전하게 재사용할 수 있다.
