Ariel / Enemy 스킬 런타임 리팩토링 달성 현황

기준 문서: 2026-05-29-skill-runtime-refactor-feedback-handoff.md. 이 보고서는 확인한 코드와 보드 근거만 사용해 현재 구조가 목표 구조에 얼마나 가까워졌는지 정리한다.

요약

Ariel 스킬 구조는 목표 구조에 상당히 가까워졌다. UnitSkillController.cs가 유닛별 스킬 tick과 자동/수동 실행 요청 생성을 맡고, SkillExecutionPlan.cs가 condition/action/modifier/effect/trigger 노드를 담으며, SkillPlanActionDispatcher.cs가 effect와 trigger 실행을 공통 경로로 넘긴다.

Enemy 스킬도 별도 경로에서 node 기반 구조로 많이 전환됐다. EnemyDefinition.cs가 EnemySkillPlanDefinition을 보유하고, EnemyCombatSystem.cs 내부의 EnemySkillPlanRuntime이 Stage 2 스킬의 damage area, projectile, heal, chain, charge, outgoing damage debuff 등을 실행한다.

다만 완성은 아니다. Ariel은 아직 SkillExecutionSnapshot.cs에 여러 flat multiplier 필드가 남아 있고, effect/trigger 실행도 완전히 독립 handler 목록으로 분리된 것이 아니라 SkillMultiEffectExecutor.cs, SkillTriggerRuntime.cs로 위임되는 호환 구조다. Enemy는 공용 SkillExecutionPlan.cs이 아니라 Enemy 전용 plan/runtime을 사용한다. Eve, Vega, Sein, Rin 스킬을 리팩토링하면서 이 남은 부분을 공용 구조로 흡수하는 것이 다음 단계다.

Ariel: 높음 목표 구조의 핵심 축인 unit controller, plan node, action dispatcher가 실제 코드에 들어가 있다.
Enemy: 중간 이상 Enemy 전용 node runtime은 구축됐지만 플레이어/몬스터 공용 plan 구조와는 아직 분리되어 있다.
전체 목표: 진행 중 표시/상태/스킬 요청/전투 서비스 분리는 진전됐고, handler 완전 분리는 남아 있다.

Ariel 스킬 리팩토링 근거

1. Actor와 RuntimeModel의 책임 분리

MonsterUnitActor.cs는 Initialize에서 모델 참조를 받고 debug view를 갱신하며, ShowDamage, TryPlayActiveSkillAnimation, TryPlayHitAnimation, TryPlayDeathAnimation, RefreshDebugView를 가진다. HP mutation, damage rule, status application은 여기 없다.

BaseUnitRuntimeModel.cs는 Identity, Stats, Defenses, Resources, SkillRuntime, Statuses, auto flag를 보유한다. MonsterUnitRuntimeModel.cs은 여기에 State만 추가한다. 즉 목표 구조의 “표시 객체”와 “런타임 상태 객체” 분리는 현재 코드에서 확인된다.

2. UnitSkillController 도입

기준 문서 작성 시점에는 unit-scoped skill owner가 없다는 문제가 있었다. 현재는 UnitSkillController.cs가 존재하고, Tick에서 해당 유닛의 SkillRuntime을 tick한 뒤 auto route 조건을 검사하고 SkillExecutionRequest를 만든다. 수동 실행도 TryExecuteManual에서 같은 요청 객체로 들어간다.

SkillExecutionSystem.cs는 Dictionary<UnitRosterEntry, UnitSkillController>를 통해 유닛별 controller를 캐시하고, 각 roster entry를 controller에 위임한다. 이것은 목표 구조의 “캐릭터가 스킬 사용의 주체”라는 방향을 실제 코드로 상당히 반영한 부분이다.

3. Ariel choice와 normalized node

SkillExecutionPlan.cs에는 SkillExecutionPlanNodeKind로 CastCondition, Action, DamageModifier, CritModifier, OnKillAction, Trigger, Visual 등이 정의되어 있다. SkillExecutionPlan은 Nodes, CastConditions, Actions, DamageModifiers, CritModifiers, KillActions, EffectActions, TriggerActions를 제공한다.

InGameSkillDefinitionMapper.cs는 skill definition의 NormalizedPlanNodes를 skill data로 옮긴다. Ariel 보드 근거에 따르면 Ariel choice의 old wide column 일부는 normalized node와 plan action handler 경로로 이동했다. 즉 Ariel은 현재 목표 구조를 검증하는 선행 사례가 됐다.

4. 아직 남은 Ariel 쪽 미완성

SkillExecutionSnapshot.cs에는 여전히 DamageMultiplier, ShieldAmountMultiplier, CooldownMultiplier, RadiusMultiplier, ReloadTimeMultiplier, BossDamageMultiplier 같은 flat 필드가 많다. 이것은 기준 문서가 지적한 “wide snapshot field 증가”가 완전히 해소되지는 않았다는 근거다.

또한 SkillPlanActionDispatcher.cs는 effect/trigger를 직접 완결 처리하기보다 SkillMultiEffectExecutor.cs와 SkillTriggerRuntime.cs로 넘긴다. 따라서 action handler 구조는 진입점이 생긴 상태이고, 세부 handler 분리는 계속 진행해야 한다.

Enemy 스킬 리팩토링 근거

1. Enemy 전용 plan 구조

EnemyDefinition.cs에는 EnemySkillPlanDefinition, EnemySkillPlanNodeDefinition, EnemySkillPlanParamDefinition이 존재한다. Enemy active/basic skill은 BasicSkillPlan, ActiveSkillPlan으로 plan을 들 수 있다.

EnemyCombatSystem.cs 내부의 EnemySkillPlanRuntime은 HasCombatStartTrigger, TickPendingActions, TickActiveCharge, node 실행 switch를 가진다. action op는 DamageArea, SpawnProjectile, Heal, DamageThenDelayedChain, ChargeDamageStatus, ApplyOutgoingDamageMultiplierStatus 같은 Stage 2 enemy skill behavior를 처리한다.

2. Enemy에서 달성된 부분

Enemy 스킬은 더 이상 단순 switch 하나로만 끝나는 구조가 아니다. EnemyCombatState에는 pending chain action과 active charge action이 있고, EnemySkillPlanRuntime은 combat start trigger, delayed chain, charge 상태, collider-backed damage area, projectile spawn을 처리한다.

최근 작업 근거상 FireDragonSlash는 collider-backed hitbox를 사용하고, Arsen intimidation은 stage-persistent status로 들어간다. 이런 처리는 기준 문서의 “작은 action/handler 단위로 행동을 표현한다”는 방향과 맞다.

3. Enemy에서 아직 남은 부분

Enemy plan은 공용 SkillExecutionPlan.cs을 쓰지 않고 EnemySkillPlanDefinition과 EnemySkillPlanRuntime을 쓴다. 따라서 구조 방향은 비슷하지만, Ariel/Monster 공용 skill execution plan과 완전히 합쳐진 상태는 아니다.

또한 EnemyCombatSystem.cs 안에 EnemySkillPlanRuntime과 여러 실행 helper가 같이 들어 있다. 현재 동작을 빠르게 안정화하기에는 효과적이지만, 장기적으로는 action handler 파일 또는 enemy skill handler 단위로 분리할 여지가 있다.

현재 달성도 판단

평가 항목 판단 이유
Actor에서 gameplay 책임 제거 거의 달성 MonsterUnitActor.cs는 표시와 애니메이션 중심이고, runtime reset은 MonsterUnitRuntimeStateService.cs가 맡는다.
유닛별 스킬 소유자 상당히 달성 UnitSkillController.cs가 생겼고, SkillExecutionSystem.cs이 유닛별 controller를 캐시한다.
CSV 기반 plan node 부분~상당 달성 Ariel은 SkillExecutionPlan.cs 기반, Enemy는 EnemySkillPlanDefinition 기반으로 node화됐다. 두 경로는 아직 통합되지 않았다.
Action/modifier handler 분리 부분 달성 SkillPlanActionDispatcher.cs는 있으나, 실제 처리는 기존 executor/runtime에 많이 남아 있다.
flat snapshot field 감소 미완성 SkillExecutionSnapshot.cs에 아직 다수의 flat multiplier와 choice 결과 필드가 남아 있다.
공유 combat service coordination 상당히 달성 InGameCombatManager.cs가 damage/status/trigger/status tick을 조정하고, resource mutation과 runtime state reset은 별도 서비스로 분리됐다.

앞으로의 완성 방향

현재 구조는 Ariel과 Enemy를 통해 목표 구조의 뼈대를 실제 코드에 올린 상태다. 완성은 Eve, Vega, Sein, Rin을 같은 방식으로 옮기면서 진행하는 것이 안전하다. 이유는 한 번에 전체 스킬 시스템을 갈아엎으면 현재 CSV 호환성과 Play Mode 동작 검증 범위가 너무 커지기 때문이다.

  • Eve, Vega, Sein, Rin의 특수 조건과 피해 보정은 새 flat field를 늘리기보다 SkillExecutionPlan.cs의 action/modifier node로 옮긴다.
  • 반복되는 damage/status/projectile/zone/visual 처리는 SkillPlanActionDispatcher.cs 아래의 명확한 handler로 분리한다.
  • Enemy 전용 plan은 당장 유지하되, 공통화 가능한 action op와 hitbox/projectile/status 처리만 먼저 공유 handler로 뽑는다.
  • SkillExecutionSnapshot.cs는 당장 제거하지 말고, 각 몬스터 리팩토링 때 flat 필드를 node 결과로 대체하면서 점진적으로 줄인다.
  • Play Mode 검증은 몬스터 단위로 진행한다. Ariel은 선행 기준, 다음 몬스터들은 같은 구조를 재사용하는 검증 대상이 된다.

결론

Ariel 스킬은 기준 문서의 목표 구조를 “대부분의 핵심 방향에서 달성한 상태”다. Actor와 model 책임이 분리됐고, unit-scoped controller가 생겼으며, normalized node와 execution plan/action dispatcher가 실제 경로에 들어갔다.

Enemy 스킬은 “공용 구조와 같은 철학을 가진 별도 구현” 상태다. Stage 2 스킬의 복잡한 행동은 node runtime으로 옮겨졌지만, 아직 공용 SkillExecutionPlan.cs 경로와 통합되지는 않았다.

따라서 현재 상태는 완성이라기보다 목표 구조의 중간 지점이다. 남은 Eve, Vega, Sein, Rin 리팩토링을 통해 flat snapshot field를 줄이고, action/modifier handler를 더 독립화하며, Ariel과 Enemy에서 검증된 구조를 공용 패턴으로 굳히면 목표 구조에 도달할 수 있다.
