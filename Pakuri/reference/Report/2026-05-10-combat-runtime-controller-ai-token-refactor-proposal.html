Structure Proposal

CombatRuntimeController 구조 분리 제안서

이 문서는 현재 전투 런타임 구조를 "파일이 많다"는 인상 수준이 아니라, 실제 코드 소유권, AI 작업 비용, 토큰 소비, 컨텍스트 윈도우 낭비, 그리고 실제 프로그래머의 가독성 관점에서 재검토하기 위한 설득 자료다.

핵심 결론: 지금 구조는 "partial로 나뉜 큰 클래스"가 아니라, 사실상 하나의 거대한 shared-state 전투 객체에 가깝다. 그래서 사람도 읽기 어렵고, AI 에이전트는 더 비싸게 작업하게 된다.

1. 현재 구조가 실제로 어떤 상태인지

문제는 단순히 CombatRuntimeController.cs 한 파일이 크다는 점이 아니다. 전투 상태의 핵심 필드가 여전히 한 클래스에 모여 있고, 각 partial 파일이 그 상태를 같이 읽고 쓰기 때문에 실제 책임 분리가 끝나지 않았다.

2. 왜 나눠야 하는가: AI 프로그래밍, 토큰 절약, 컨텍스트 윈도우 관점

2-1. 읽기 비용이 작업 비용이 된다

AI 에이전트는 필요한 코드 조각만 읽으면 싸게 끝나지만, 공유 상태가 크고 숨은 결합이 많으면 안전하게 수정하기 위해 더 넓은 범위를 다시 읽어야 한다.

예를 들어 core + party + projectiles + Eve skill만 읽어도 약 220,819 chars, 대략 55,205 tokens 수준이다. 여기에 지시문, 보드 문서, diff, 빌드 로그, 연관 파일이 추가되면 금방 커진다.

2-2. 컨텍스트 윈도우 낭비가 생긴다

진짜 필요한 로직은 "Eve B 지속시간 조정" 같은 작은 변경일 수 있다. 그런데 그 변경이 projectiles, skillEffects, manifestedMonsters, selectedUnitRuntime와 엮여 있으면 관련 partial을 통째로 다시 올려야 한다.

이것은 정보량이 아니라 결합도 때문에 발생하는 컨텍스트 낭비다.

2-3. 수정 누락 위험이 커진다

shared-state 구조에서는 동일한 상태를 여러 partial이 직접 만진다. 그러면 한 경로만 고치고 다른 경로를 놓치기 쉽다.

2-4. "분리된 것처럼 보이지만 실제로는 덜 분리됨"

몬스터 runtime adapter도 완전한 독립 모듈이 아니다. 현재 구조는 controller를 잡고 메서드를 다시 forwarding하는 형태다. 

CombatMonsterSkillRuntime.cs
29: protected CombatRuntimeController Controller { get; }
128: new EveMonsterSkillRuntime(this)
154: return monsterSkillRuntimeLookup.TryGetValue(...)

즉, 파일 구조는 나뉘어도 AI는 여전히 controller 전체를 이해해야 안전하다.

토큰 최적화 관점에서 가장 비싼 구조는 "코드가 많은 구조"보다 "작은 변경에도 큰 범위를 다시 읽게 만드는 구조"다. 현재 구조는 후자에 가깝다.

3. 왜 나눠야 하는가: 실제 프로그래머의 가독성과 유지보수 관점

  • 책임 경계가 흐리면 새 작업자가 "어디를 고쳐야 하는지"보다 "어디까지 읽어야 안전한지"부터 고민하게 된다.
  • update 순서가 하나의 메서드에 모이면, 특정 하위 시스템 변경이 다른 하위 시스템 타이밍에 미치는 영향이 커진다.
  • partial이 많아도 shared private field를 같이 쓰면 IDE 탐색 결과가 곧바로 책임 분리로 이어지지 않는다.
  • 버그 수정이 "한 기능 수정"이 아니라 "이 상태를 건드리는 모든 경로 찾기" 작업으로 바뀐다.
  • 코드 리뷰 역시 파일 단위가 아니라 시스템 단위 검토가 필요해져 검토 범위가 불필요하게 커진다.
반대로 기능 단위로 나누면 "읽는 범위"와 "수정 범위"가 비슷해진다. 이것은 사람에게도 좋고, AI 에이전트에게는 훨씬 더 중요하다.

4. 어떻게 나눌 수 있는가: 실제 기능 단위 분해안

전체를 한 번에 갈아엎는 방식보다, 현재 코드 소유권을 좁히는 순서로 단계적으로 분해하는 편이 안전하다.

분해 단위 현재 근거 분리 이유 분리 후 역할
Battle Orchestrator CombatRuntimeController.cs:481-505 현재는 lifecycle + 모든 서브시스템 호출이 섞여 있음 Unity lifecycle, update 순서, scene wiring만 담당
Selected Unit Combat selectedMonster, selectedUnitRuntime, 탄창/재장전 필드 1P 상태가 전역 controller 필드와 너무 밀착됨 1P 발사, 재장전, 자동 스킬, 방어막 동기화 담당
Manifested Party Runtime CombatRuntimeParty.cs 1,890 lines 파티 구성, UI, 일부 전투 로직이 한 파일에 섞여 있음 2P~5P 슬롯 구성, 파티 상태, manifested 전투 틱 담당
Projectile / Effect / Drone Simulation projectiles, skillEffects, drones 여러 스킬 partial이 같은 전장 오브젝트 리스트를 직접 수정 투사체 진행, 충돌, 지속 이펙트, 드론 틱을 한곳에서 담당
Enemy Simulation CombatRuntimeEnemies.cs, GetStageOneEnemies 적 스폰/이동/타겟팅은 독립적인 서브시스템 성격이 강함 적 생성, 이동, 타겟 우선순위, 적 공격 담당
Reward / Combat Result Flow rewardOptions, 승패 상태, 보상 상태 전투 시뮬레이션과 보상 UI 흐름은 관심사가 다름 전투 종료 판단 이후의 보상 생성/적용 담당

Monster Skill Executors CombatRuntimeEveSkills.cs 등 현재는 스킬 파일이 shared list를 직접 수정함 전장 서비스 인터페이스를 통해서만 발사/이펙트 생성 요청
핵심은 "파일을 더 만드는 것"이 아니라, 누가 어떤 상태를 소유하는지 명확히 바꾸는 것이다. 그래야 AI와 사람이 모두 작은 범위만 읽고도 안전하게 수정할 수 있다.

5. 실제 분해 순서 제안

  1. 먼저 전투 상태 소유권을 문서로 고정한다. 무엇이 selected-unit 소유인지, 무엇이 party 소유인지, 무엇이 projectile system 소유인지 먼저 정한다.
  2. Manifested Party를 먼저 분리한다. 현재 가장 큰 manager partial이고, 파티/상태 UI/전투가 교차한다.
  3. Projectile / Effect / Drone를 분리한다. shared battlefield list를 한곳으로 모은다.
  4. Enemy Simulation을 분리한다. 타겟팅과 스폰 정책을 selected-unit 로직에서 떼어낸다.
  5. Selected Unit Combat을 분리한다. 1P 재장전, 자동 스킬, 실드 미러링을 controller에서 꺼낸다.
  6. 마지막에 monster runtime adapter가 controller 전체를 보지 않도록 인터페이스를 좁힌다.
순서를 거꾸로 잡으면 안 된다. 예를 들어 selected-unit만 먼저 뽑아도 projectile/effect shared state가 그대로면 결국 controller 재의존이 다시 생긴다.

6. 무엇을 싱글톤화할 수 있는가

싱글톤은 "어디서나 접근 가능"하다는 장점이 있지만, 그 장점은 진짜 전역 데이터에만 써야 한다. 이미 저장소 안에도 그 방향의 예시가 있다.

이미 좋은 전역 예시 1: PakuriDataManager

PakuriDataManager.cs
18: private static readonly PakuriDataManager instance = new PakuriDataManager();
24: public static PakuriDataManager Instance => instance;
26: public GameDataCatalog CurrentCatalog { get; private set; }
28: public void RegisterCatalog(GameDataCatalog catalog)

이 객체는 몬스터/적/스킬/보상 정의 lookup을 관리한다. 읽기 중심 전역 데이터 저장소이기 때문에 싱글톤 성격이 잘 맞는다.

이미 좋은 전역 예시 2: RunStartContext

RunStartContext.cs
9:  public static RunStartContext Instance { get; private set; }
15: public static RunStartContext Ensure()
24: DontDestroyOnLoad(contextObject);
40: private void Awake()
49: DontDestroyOnLoad(gameObject);

씬을 넘겨야 하는 "실행 컨텍스트"는 전역 1개만 존재하면 되는 성격이므로 singleton-style MonoBehaviour가 합리적이다.

싱글톤 후보 왜 괜찮은가 비고
데이터 카탈로그 / 정의 조회 게이트웨이 전투 인스턴스마다 새로 생길 필요가 없고, 대부분 read-mostly 데이터다. PakuriDataManager가 이미 같은 역할을 수행 중
CSV / 런타임 데이터 초기화 서비스 프로세스 단위로 1회 초기화되는 편이 자연스럽다. PakuriCsvRuntimeData가 static partial로 이미 존재
씬 간 Run 시작 컨텍스트 단일 실행 문맥을 씬 사이에 전달하는 역할이다. RunStartContext가 이미 해당 패턴 사용
읽기 전용 전투 규칙/설정 레지스트리 여러 시스템이 같은 룰 테이블을 참조한다면 전역 1개 접근점이 편하다. 단, mutable battle state를 넣으면 안 됨
싱글톤의 장점은 참조 배선 비용을 줄이고, 단일 진실 공급원(single source of truth)을 만들 수 있다는 점이다. 다만 그 장점은 전역 정의/설정/컨텍스트에 한정해서 써야 한다.

7. 무엇을 싱글톤화하면 안 되는가

대상 왜 안 되는가
enemies, projectiles, skillEffects, drones 이것들은 현재 전투 인스턴스의 상태다. 전역화하면 오히려 숨은 결합이 커지고 테스트/리셋도 더 어려워진다.
selectedMonster, selectedUnitRuntime, 탄창/쿨다운/실드 상태 1회 전투의 mutable runtime state다. 전역보다 인스턴스 소유가 명확해야 한다.
manifestedMonsters와 그 파생 상태 전투 단위 파티 상태다. 싱글톤으로 올리면 현재 controller가 가진 문제를 다른 전역 객체로 옮기는 것뿐이다.
rewardOptions, 승패/보상 대기 상태 전투 결과 플로우의 임시 상태이므로 battle session에 묶여 있어야 한다.
정리하면, 지금 문제를 "전역 접근이 필요하니 싱글톤으로 빼자"로 풀면 안 된다. 그 방식은 controller의 복잡도를 다른 이름의 전역 상태로 옮기는 것에 불과할 수 있다.

8. 싱글톤 패턴 자체의 장점과 참고 코드

외부 참고 코드 D:\Unity\lost-library-PC\WorkShop_Sad\Assets\Scripts\Common\Core\Singleton.cs는 전형적인 non-MonoBehaviour generic singleton 패턴을 보여준다.

참고 코드의 핵심 구조

Singleton.cs
25: public static T Instance
36: protected virtual void Init() { }
42: protected Singleton() { }
43: internal void InternalInit()
65: internal static class SingletonAllocator
74: CreateInstance(typeof(T));
111: singleton.InternalInit();

장점은 접근점이 단일하고, 생성 시점과 초기화 지점을 통제할 수 있으며, scene object 유무와 무관하게 앱 전역 서비스처럼 쓸 수 있다는 점이다.

이 패턴이 잘 맞는 경우

  • 전역 데이터 레지스트리
  • 정적 규칙 테이블 캐시
  • 씬 비의존 앱 서비스
  • 읽기 중심 카탈로그 조회

이 패턴이 안 맞는 경우

  • 매 전투마다 리셋되어야 하는 runtime state
  • scene instance와 결합된 오브젝트 리스트
  • 하나의 전투 안에서만 유효한 임시 상태
// 예시: 읽기 전용 전투 정의 게이트웨이
// 아래 예시는 "이런 종류의 전역 데이터"에만 singleton을 쓰자는 예시이며,
// 현재 저장소에 존재하는 구현이 아니라 설계 예시다.

using Common.Core;
using Pakuri.Data;

public sealed class CombatDefinitionGateway : Singleton<CombatDefinitionGateway>
{
    protected override void Init()
    {
        Catalog = PakuriDataManager.Instance.CurrentCatalog;
    }

    public GameDataCatalog Catalog { get; private set; }

    public MonsterDefinition ResolveMonster(string id)
    {
        return PakuriDataManager.Instance.ResolveMonster(id, Catalog);
    }
}

위 예시처럼 전역 조회 게이트웨이는 singleton이 어울리지만, CurrentBattleState 같은 mutable runtime state를 이런 형태로 올리는 것은 권장하지 않는다.

9. 권장 결론

  • CombatRuntimeController는 지금도 동작은 가능하지만, AI 협업과 장기 유지보수 관점에서는 이미 비용이 높은 구조다.
  • 지금 분리해야 하는 이유는 "예쁘게 만들기 위해서"가 아니라, 작은 작업을 작은 컨텍스트 안에서 끝낼 수 있게 만들기 위해서다.
  • 파일 분리보다 중요한 것은 상태 소유권 분리다.
  • 싱글톤은 전역 정의/설정/씬 간 컨텍스트에는 유효하지만, 전투 runtime state 문제의 해법은 아니다.
  • 가장 먼저 손댈 곳은 Manifested Party, Projectile / Effect / Drone, Enemy Simulation 경계다.
이 구조 개선의 목표는 "클래스를 잘게 쪼개기"가 아니다. 작업자가 필요한 만큼만 읽어도 안전하게 수정할 수 있는 구조를 만드는 것이다.
