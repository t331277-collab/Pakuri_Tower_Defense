Designer Roadmap

Assets/CSVData 원본 전환 로드맵

목적은 기존 Assets/Legacy 아래의 데이터/스크립트를 참고 자료로만 남기고, 새 Assets/CSVData CSV 3개를 몬스터, 적, 스킬 수치의 원본으로 삼는 것이다. 이 문서는 코드 구현이 아니라 Code Builder가 따라야 할 작업 순서와 검증 기준이다.

1. 현재 확인된 상태

항목 확인 결과 근거
새 CSV 원본 위치 Assets/CSVData가 존재하고 EnemyStat.csv, MonsterStat.csv, SkillData.csv가 존재한다. 세 파일은 현재 0 byte로 비어 있다. Get-Item Pakuri\Assets\CSVData\EnemyStat.csv, MonsterStat.csv, SkillData.csv
기존 데이터 위치 Assets/Legacy/CSVdata, Assets/Legacy/Data, Assets/Legacy/Scripts가 존재한다. Get-ChildItem Pakuri\Assets\Legacy
레거시 컴파일 상태 Assembly-CSharp.csproj는 아직 Assets\Legacy\Scripts\... 파일들을 컴파일 대상으로 포함한다. Select-String Pakuri\Assembly-CSharp.csproj -Pattern "Legacy"
현재 InGame 의존성 Scripts2/InGame의 일부 파일은 아직 Pakuri.Data, MonsterDefinition, SkillDefinition, PakuriCsvRuntimeData, PakuriDataManager를 참조한다. Select-String Pakuri\Assets\Scripts2 -Pattern "Pakuri.Data|MonsterDefinition|SkillDefinition|PakuriCsvRuntimeData"
레퍼런스 원본 몬스터 설계 문서는 Pakuri/reference/2.Monster, 적 설계 문서는 Pakuri/reference/5.enemy 아래에 존재한다. Get-ChildItem Pakuri\reference\2.Monster, Get-ChildItem Pakuri\reference\5.enemy
중요: Assets/Legacy로 이동되어 있어도 컴파일 대상이거나 씬/리소스에서 참조되면 여전히 동작할 수 있다. 따라서 “Legacy는 참고만 하고 게임 내에서 동작하지 않는다”는 목표는 별도의 비활성화/참조 제거 단계로 검증해야 한다.

4. 작업 순서

Phase 0 Legacy 격리 기준 확정

Assets/Legacy는 참고 전용이라는 정책을 먼저 코드 기준으로 정의한다. 이 단계에서는 레거시 파일을 삭제하지 않는다.

  • Assembly-CSharp.csproj와 Unity 컴파일에서 레거시 스크립트가 아직 들어오는지 확인한다.
  • 씬, 프리팹, Resources가 레거시 GameDataCatalog, PakuriCsvRuntimeData, CombatRuntimeController를 참조하는지 목록화한다.
  • 새 InGame 경로가 완성될 때까지 레거시는 “빌드 차단 없이 남아 있는 구 코드”로 취급한다.

완료 기준: 레거시 참조 제거 대상 목록과 보존 대상 목록이 문서화되어 있다.

Phase 1 새 CSV 스키마 작성

비어 있는 세 CSV에 헤더를 먼저 추가한다. 헤더는 나중에 로더와 검증기가 의존하는 계약이므로, 데이터 입력보다 먼저 고정해야 한다.

  • MonsterStat.csv, EnemyStat.csv, SkillData.csv의 컬럼명을 확정한다.
  • 모든 ID 컬럼의 명명 규칙을 정한다. 예: eve, eve-a, stage1-swordsman.
  • 숫자 단위를 명시한다. 예: 초 단위, 배율 단위, 퍼센트/0~1 범위.

완료 기준: 세 CSV가 0 byte가 아니며, 헤더만으로도 로더/검증기 구현이 가능하다.

Phase 2 기준 데이터 1차 입력

reference/2.Monster와 reference/5.enemy를 기준으로 직접 행을 만든다. 마크다운에서 자동 로드하는 파이프라인은 현재 확인되지 않았으므로, 이 단계의 원본은 사람이 채운 CSV다.

  • 먼저 Eve와 Stage 1 대표 적 1~2개만 입력해 연결 테스트 데이터를 만든다.
  • 스킬은 Eve A~E 또는 Eve E 같은 대표 케이스를 먼저 입력한다.
  • 문서에 수치가 없는 항목은 임의로 invent하지 말고 빈 값 또는 명시적인 TODO 값으로 둔다.

완료 기준: 최소 1개 몬스터, 1개 적, 1~2개 스킬이 새 CSV에 들어 있다.

Phase 3 새 CSV 로더와 Row 모델 구현

Scripts2/InGame 아래에 새 로더를 만든다. 이 로더는 레거시 PakuriCsvRuntimeData, GameDataCatalog, MonsterDefinition, SkillDefinition을 사용하지 않는다.

  • CSV 파일별 row 구조체 또는 클래스를 만든다.
  • 필수 컬럼 누락, ID 중복, enum 파싱 실패, 숫자 파싱 실패를 검증한다.
  • 로드 결과를 ID 기반 catalog/service로 제공한다.

완료 기준: Unity Editor 또는 빌드 검증에서 새 CSV를 읽고 ID로 행을 조회할 수 있다.

Phase 4 유닛 런타임 모델 연결

UnitFactory와 관련 유닛 생성 경로를 새 CSV catalog 기준으로 바꾼다.

  • MonsterStat.csv에서 MonsterUnitRuntimeModel을 만든다.
  • EnemyStat.csv에서 EnemyUnitRuntimeModel을 만든다.
  • BaseUnitRuntimeModel에는 HP, Shield, 저항, 기본 공격력 같은 공통 스탯만 들어가게 유지한다.

완료 기준: Scripts2/InGame/Units가 레거시 MonsterDefinition, EnemyDefinition, PakuriDataManager 없이 모델을 생성한다.

Phase 5 스킬 데이터 매핑 연결

SkillData.csv를 ProjectileSkillData, ZoneSkillData, BuffSkillData, ShieldSkillData, PassiveSkillData 계열로 매핑한다.

  • runtime_kind가 어떤 SkillData subclass로 가는지 명시한다.
  • 피해, 계수, 쿨타임, 틱 주기, 지속시간, 탄창, 재장전은 스킬 데이터에서만 읽는다.
  • Eve-E 같은 장판형 스킬은 Field 또는 zone 계열로 매핑하고, 투사체 탄속/투사체 발사 간격으로 해석하지 않는다.

완료 기준: InGameSkillCatalog가 레거시 SkillDefinition 없이 새 CSV에서 SkillData를 만든다.

Phase 6 사용자 제작 프리팹 바인딩

프리팹은 코드로 생성하지 않는다. 사용자가 Unity Editor에서 만든 프리팹에 Actor/Binding 컴포넌트를 붙이고, 컴포넌트는 CSV ID를 통해 런타임 데이터를 받는다.

  • 몬스터 프리팹은 Assets/Prefab/Monster에 둔다.
  • 적 프리팹은 Assets/Prefab/Enemy에 둔다.
  • 스킬/효과 프리팹은 Assets/Prefab/Skill에 둔다.
  • 프리팹은 수치를 소유하지 않고, ID와 표시/애니메이션/이펙트 바인딩만 소유한다.

완료 기준: 프리팹을 교체해도 CSV ID가 같으면 같은 스탯/스킬 수치로 동작한다.

Phase 7 스킬 실행 구현

스킬 실행기는 SkillData.csv에서 매핑된 SkillData를 읽어서 동작한다. 이 단계부터 projectile, zone, buff, shield, passive 등의 실제 실행이 들어간다.

  • Projectile 계열은 탄창, 재장전, 투사체 속도, 명중 처리의 책임을 가진다.
  • Zone 계열은 반경, 지속시간, 틱 주기, tick damage/status의 책임을 가진다.
  • Buff/Shield/Passive 계열은 대상, 지속시간, 트리거, 갱신 규칙을 가진다.

완료 기준: 스킬 수치를 바꾸려면 C#이 아니라 SkillData.csv를 수정하면 된다.

Phase 8 Legacy 비활성화 검증

새 경로가 충분히 연결된 뒤에만 레거시 런타임 경로를 비활성화한다. 목표는 Assets/Legacy가 컴파일/씬/Resources/런타임 초기화에서 빠지는 것이다.

  • Scripts2/InGame에서 Pakuri.Data 참조가 사라졌는지 확인한다.
  • 레거시 RuntimeInitializeOnLoadMethod가 실행되지 않는지 확인한다.
  • 씬에 레거시 CombatRuntimeController 또는 구 Run UI 경로가 남아 있으면 새 InGame 전환 범위에 맞춰 분리한다.

완료 기준: 새 InGame 실행 경로가 레거시 CSV/Data/Scripts 없이 빌드되고, 필요한 런타임 데이터는 Assets/CSVData에서만 온다.

5. Code Builder 인수 기준

  • 구현은 한 번에 Legacy 제거까지 가지 말고, CSV 스키마 → 새 로더 → 유닛 모델 → 스킬 매핑 순서로 작게 나눈다.
  • 각 단계는 dotnet build Pakuri\Assembly-CSharp.csproj --no-restore와 Unity Editor refresh/console 확인으로 검증한다.
  • Play Mode 검증은 사용자 소유다. Code Builder는 빌드, 컴파일, 로더 조회, 에디터 코드 실행 결과까지만 증거로 남긴다.
  • Code Builder가 구현을 마친 뒤 Code Reviewer 단계가 필요하면, 저장소 규칙에 맞게 명시 권한 또는 검증된 외부 실행 흐름을 사용한다.

6. 핵심 결론

위 순서대로 진행하면 이후 로드맵의 몬스터/유닛 프리팹 제작과 스킬 구현은 기존 MonsterDefinition, SkillDefinition, PakuriCsvRuntimeData가 아니라 사용자가 직접 관리하는 Assets/CSVData CSV를 기준으로 진행할 수 있다.
단, 현재 확인된 코드 상태에서는 Assets/Legacy 스크립트가 여전히 컴파일 대상이고 Scripts2/InGame도 일부 레거시 데이터 타입에 의존한다. 따라서 새 CSVData 전환은 “데이터 파일 작성”만으로 끝나지 않고, 새 로더와 InGame 의존성 제거가 필수다.
