Pakuri 데이터 구조 리팩토링 단계별 작업 로그

이 문서는 “데이터 구조 전체 리팩토링” 명령 이후 작업이 한 번에 끝난 것이 아니라, 실제 로그와 board 기록을 기준으로 여러 단계로 나뉘어 진행됐다는 점을 드러내기 위한 단계별 보고서다. 기준은 boards/DATA, boards/RUN, boards/COMBAT, boards/OPS/REVIEWER_BLACKBOARD.md, 그리고 현재 코드다.

단계 요약 표

단계 핵심 결과 상태 다음 단계로 이어진 이유
0단계 기준선 CSV / markdown / hardcoded seeder / SO asset 혼합 구조 개선 전 원본 고정, 검증 강제, query contract, 구조 분해가 모두 필요했다.
1차 개선 초기 CSV runtime migration과 startup validation / quit 경로 도입 부분 구현 Reviewer가 asset path, fallback, query contract, monolith 문제를 잡아냈다.
Reviewer Gate 수동 Code Reviewer FAIL FAIL player-safe asset path와 source-of-truth 고정, query 통일이 더 필요했다.
2차 개선 Assets/CSVdata/source, Resources-backed catalog, PakuriDataManager 도입 부분 구현 source/asset 안전성은 올라갔지만 loader monolith와 consumer query 범위가 남았다.
3차 개선 PakuriCsvRuntimeData partial 분리 부분 구현 row / parser / dataset가 여전히 한 파일군 안에 뭉쳐 있었다.
4차 개선 roster query contract 통일 부분 구현 legacy seeder와 monster 하위 collection query가 아직 직접 접근을 남겼다.
5차 개선 legacy seeder 제거 + dataset 파일 세분화 + collection query 확장 구현됨 이제 남은 문제는 다른 층위의 구조 부채(DisplayName state, Stage 1 스키마, dormant legacy asset)다.

0단계 기준선

실제 상태

  • PakuriGameDataSeeder.cs가 5몬스터와 Stage 1 적 8개를 코드에 직접 들고 있었다.
  • 같은 seeder가 reference/2.Monster/{monster}/skill 아래 markdown를 다시 읽어 SO asset을 갱신했다.
  • GameDataCatalog.asset는 Stage 1 전용 구조를 중심으로 유지됐다.

당시 미구현

  • CSV 단일 원본 고정
  • startup fatal validation
  • runtime-safe asset binding catalog
  • 통일된 DataManager query contract

다음 목표

  • 실제 런타임 원본을 하나로 고정
  • 실패를 warning이 아니라 중단으로 바꾸기
  • consumer query를 한 계약으로 모으기

1차 개선: 초기 CSV Runtime Migration

첫 구현은 CSV-first 방향 전환 자체를 여는 단계였다. 최초 loader는 Pakuri/data/source를 읽었고, startup 시 CSV 파싱과 validation을 돌린 뒤 치명적 오류면 종료하는 경로를 넣었다.

구현됨

  • typed CSV source 세트 도입
  • startup parse + validate + quit 경로 도입
  • combat / run startup이 CSV-backed catalog를 선호하도록 방향 전환 시작

부분 구현

  • source root가 아직 Pakuri/data/source 파일 경로였다.
  • asset path 바인딩 안전성과 query contract가 미약했다.

미구현 / 이월

  • Resources-backed runtime asset catalog
  • unified query contract
  • dataset 단위 구조 분해

Reviewer Gate: 중간 FAIL

이 리팩토링은 한 번에 끝나지 않았고, 중간 reviewer 단계에서 명확하게 실패했다. boards/OPS/REVIEWER_BLACKBOARD.md의 CSV Runtime Migration Reviewer 2026-05-02 기록 기준으로, 외부 reviewer는 타임아웃됐지만 수동 Code Reviewer pass는 FAIL 판정이었다.

  • 지적 1: non-Resources asset path가 player runtime에서 안전하지 않았다.
  • 지적 2: CSV가 비면 GameDataCatalog.asset가 다시 숨은 원본처럼 동작할 수 있었다.
  • 지적 3: unified query contract가 부족했다.
  • 지적 4: loader / row model / validator가 너무 한 덩어리였다.

2차 개선: Resources-backed 재구성

Reviewer FAIL 이후 source-of-truth와 asset 안전성을 먼저 보강했다.

  • Assets/CSVdata/source를 실제 source import 위치로 고정했다.
  • PakuriCsvRuntimeSourceCatalog.asset와 PakuriCsvRuntimeAssetCatalog.asset를 도입했다.
  • PakuriDataManager singleton registry를 추가했다.
  • CSV 초기화 실패 시 serialized catalog hidden fallback을 차단했다.

3차 개선: partial 분리

두 번째 단계가 source와 asset 안전성을 다뤘다면, 세 번째 단계는 커진 loader monolith를 역할별 partial 파일로 나누는 작업이었다.

  • PakuriCsvRuntimeData.cs: runtime entry
  • Loader.cs: source load
  • Validation.cs: source/runtime validation
  • Build.cs: in-memory catalog build
  • Editor.cs: sync / validate menu
  • Types.cs: enum shell

다만 이 시점에는 dataset row와 parser support가 아직 충분히 쪼개지지 않았다.

4차 개선: roster query contract 통일

이 단계에서는 gameplay entry에서 직접 catalog 배열을 읽는 경로를 먼저 정리했다.

  • GetMonsters(...), GetStageOneEnemies(...), ResolveMonster(...) 추가
  • MainMenu / RunFlow / DebugScene roster query 통일
  • RunCombatUi / RunSceneBootstrap fallback monster resolution 통일
  • CombatRuntimeEnemies stage-one enemy pool lookup 통일

하지만 monster 하위 active/passive/reward collection query는 아직 consumer에서 직접 접근이 남아 있었다.

5차 개선: legacy 제거 + dataset 세분화 + collection query 확장

이번 턴의 실제 구현은 이전 단계의 “부분 구현”을 닫는 데 집중했다.

  • PakuriGameDataSeeder.cs와 Pakuri/Seed Default Game Data 경로를 제거했다.
  • Pakuri/Bootstrap CSV Source Data From Current Catalog 메뉴와 LegacyCatalogAssetPath 의존을 제거했다.
  • CsvSupport, SourceModel, CatalogDataset, MonsterDataset, EnemyDataset 파일을 추가했다.
  • PakuriDataManager에 GetActiveSkills, GetPassiveSkills, GetRewardChoices, ResolveActiveSkill, ResolvePassiveSkill를 추가했다.
  • RunCombatUiController, DebugSceneController, CombatRuntimeEveSkills가 monster 하위 collection lookup을 manager query로 돌리게 바꿨다.

현재 시점 정리: 구현됨 / 부분 구현 / 미구현

항목 상태 근거
CSV 원본 고정 구현됨 Assets/CSVdata/source, source catalog, startup load/validate/build path
type row 기반 파서 구현됨 PakuriCsvRuntimeData.CsvSupport.cs
runtime-safe asset binding 구현됨 PakuriCsvRuntimeAssetCatalog + validation 경로
legacy seeder 경로 구현됨 PakuriGameDataSeeder.cs 삭제, bootstrap 메뉴 삭제
dataset row / parser 세분화 구현됨 CsvSupport, SourceModel, CatalogDataset, MonsterDataset, EnemyDataset
roster + collection query contract 구현됨 PakuriDataManager와 Run/Debug/Combat consumer 변경
DisplayName 기반 run state 정리 부분 구현 data query는 정리됐지만 run progression 상태 저장은 아직 별도 과제다.
Builder 후속 Reviewer 판정 미실행 이 문서 시점 기준. 이 턴 마지막에 별도 reviewer 실행 예정.

결론

이 리팩토링은 실제로 0단계 기준선 확인 → 1차 migration → Reviewer FAIL → 2차 구조 보강 → 3차 partial 분리 → 4차 roster query 통일 → 5차 legacy 제거 / dataset 세분화 / collection query 확장 순서로 진행됐다.

따라서 현재 상태를 가장 정확하게 표현하면, “CSV-first runtime 구조 전환과 그에 필요한 source/asset/query 분리가 단계적으로 닫혔고, 이제 남은 핵심 부채는 data access 이전 단계가 아니라 run-state stable-id화와 Stage 1 중심 스키마 일반화”라고 보는 것이 맞다.

단계별 한 줄 요약 0단계: 원본과 authoring 경로가 뒤섞인 상태 1차: CSV runtime의 시작점 확보 Reviewer Gate: 구조적 결함 노출 2차: Resources-backed source/asset catalog + DataManager 도입 3차: partial 분리 4차: gameplay entry roster query 통일 5차: legacy seeder 폐기 + dataset row/parser 분리 + collection query 확장
