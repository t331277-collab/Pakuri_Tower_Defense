단계 요약

단계 핵심 변화 당시 판정 다음 단계로 넘어간 이유
0단계 기준선 CSV, markdown, hardcoded seeder, SO asset이 섞인 구조 개선 전 원본 고정, 검증 강제, 조회 계약 통일이 필요했다.
1차 개선 초기 CSV runtime migration, startup parse/validation/quit 경로 도입 부분 구현 Reviewer가 hidden fallback, asset path, query contract 문제를 지적했다.
Reviewer 게이트 수동 Code Reviewer FAIL FAIL 리소스/빌드 안전성, source-of-truth 고정, 조회 계약 미흡이 확인됐다.
2차 개선 Assets/CSVdata/source, resource-backed source/asset catalog, PakuriDataManager 도입 부분 구현 핵심 방향은 맞아졌지만 loader monolith와 query 범위가 아직 컸다.
3차 개선 PakuriCsvRuntimeData를 entry/loader/validation/build/editor/types로 분리 부분 구현 row model은 아직 dataset별 파일로 안 갈라졌고, query 통일도 끝나지 않았다.
4차 개선 GetMonsters, GetStageOneEnemies, ResolveMonster 추가 및 MainMenu/Run/Debug/Combat entry 통일 부분 구현 legacy seeder 제거, dataset 세분화, 전 프로젝트 query 통일이 아직 남아 있다.

0단계 기준선: 개선 전 구조

실제 상태

  • 2026-05-01-data-structure-review.html과 DATA board 기준으로 원본이 csv + markdown + 하드코딩 + asset 혼합 상태였다.
  • PakuriGameDataSeeder.cs가 5몬스터/8적을 코드에 직접 들고 markdown skill 문서를 읽어 SO asset을 갱신했다.
  • GameDataCatalog.asset는 5 몬스터와 Stage 1 적 8개만 가지는 구조였다.

당시 미구현

  • CSV 고정 source-of-truth
  • 강한 type row 계약
  • startup fatal validation
  • runtime-safe asset binding catalog
  • 통일된 DataManager 조회 계약

다음 단계 목표

  • 런타임 로딩의 원본을 한 곳으로 모을 것
  • 파싱/검증 실패를 조용히 넘기지 않을 것
  • scene consumer의 data lookup을 한 계약으로 모을 것

1차 개선: 초기 CSV Runtime Migration

DATA board history 기준으로 첫 구현은 Pakuri/data/source를 직접 읽는 초기 CSV runtime loader를 만들고, 게임 시작 시 파싱과 validation을 수행한 뒤 치명 오류면 종료하는 흐름을 추가하는 것이었다.

구현됨

  • typed CSV source set 개념 도입
  • startup parse + validation + quit 경로 도입
  • combat startup이 CSV-backed catalog를 선호하도록 방향 전환 시작

부분 구현

  • CSV-first 방향은 잡혔지만 실제 source root가 아직 Pakuri/data/source file path였다.
  • 검증은 id/link/slot 규칙 위주였고 asset path 바인딩 안전성은 부족했다.

미구현 / 이월

  • player runtime-safe asset reference 구조
  • 통일된 query contract
  • dataset 단위 파일 분리

근거는 boards/DATA/DATA_BLACKBOARD.md의 `2026-05-02 CSV Source Runtime Migration` History와, boards/COMBAT/COMBAT_BLACKBOARD.md의 `Combat Catalog Source Resolution To CSV Runtime Data` 초기 History다.

중간 Reviewer 게이트: FAIL

이 리팩토링은 한 번에 끝나지 않았다. boards/OPS/REVIEWER_BLACKBOARD.md의 `CSV Runtime Migration Reviewer 2026-05-02` 기록 기준으로, 외부 Reviewer는 타임아웃됐고 수동 Code Reviewer pass는 FAIL 판정을 남겼다.

  • 지적 1: non-Resources asset path가 player runtime에서 안전하지 않았다.
  • 지적 2: CSV가 비면 GameDataCatalog.asset가 다시 숨은 원본처럼 동작할 수 있었다.
  • 지적 3: unified query contract가 없었다.
  • 지적 4: loader/row model/validator가 한 파일에 몰려 있었다.

이후 사용자가 CSV를 Pakuri/Assets/CSVdata로 import했고, 다음 단계 개선은 이 FAIL 항목을 고치는 방향으로 진행됐다.

2차 개선: Resources-backed CSV Runtime 재구성

Reviewer FAIL 이후의 follow-up은 “CSV를 실제 런타임 원본으로 고정하고, asset path와 query contract의 최소 뼈대를 세우는 것”에 집중됐다.

구현됨

  • source root를 Assets/CSVdata/source로 이동
  • PakuriCsvRuntimeSourceCatalog.asset와 PakuriCsvRuntimeAssetCatalog.asset 생성
  • asset-path coverage validation 추가
  • PakuriDataManager singleton registry 추가
  • CSV 초기화 실패 시 serialized catalog hidden fallback 차단

부분 구현

  • GetData<T>(id)는 들어갔지만 query contract는 아직 Run 진입부 lookup 중심이었다.
  • loader/validation/build/editor/type 지원이 여전히 큰 정적 파일 묶음이었다.

미구현 / 이월

  • MainMenu/Debug/Combat entry의 전면 roster query 통일
  • monolith 분해
  • legacy seeder 정리

근거는 boards/DATA/DATA_BLACKBOARD.md, boards/RUN/RUN_BLACKBOARD.md, boards/COMBAT/COMBAT_BLACKBOARD.md의 2026-05-02 CSV runtime migration / catalog source resolution task blocks와 현재 PakuriCsvRuntimeData.cs, PakuriDataManager.cs다.

3차 개선: Loader Monolith 분해

다음 단계는 기능 축 기준의 파일 분해였다. 기존 PakuriCsvRuntimeData.cs 하나에 몰려 있던 로직을 runtime entry / loader / validation / build / editor / types로 나눴다.

구현됨

  • PakuriCsvRuntimeData.cs: runtime entry
  • PakuriCsvRuntimeData.Loader.cs: source load
  • PakuriCsvRuntimeData.Validation.cs: source/runtime validation
  • PakuriCsvRuntimeData.Build.cs: in-memory catalog build
  • PakuriCsvRuntimeData.Editor.cs: bootstrap/sync/menu
  • PakuriCsvRuntimeData.Types.cs: parser support / row model

부분 구현

  • monolith는 해소됐지만 row model과 parser support 타입은 아직 Types.cs 하나에 남아 있다.

미구현 / 이월

  • dataset별 row model 파일 분리
  • validator의 dataset 단위 세분화

근거는 boards/DATA/DATA_BLACKBOARD.md의 `Builder split PakuriCsvRuntimeData.cs ...` history와 현재 파일 구조다.

4차 개선: 조회 계약 통일

마지막 구현 단계는 “게임플레이 진입부에서 아직 남아 있던 direct catalog access를 줄이는 것”이었다. 이 단계에서 PakuriDataManager는 단순 id lookup registry에서 roster/fallback query 계약을 가진 data access 레이어로 확장됐다.

구현됨

  • GetMonsters(...), GetStageOneEnemies(...), ResolveMonster(...) 추가
  • MainMenu / RunFlow / DebugScene roster query 통일
  • RunCombatUi / RunSceneBootstrap fallback monster resolution 통일
  • CombatRuntimeEnemies stage-one enemy pool lookup 통일

부분 구현

  • 현재 통일 범위는 gameplay entry/UI와 stage-one enemy pool 중심이다.
  • 프로젝트 전체 모든 data consumer가 stable-id query service로 완전히 정리된 것은 아니다.

미구현 / 이월

  • legacy seeder 제거
  • 모든 consumer의 query contract 전면 통일
  • display-name 기반 run state 정리

근거는 boards/DATA/DATA_BLACKBOARD.md, boards/RUN/RUN_BLACKBOARD.md, boards/COMBAT/COMBAT_BLACKBOARD.md의 query unification task blocks와, 현재 PakuriDataManager.cs, MainMenuFlowController.cs, DebugSceneController.cs, RunFlowController.cs, RunCombatUiController.cs, RunSceneBootstrap.cs, CombatRuntimeEnemies.cs다.

현재 시점 정리: 구현됨 / 부분 구현 / 미구현

항목 현재 상태 근거
CSV 원본 고정 구현됨 Pakuri/Assets/CSVdata/source, PakuriCsvRuntimeSourceCatalog, startup load/validate/build path
type row 기반 강한 파서 구현됨 현재 CSV runtime parser와 validation 경로
runtime-safe asset binding 구현됨 PakuriCsvRuntimeAssetCatalog + source/runtime validation
query contract 통일 부분 구현 PakuriDataManager는 확장됐지만 전 프로젝트 완전 통일은 아님
monolith 분해 부분 구현 partial 분리는 완료, dataset-level row model 분리는 미완료
legacy seeder 제거 미구현 Assets/Scripts/Data/Editor/Legacy/PakuriGameDataSeeder.cs 잔존
Builder follow-up 이후 Reviewer 재실행 미구현 boards/OPS/REVIEWER_BLACKBOARD.md는 새 Reviewer pass 미실행 상태를 기록한다.

결론

이 리팩토링은 한 번에 끝난 작업이 아니었다. 실제 기록상 흐름은 1차 개선으로 방향 전환, Reviewer FAIL로 문제 노출, 2차 개선으로 runtime-safe한 CSV-first 구조 보강, 3차 개선으로 loader 분해, 4차 개선으로 gameplay entry query 통일 순서로 진행됐다.

따라서 현재 상태를 가장 정확히 표현하면 “원본 고정과 런타임 로딩 구조는 구현 완료, query와 dataset 구조는 단계적으로 개선 중, legacy authoring 경로 정리는 아직 미완료”다.

현재 리팩토링 단계를 한 줄로 요약하면: 0단계 기준선 확인 → 1차 개선: 첫 CSV runtime migration → Reviewer FAIL → 2차 개선: resource-backed source/asset catalog + DataManager → 3차 개선: PakuriCsvRuntimeData partial 분리 → 4차 개선: MainMenu/Run/Debug/Combat entry query contract 통일 → 잔여 과제: legacy seeder 제거 / dataset 세분화 / 전면 query 통일 / Reviewer 재검증
