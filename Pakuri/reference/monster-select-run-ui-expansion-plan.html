Pakuri 몬스터 선택 UI + Run 확장 설계안

이 문서는 현재 구현된 이브 단독 전투 프로토타입 위에 몬스터 선택 UI, Run 시작, 전투 종료 후 스킬/보상 선택을 어떻게 확장하는 것이 맞는지 정리한 설계 문서다. 아래 내용은 실제 코드와 reference 문서를 다시 확인한 뒤, 현재 있는 것과 새로 제안하는 구조를 분리해서 적었다.

짧은 결론

지금 상태에서 가장 안전한 방향은 현재 이브 전용 전투 컨트롤러를 바로 덧칠하지 않고, Run 상태 관리, UI 상태 관리, 몬스터/스킬 데이터, 공통 전투 계산을 먼저 분리하는 것이다.

추천 흐름은 하나의 씬에서 오버레이 UI만 전환하는 방식이다. 즉 몬스터 선택 패널 → 전투 HUD → 전투 종료 보상 패널을 같은 런타임 위에 얹고, 선택한 몬스터에 따라 전투용 실행기만 바꾸는 구조가 현재 프로젝트 규모와 가장 잘 맞는다.

현재 확인된 사실

  • 코드 현재 게임 전용 C# 스크립트는 DamageCalculator.cs, EveVerticalSliceController.cs 두 개만 있다.
  • 씬 현재 활성 씬은 Assets/Scenes/SampleScene.unity이며, 루트 오브젝트는 Main Camera, Global Light 2D, CombatRoot 3개다.
  • 전투 CombatRoot 아래에는 Nexus, EveUnit, EnemySpawnPoint, InputTarget, EnemyRoot, ProjectileRoot가 있다.
  • UI Assets 아래에서 .uxml, .uss 파일은 확인되지 않았다. UI 명칭이 붙은 별도 자산도 없다.
  • 현재 보상 EveVerticalSliceController는 승리 시 고정된 이브 전용 보상 버튼 3개를 직접 생성한다. 문서 기반 풀 생성 구조는 아직 없다.
  • 현재 전투 계산 DamageCalculator.Resolve(...)는 단일 defense 값만 받아 계산한다. 문서의 속성별 저항 구조는 아직 반영되지 않았다.

지금 바로 막히는 지점

  • 공통화 부족 현재 전투 코드는 변수명과 로직이 eveSpellPower, eveBaseLightningDamage처럼 이브에 강하게 고정돼 있다.
  • 상태이상 부족 현재 런타임에는 감전 비슷한 단순 스택만 있고, 문서에 있는 추위, 빙결, 취약, 신성 방어막, 축복, 신성 노출, 이름표식, 침묵, 몰살 허가를 공통 처리하는 시스템이 없다.
  • 보상 규칙 부족 일반/중간보스/보스 전투별 골드, 어둠의 흔적, 포로, 유물 보상 차등 지급과 스테이지 배율이 코드에 없다.
  • 스킬 선택지 부족 현재는 신규 액티브, 신규 패시브, 액티브 특성, 마스터를 섞는 선택지 풀이 없다.
  • 범위 제약 린은 현재 실제 폴더에 f-ambidextrous.md만 있고 g~j 패시브 문서가 없다. 따라서 1차 구현에서는 린을 플레이 가능한 선택지로 두기 어렵다.

추천 플레이 흐름

1. 시작 패널 Run 메인 창에서 문서가 완비된 4개 몬스터 카드 중 1개를 고른다. 린 카드는 보이더라도 준비 중 더미 상태로 잠가 둔다. 카드에는 역할, 속성 축, 시작 스킬 A 이름을 보여준다.
2. Run 시작 선택한 몬스터를 기준으로 RunSession을 생성한다. 초기 습득 스킬은 액티브 A만 보유, 패시브는 없음으로 시작한다.
3. 전투 HUD 전투 중에는 선택 몬스터 정보, 탄창/재장전, 현재 일차/스테이지, 전투 종류, 적 수, 넥서스 체력을 표시한다.
4. 전투 종료 보상 골드, 어둠의 흔적, 포로, 유물 여부를 먼저 보여주고, 그 다음 스킬 선택지 3개 중 1개를 고르게 한다.
5. 다음 일차 진행 선택 결과를 현재 RunSession에 반영하고, 11일차 구조에 따라 다음 전투 또는 스테이지 전환으로 넘어간다.

UI 구조 제안

현재는 UI 자산이 전혀 없으므로, 저는 UI Toolkit 기반의 단순 오버레이 UI를 추천한다. 이유는 현재 OnGUI로 임시 HUD를 그리고 있지만, 몬스터 선택 카드 / 런 시작 버튼 / 보상 선택 카드 / 다음 일차 버튼까지 늘어나면 즉석 OnGUI 방식은 빠르게 지저분해질 가능성이 높기 때문이다.

패널 목적 핵심 요소 현재 상태
RunFrontPanel 몬스터 선택과 Run 시작 몬스터 카드 4개, 역할 요약, 시작 스킬 A, Start 버튼, 린 더미 카드 없음
RunHudPanel 전투 중 상태 표시 스테이지/일차, 선택 몬스터, HP, 탄창, 현재 스킬 세트 현재는 OnGUI 임시 HUD만 있음
RewardPanel 전투 종료 보상 선택 골드, 어둠의 흔적, 포로 요약, 유물 3택1, 스킬 선택지 3개 현재는 이브 고정 선택지 3개만 있음

씬은 우선 하나로 유지하고, 패널 표시 상태만 바꾸는 쪽이 현재 SampleScene 기반 프로토타입과 가장 잘 맞는다.

씬 오브젝트 제안

  • 제안 CombatRoot/EveUnit는 SelectedMonsterUnit 또는 TowerUnit로 일반화한다.
  • 제안 선택한 몬스터에 따라 같은 위치에 다른 실행기를 붙인다.
  • 제안 카메라, 넥서스, 적 스폰 포인트, 투사체 루트는 공통 전장 자산으로 유지한다.

보상 선택지 생성 규칙 제안

  1. 현재 몬스터가 배울 수 있는 신규 액티브를 찾는다. 액티브는 A 포함 최대 3개까지만 허용한다.
  2. 현재 몬스터가 배울 수 있는 신규 패시브를 찾는다. 패시브는 최대 3개까지만 허용한다.
  3. 패시브 F는 기본적으로 후보에 넣고, G~J는 대응 액티브를 배웠을 때만 후보에 넣는다.
  4. 이미 배운 액티브는 남아 있는 특성이 있을 때 특성 후보를 넣는다.
  5. 액티브 특성 3개를 모두 고른 액티브는 마스터 선택지 2개 중 아직 고르지 않은 후보를 넣는다.
  6. 모든 후보를 하나의 풀에 모아 섞고, 중복 없이 3개를 보여 준다.
  7. 선택한 후보는 이후 동일 런에서 다시 후보로 나오지 않게 한다.

이 흐름 자체는 monster-basic-rule.md, skill-choice-pool-rule.md, 그리고 사용자 결정과 맞는다. 패시브는 슬롯 F~J 총 5개가 존재하고, 런 중 최대 3개까지 습득하는 구조로 보는 것이 맞다.

왜 공통 전투 코어가 먼저 필요한가

  • 속성 저항 문서 기준 피해는 물리/화염/번개/얼음/어둠/신성 6속성 저항을 각각 참조한다. 현재 계산기는 이 구조가 없다.
  • 행동속도 문서 기준 행동속도는 발사 간격과 쿨타임 충전에 영향을 준다. 현재 전투 코드는 이브의 개별 필드만 직접 조절한다.
  • 상태이상 베가의 이름표식, 아리엘의 방어막, 세인의 화염 저항 감소, 이브의 빙결 계열은 공통 상태 저장소 없이는 누적이 어렵다.
  • 무기 타입 차이 기본 A 스킬만 봐도 단일 투사체, 3연 검기, 관통, 방어막 시너지, 표식 연계가 모두 다르다. 현재 이브용 투사체 코드만으로는 확장성이 낮다.

추천 구현 순서

  1. 1단계: Run 상태와 UI 상태 분리
    현재 EveVerticalSliceController가 함께 들고 있는 전투/보상/일차 상태를 RunSession과 CombatDirector로 나눈다.
  2. 2단계: UI Toolkit으로 선택 패널, HUD, 보상 패널 뼈대 작성
    이 단계에서는 먼저 버튼과 텍스트만 동작해도 된다.
  3. 3단계: 몬스터/스킬 카탈로그 데이터 작성
    아리엘, 이브, 세인, 베가의 A~J 스킬 메타데이터와 특성/마스터 정의를 먼저 정리하고, 린은 더미 엔트리만 둔다.
  4. 4단계: 전투 공통 스탯/속성/상태 처리 추가
    속성별 저항, 치명타 저항, 행동속도, 방어막, 표식, 감전/추위/빙결/침묵 처리 기반을 만든다.
  5. 5단계: 몬스터별 기본 A 스킬 실행기 구현
    Run 시작 직후 플레이 가능하려면 최소한 문서가 완비된 4몬스터의 A 스킬은 모두 동작해야 한다. 린은 이 단계에서 더미 유지다.
  6. 6단계: 보상 선택지 풀 생성기 구현
    문서 기준으로 신규 액티브, 신규 패시브, 특성, 마스터를 하나의 후보 풀로 만들고 3개를 제시한다.
  7. 7단계: B~E, F~J 실제 효과 구현
    보상에서 선택 가능한 항목은 실제 런타임 효과가 있는 것만 노출하는 것이 안전하다.
  8. 8단계: 포로와 유물의 후속 시스템 연결
    이 부분은 스킬 강화 UI와 별도로 확장할 수 있다.

제가 권하는 구현 원칙

  • 권장 선택지 UI는 먼저 단순하게 만든다. 카드 디자인보다 상태 전환과 데이터 연결이 먼저다.
  • 권장 몬스터별 A 스킬은 실행기 클래스로 나누고, 현재 이브 코드는 그 첫 사례로 분해한다.
  • 권장 문서 간 수치 충돌이 있는 항목은 엔진에 상수로 박지 말고 데이터 정의를 그대로 읽게 만든다.
  • 주의 실제 효과가 없는 스킬을 보상 선택지에 먼저 띄우면 플레이어가 선택 후 결과를 신뢰하지 못하게 된다.

확정된 결정 사항

  • 확정 모든 몬스터는 패시브 슬롯 F~J 총 5개를 가진다.
  • 확정 런 중 실제로 습득 가능한 패시브는 최대 3개다.
  • 확정 이번 범위에서 포로 보상은 표시만 하는 정보로 처리하고, 영입/합류 시스템은 나중에 붙인다.
  • 확정 1차 플레이 가능 몬스터는 아리엘, 이브, 세인, 베가 4종으로 두고, 린은 더미 상태로 남긴다.
  • 확정 따라서 첫 구현에서는 몬스터 선택 → Run 시작 → 전투 → 보상 표시 → 스킬 선택 흐름을 우선 완성하면 된다.

남은 실제 문서 갭

  • 저장소 확인 아리엘, 이브, 세인, 베가는 실제 폴더에 f~j 패시브 문서가 모두 있다.
  • 저장소 확인 린은 현재 실제 폴더에 f-ambidextrous.md만 있고 g~j 패시브 문서는 없다.
  • 의미 사용자 결정에 따라 1차 구현에서는 린을 더미 상태로 두고, 문서가 완비된 4몬스터만 플레이 가능 대상으로 잡는 것이 현재 저장소 상태와 맞다.

한 줄 추천

저는 이 작업을 “이브 전용 전투 코드에 UI를 얹는 일”로 보기보다, “단일 몬스터 Run 프레임을 일반화해서 우선 4개 몬스터를 안정적으로 받게 만들고, 린은 더미로 남겨 후속 확장 여지를 확보하는 일”로 보는 게 맞다고 생각한다. 그래야 몬스터 선택, 스킬 풀, 전투 후 보상, 추후 유물/포로 확장까지 한 번의 구조로 이어진다.
